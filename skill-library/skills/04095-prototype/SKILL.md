# Prototype

原型（prototype）是**回答一个问题的抛弃式代码**。问题决定它的形态。

## 选一个分支

利用用户的提示、周边代码，或者趁用户在场时直接问，确定要回答的是哪个问题：

- **「这套逻辑 / 状态模型感觉对吗？」** → [LOGIC.md](LOGIC.md)。构建一个可分享的单个 HTML 文件（自由把玩的按钮加上分页的引导式走查），推动状态机穿过那些纸上难以推理的用例，而且非开发者也能操作。
- **「它应该长什么样？」** → [UI.md](UI.md)。在单一路由上生成几个截然不同的 UI 变体，通过 URL 查询参数和一个悬浮底栏切换。

两个分支产出的制品截然不同，选错会浪费整个原型。如果问题确实模棱两可且联系不上用户，就默认选择与周边代码更匹配的那个分支（后端模块 → logic；页面或组件 → UI），并在原型顶部写明这个假设。

## 两者共同适用的规则

1. **从第一天起就是抛弃式的，并且明确标注。**把原型代码放在它真正会被用到的地方附近（挨着它为原型而服务的模块或页面），让上下文一目了然，但命名要让随便一个读者都能看出它是原型、不是生产代码。对于抛弃式 UI 路由，遵守项目已有的路由约定；不要发明新的顶层结构。
2. **运行起来毫不费力。**UI 原型从项目任务运行器里的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示是用户双击即开的单个 HTML 文件。无论哪种，启动都不需要动脑。
3. **默认不做持久化。**状态住在内存里。持久化正是原型要*检验*的东西，而不是它应当依赖的东西。如果问题明确涉及数据库，就使用一个临时数据库或本地文件，并取一个明确的「PROTOTYPE, wipe me（原型，可清空）」名字。
4. **跳过打磨。**不写测试，不做超出让原型_跑得起来_之外的错误处理，不搞抽象。目的是快速学到东西。
5. **把状态亮出来。**每次动作之后（逻辑），或每次切换变体时（UI），打印或渲染完整的相关状态，让用户看到什么变了。
6. **完成后把它留存下来。**把任何经过验证的决策折进真实代码，然后把原型本身留存为**一手来源**：提交到一个主干之外的一次性分支，并在实现议题上留下指向该分支的上下文指针。答案（结论和它所敲定的问题）也要记录在议题或某次提交中。主干分支只保留经过验证的决策。
