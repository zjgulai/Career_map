# Simplify Codebase（简化代码库）

减少代码库必须保持一致的概念与义务的数量。行数减少只是辅助证据，不是目标。一次成功的运行完全可以得出结论：受检面已经合理，无需简化。

## 选择模式与范围

先选**授权模式**：

- **Survey（审计）**：用于简化审计、调查或候选发现类请求。保持只读，返回带排序的证据。
- **Change（修改）**：用于明确的简化、删除、合并、重构或仓库文档修改请求。证明每一刀，在授权范围内实施，并验证存活下来的契约。

再选**覆盖范围**：

- **Focused（聚焦）**：用户点名了某个子系统、符号、状态机、依赖或疑似重复点时使用。先把该边界覆盖透，再向外扩展。
- **Broad（全库）**：请求横跨整个仓库或要求给出多个候选时使用。先对系统分区，再逐一交代范围内每个域。

删除一个仍可达的能力、仍被支持的接口、持久化表示或兼容路径，是**产品决策**。除非用户已经选定，否则先描述后果并取得指示，再动手。

## 建立契约

1. 读仓库的指引、架构与决策记录、清单文件、测试指引和生成文件约定。
2. 检查版本控制状态，保留无关的改动。分类前先识别 vendored、生成、迁移、fixture 和公开包等表面。
3. 从入口点出发，沿配置、注册、分发、持久化、进程和线路边界追踪运行时路径。记录公开的、动态的、持久化的、生成的和兼容敏感的契约。
4. 在 Change 模式下，找到仓库真实的验证命令，条件允许时采集一个成比例的基线。基线本身失败时，要说明它收窄了最终检查能证明的范围。

保护授权、信任边界校验、安全隔离、无障碍要点、防数据丢失、存储格式兼容和建立静默状态的清理逻辑。对这些保护的改动要当作**独立的、被明确授权的目标**，不能当作简化时的顺带行为。

契约地图完整的标准：范围内所有入口点与授权边界都已枚举，每一条都追踪到能说出其所有者和可观察契约的程度，每一处未检查或外部不可知的面都记为盲点。

## 覆盖相关面

对每一次 Broad 任务，以及对涉及动态架构或依赖替换的 Focused 任务，先读 [investigation.md](references/investigation.md)。在给发现排序前先建覆盖地图；第一个看似可删的候选不得终结调查。

涉及并发、取消、就绪、清理、防御性拷贝、校验、授权、安全隔离、无障碍、防数据丢失或跨进程数据时，再读 [boundaries-and-lifecycle.md](references/boundaries-and-lifecycle.md)。

用仓库原生的搜索、编译器和 linter 输出、依赖元数据与历史记录作为发现工具。在运行时消费者和契约被查验之前，只把它们的结果当作线索。

## 建立证明记录

对每个进入消费者地图证据阶段、或可能退役一条有意义的契约的范围内线索，记录：

```text
Finding ID: 稳定的报告内标识，如 S1 或 S2
Candidate: 拟删除或合并的确切契约、表示或层
Locus: 所有权边界、符号，以及验证过的精确路径或行号
Topology: 已确认的节点与关系 ID、主位置、相关节点、路径与割集（有用时）；否则不适用
Burden: 它造成的概念、同步、发布或测试成本
Reachability: 生产、非生产、动态、外部与持久化消费者分别是谁
Rationale: 它为什么存在，那个理由今天是否仍然成立
Cut: 受影响的声明、实现、分支、产物、文档与依赖
Consequence: 被放弃的可观察能力或兼容行为
Confidence / risk: 证据强度、不确定性、爆炸半径与可逆性
Proof: 能暴露一次错误删除的最小检查
Net effect: 移除的维护概念减去新增的替代或迁移机制
```

保持 Finding ID 在一次运行内稳定，让摘要、证明记录、源码链接和任何可视化伴随物指向同一个候选。不要为填位置字段而编造行号、所有者、关系或路径。未知事实标为 unresolved（未决）。

当候选与存活消费者共享同一产物时，证明删除边界要细到**文件粒度以下**：交代候选独有的选择器、成员、字段、键、注册表条目、生成片段和 fixture，同时不惊动存活的拥有者。

出现以下情况时，保留或降级候选：存在真实消费者；动态可达性仍未查清；当前决策仍然拥有该设计；改动只是把复杂度搬到别处；结果超出范围或没有退役任何有意义的义务；或者可用的检查无法区分成功与意外破坏。

**置信度与收益分开排序。** 一个高价值的猜测不高于一个更小的、已证明的切割。

候选证明完整的标准：每个合格线索都被分类为已排序（ranked）、已拒绝（rejected）或未决（unresolved），且每个未决线索都写明做决定所需的事实。

## 决定与行动

Survey 模式下，报告带排序的证据后即停。当某个被拒绝的重要候选能带来教训、或指出了一个具体的缺失事实时，把它一并写入。

Change 模式下，读 [execution-and-recovery.md](references/execution-and-recovery.md)，选择最强的已授权切割。默认批大小是**一个所有权边界**，不是一次运行的限额：对一组明确要求的切割，完成并验证一个边界后再开始下一个。

如果用户请求简化提案、本地清理标注或设计记录合并，或者选中的改动会使 ADR、RFC、设计笔记或架构清单失效，读 [decision-records.md](references/decision-records.md)。不要把一次普通代码审计变成仓库级文档清洗。

如果用户要求合并来自另一个分支、PR、任务或 agent 运行的发现，读 [integrating-findings.md](references/integrating-findings.md)。保留证据，不保留候选数量。

**只有用户明确要求、或确认了你的提议时，才生成可视化伴随物。** 如果已确认的关系能让某个候选更清楚，说明这张图会讲清什么，并**先询问**再生成。未经确认就交付文字报告，不要因为等可视化交付而拖延审计。可视化交付经授权后，读 [visual-reporting.md](references/visual-reporting.md) 并使用内置的 cleanup-map renderer。地图是证明记录的可选伴随物，本身不是证据。除非用户要求写仓库文件，否则不要把 Survey 产物写进目标仓库。

## 交付结果

Survey 交付：覆盖范围、带排序的证明记录、被拒绝或未决的高价值线索、每个不确定点的下一条所需事实。可视化伴随物被请求或确认时，单独报告它的状态与 cleanup-map 的 Finding 深链接。

让交接保持可扫读。**先给结果**，然后只保留用户需要的证明记录、影响决策的不确定性、可视化链接与验证。不要叙述搜索过程，不要用几个标签重复同一证据，不要附通用建议，不要留空章节。简洁不减少必填的证明字段：每个字段只写一次，用最短的形式保留其主题、证据强度、后果与边界。

Change 交付：完成 [execution-and-recovery.md](references/execution-and-recovery.md) 定义的验证与操作回执。一张 Before/Cut/After/Verify cleanup map 可以解释结构改动，但**永远不能替代操作回执**。分层报告每层验证；一个窄范围的绿灯不构成更广的运行时、部署或用户验收。
