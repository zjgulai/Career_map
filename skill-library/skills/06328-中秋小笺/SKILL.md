# mid-autumn-chat-letter（中秋小笺）

生成“深海军蓝夜空 + 奶油金 + 左侧信息组 + 右上月亮奔跑玉兔 + 下半数据卡片”的中秋年度对话报告竖版海报。宽度固定 1080，高度随内容自适应。

支持两种对象：
- **私聊（1:1）**：给定一位同事，统计“你 × TA”两人的一年，头部显示「本人 × 同事」，文案写两个人的情谊。
- **群聊（group）**：给定一个群，统计全群所有人的一年，头部只显示**群名**，第 5 张卡显示**群里说话最多的人**、第 8 张卡标签变为“全群最爱的表情”，文案讲这群人这一年共同的故事与对全体的祝愿。

另有 **模式 B · 纯视觉修改**：用户已有海报、只改样式（月亮、月饼、顶部排布、去残影、修拼接），此时用 `scripts/rebuild_top_zone.py` 的确定性重建思路，不要整图交给生图模型。该脚本依赖的 `template_poster.png`、`moon_rabbit_reference.png` 不随技能分发，在“中秋小笺_可选源素材.zip”内，用到时按 README 放回 `assets/`。

## 本地运行（跨平台：macOS / Windows / Linux）

技能不依赖彩色 emoji 字体（月饼/月亮玉兔/二维码/LOGO 都内置为图片资产），换电脑结果一致。中文字体也已内置（子集覆盖《通用规范汉字表》8105 字，含现代通用中文与常见姓名，如“昇”），仅当遇到该表之外的极生僻人名用字时，才会逐字自动回退到系统自带中文字体，保证不出现豆腐块（详见下文“字体与缺字回退”）。

1. 需要 Python 3.8+。安装运行依赖（仅两个必需）：`pip install -r requirements.txt`（Pillow、jieba）。
2. 首次运行先自检：`python3 scripts/check_env.py`（Windows 用 `py` 或 `python`），必需项全部 ✓ 再继续；脚本逐项检查 Python、依赖、内置字体、视觉资产与合成能力，并给出缺什么、怎么修。
3. 已内置资产（正常情况下无需在系统里装字体）：
   - 中文字体 `assets/fonts/`：仅两套——`NotoSerifCJK-Bold-SC.otf`（标题/数字，宋体粗）与 `NotoSansCJK-Medium-SC.otf`（正文/标签，黑体中粗）。它们是从官方 Noto CJK 多语言 TTC 抽出简体子字体（TTC index 2）、再按 **ASCII + 《通用规范汉字表》8105 字（含 GB2312，并额外覆盖“昇”等约 1300 个人名 / 地名 / 科技用字）+ 常用标点** 子集化并做 CFF 特化压缩的产物，两套合计约 4.2MB（整套技能解压约 4.4MB）。
   - **缺字自动回退（逐字）**：渲染时每个字先查内置子集，遇到《通用规范汉字表》之外的极生僻字（如 䶮、𬱖 等扩展区人名用字），该字自动改用系统中文字体绘制，按字重走一条回退链（Linux 优先 Noto Sans/Serif CJK SC，其次 Droid/文泉驿；macOS 用 PingFang/STHeiti；Windows 用微软雅黑/宋体/黑体；都没有再用 `fc-list` 兜底），其余字仍用内置字体，因此既不出现豆腐块、视觉也几乎无差异。系统里完全没有任何中文字体的极端情况下，内置 8105 字子集仍能覆盖几乎全部正常文案。维护者可用 `scripts/subset_fonts.py`（需 `pip install fonttools`，可选 cffsubr；仅打包时用）从官方 TTC 重新生成，脚本顶部 `COVERAGE` 可在 `"common"`（默认、8105 字）、`"gb2312"`（最小）与 `"gbk"`（约 2.2 万字、更大）之间切换。
   - 月亮玉兔成品抠图 `assets/moon_rabbit_cutout.png`（600×760 透明底，直接贴，**不需要 numpy/opencv**）。
   - 月饼成品图 `assets/mooncake_emoji.png`（🥮，直接缩放贴入，**不需要彩色 emoji 字体**）。
   - 固定二维码 `assets/qr_code.png`、组合 LOGO `assets/logos/feishu_doubao_logo.png`。
4. 多级回退（保证不崩、不出空白）：
   - 月亮玉兔：`get_moon_rabbit()` 优先成品抠图 `moon_rabbit_cutout.png`；仅当成品缺失才用 numpy+cv2 从 `moon_rabbit_reference.png` 重抠——该参考图不随技能分发，在单独的“中秋小笺_可选源素材.zip”里，正常生成用不到。
   - 月饼：`get_mooncake()` 优先成品 `mooncake_emoji.png` → 系统彩色 emoji 字体（macOS Apple Color Emoji / Windows Segoe UI Emoji / Linux NotoColor Emoji）→ 程序化简笔月饼。
   - 二维码：固定 `assets/qr_code.png`；仅当资产缺失且装了 qrcode 时才按 `--qr-url` 动态生成。
   - 因此 `numpy`、`opencv-python-headless`、`qrcode`、`fonttools` 默认都**不必安装**。
5. 拉取聊天记录（第 1 步）需要可用的 lark-cli 并已登录。解析顺序为 `LARK_CLI` 环境变量 → PATH → 常见目录；不在 PATH 时设置 `LARK_CLI=/完整路径/lark-cli`（Windows 可为 `.cmd/.exe`）。仅做本地复算（`--from-raw`）或纯渲染时不需要 lark-cli。
6. Windows 路径含空格要加引号。
7. **安全命令约束（避免新用户首次使用弹出“危险指令”确认）**：本技能是普通文件夹、放进 `.user_skills/mid-autumn-chat-letter/` 即可直接运行，**无需安装脚本，也不要执行任何 `rm -rf` / `rm -fr` / 递归强制删除 / `sudo` / 清空固定临时目录（例如 `rm -rf /tmp/skill_install`）之类的高危命令**——生成海报完全不依赖删除任何目录。解压技能时直接解压到唯一临时目录（Python `tempfile.mkdtemp()`，用完交给系统回收）或解压覆盖即可。脚本内确需清理时，只用 Python `shutil.rmtree()` 删除自己刚创建的目录（技能现状仅一处、删自身分段缓存）。据此执行，新用户首次使用不会看到危险指令确认，**生成过程与产物完全不变**。

## 模式 A：数据驱动生成（三步）

依赖：拉数据需 `lark-cli`（已登录，统一带 `--as user`）；Python 侧渲染只需 Pillow、统计只需 jieba。

### 第 1 步：拉取并统计聊天记录

**对象解析（最高优先级，先于一切追问）：** 先从用户这条消息里直接拿到“对象 + 类型”，能直接确定就**直接跑下面的命令，不要追问**：

- **@ 了人**（飞书 @ 会携带该用户的账号标识）：直接判定为**私聊**、对象就是被 @ 的人——拿得到 id 时优先用 `--open-id <ou_...>`，否则用 `--colleague "<@显示名>"`；**不要再问“私聊还是群聊”，也不要让用户重新输入姓名**。
- **@ 了群 / 插入群名片或群链接**（携带 chat_id）：直接判定为**群聊**，优先 `--chat-id <oc_...>`，否则 `--group "<群名>"`，同样跳过类型与名称追问。
- 消息里直接给了 open_id / chat_id / 飞书会话链接：按上述对应类型直接解析使用。
- **只有当用户没有 @、没给链接或 id、只给了一个名字或只说“帮我做中秋海报”时**，才追问：先确认私聊 / 群聊，再请对方提供姓名或群名（追问尽量少、一轮问清，不要分两轮）。
- 仅在有歧义时才确认：一条消息同时 @ 了多个人、或又 @ 人又 @ 群、无法判断唯一对象时，列出来让用户选一个。
- @ 的若是**用户本人**：提示“不能和自己生成私聊小笺，请 @ 一位同事或一个群”。
- @ 已携带唯一 id 时无需再做同名确认；只有只拿到名字文本、且检索出重名 / 多候选时，才按下面的“同名 / 多候选二次确认”列候选。

**私聊：**
```bash
python3 scripts/chat_analyzer.py \
  --colleague "<同事姓名>" --days 365 --user-name "<本人姓名>" \
  --output chat_stats.json --raw-output messages_raw.json
```
**群聊：**（把 `--colleague` 换成 `--group`；多候选时用 `--chat-id` 显式指定）
```bash
python3 scripts/chat_analyzer.py \
  --group "<群名>" --days 365 \
  --output group_stats.json --raw-output group_raw.json
```

> **这条命令要按同样的参数反复调用，直到返回 `status="completed"`。** 单次最多跑 115 秒就会返回；返回 `status="in_progress"` 表示进度已落盘、还没拉完，**原样再跑一遍**即可从断点继续（详见下面"大记录防超时 / 防中断"）。

- **同名 / 多候选二次确认（硬规则，退出码 2）**：
  - 私聊检索到多位同名同事，或群聊检索到多个同名/相近群（脚本只取首页、不做全量翻页）时，以退出码 `2` 打印候选 JSON（私聊：姓名/部门/邮箱/open_id；群聊：群名/chat_id/成员数，最多前 10 个）。必须把候选列给用户确认，私聊用 `--open-id <ou_...>`、群聊用 `--chat-id <oc_...>` 显式指定重跑，**禁止自行猜测**。群名太宽泛（如“反馈”命中几十个群）时，提示用户补全群名或直接给 chat_id。
- **不足 30 条拦截（硬规则，退出码 3）**：近 365 天消息总数 `< 30`（阈值可用 `--min-messages` 调整，默认 30）时礼貌拦截并停止，不产出海报。私聊话术：“聊天记录不足 30 条，暂时无法生成，很抱歉，可以换一位同学试试”；群聊话术：“该群近一年聊天记录不足 30 条，暂时无法生成，可以换一个更活跃的群试试”。原样转告用户。
- **大记录防超时 / 防中断（限时分片 + 按批续传 + 登录熔断，硬规则）**：
  - **单次前台调用最多 115 秒**（`--run-seconds`，默认 115，可调小）：约前 105 秒用于拉取，最后约 10 秒留给统计、落盘和收尾，到点必然返回。这样每次 Bash 调用都是短请求，不会再因为长调用被服务升级 / 容器迁移打断（1701）。
  - **必须按幂等方式多次调用（最重要的一条）**：脚本 stdout 的**最后一行是 JSON 结果**，只看 `status`：
    - `status="in_progress"`（`should_continue: true`）——**这是正常进度，不是错误**。已拉到的分页都已落盘。**用完全相同的参数、在相同工作目录，把同一条命令再跑一遍**，循环直到拿到 `completed`。一年的大群通常需要几轮。
    - `status="completed"`——数据齐全，`stats_path` / `raw_path` 可用，才进入第 2 步。对已完成的任务重复调用会直接返回 `completed`、不会重拉。
    - `status="failed"`（`should_continue: false`）——参数、权限或数据完整性问题（如 lark-cli 参数错、缺 scope、分页游标异常）。**不要盲目重跑**，按 `message` 改正后再跑。
    - `status="auth_expired"`（退出码 4）/ `status="segment_incomplete"`（退出码 5）——按下面两条对应处理。
  - **续跑依赖输出路径，不要中途改参数**：检查点写在 `<raw-output>.segments/`，并与聊天对象和 `--days` 等窗口参数绑定。**同一任务每轮必须用同样的 `--output` / `--raw-output` 和同样的对象参数**；换了参数或换了聊天对象却复用同一路径会被直接拒绝（`failed`），这是为了防止把别的聊天的缓存读进来。新任务请换新的输出路径。
  - **时间窗在第一次调用时冻结**：首轮把起止时间写进 `<raw-output>.segments/resume.json`，后续各轮沿用，所以"原参数重跑"不会让查询窗口随时间滑动、也不会漏掉边界消息。
  - 时间窗默认按 **20 天一段**（`--segment-days`），多段**并发拉取**（默认 `--fetch-workers 3`；上万条的超大群可提到 `4–6`，一旦限流再降回 2–3）；各 worker 启动错峰，避免多个 lark-cli 进程同一瞬间读取 / 刷新缓存 token。每段单次请求超时 240s（`--segment-timeout`）并带退避重试。
  - **按批原子落盘**：每次 lark-cli 调用翻 `--pages-per-call` 页（默认 12），这一批消息和它的下一页游标一起原子写入 `<raw-output>.segments/`。批次大小会按本分片剩余预算自动缩小，不会启动注定被截断的一批。因此分片到点或进程被杀最多丢当前未完成的那一批，已提交的批在下一轮直接复用、不重拉。检查点**会一直保留**（不再自动清理）。
    - 为什么是按批而不是逐页：一次 lark-cli 调用有约 2.1 秒固定开销（主要是 TLS 握手与认证初始化，进程启动只占 0.16 秒），逐页调用会为每页重付一次。实测同一个群全年拉取，逐页 92s、按批 60s、旧的整窗口 53s。
  - **同一输出路径不能并发跑两个**：脚本持有运行锁，重复启动会以 `failed` 拒绝，避免两个进程交叉写同一批检查点。
  - **认证 / token 报错先自愈、不轻易熔断**：多个并发进程刷新缓存 token 时可能偶发竞争，使某个时间段报 token 错、而手动单跑同一段却成功。遇到认证 / 令牌类报错先按 2s、4s 退避重试（新进程会重读 / 刷新 token），**任何一次成功都会把认证失败计数清零**；限流（429 / rate limit / 限流）按普通退避重试、不计入认证失败。
  - **登录态真过期才熔断（退出码 4，硬规则）**：lark-cli 的临时 user token 可能在超长任务中途过期，脚本无法非交互重新登录。只有**跨请求累计 6 次认证失败、退避后仍无法恢复**（已排除 429 / 限流）才判定登录真过期：停止派发新段、保留全部已完成批次，以退出码 `4` 打印 `status=auth_expired` 与中文提示。此时引导用户重新完成飞书 / lark-cli 登录授权，再原样重跑同一条命令即从断点续传，已拉数据不丢失。
  - **少数段失败不拖垮全局（退出码 5）**：若个别时间段在重试后仍失败（偶发 token 竞争、超时或限流），其余段照常跑完并落盘，最后以退出码 `5` 打印 `status=segment_incomplete` 与缺失的时间段；原样重跑同一条命令即只补这些段（反复卡在同一段时可降 `--fetch-workers 2` 或 `--segment-days 10`）。
  - 统计窗口起点对齐到首日 00:00（覆盖完整第一天，同一天内重跑结果可复现）。
- **表情表态 Reaction 随消息内嵌返回（默认零额外请求，消息再多也不丢）**：拉消息时列表接口已为每条有表态的消息附带 `reactions.counts`（每种 `reaction_type` 及人数，接口侧按 ≤20/批、最多 4 并发批量获取，单批失败静默跳过），分析器直接读取计数，**不再对全量消息逐条 `batch_query`**——彻底避免“消息太多→表态补抓成百上千次→整体超时被跳过”。仅当对**不含表态的旧 raw** 想补抓时才显式加 `--backfill-reactions`（走 `im reactions batch_query`，默认最多 2000 条消息、超出按时间均匀采样，`--reaction-cap` 可调）；`--skip-reactions` 会连内嵌表态一起跳过（最快，纯消息统计用）。
- 成功后产出 `*_stats.json`（8 类数据 + 关键词 + 表情 + 月/小时分布 + 风格标签 + 全年均匀文本样本）与 `*_raw.json`（原始消息，供取材与复算，勿重复拉取）。
  - 私聊 stats：`chat_type="1on1"`、`colleague_name`、`open_id`（ou_ 开头，第 4 步发送用）。
  - 群聊 stats：`chat_type="group"`、`group_name`、`chat_id`（oc_ 开头）、`member_count`（可能为空）、`top_senders`（发言最多的成员榜，供封号文案取材）。

**8 类数据字段 → 海报卡片**：`total_messages`(条消息)、`chat_days`(个聊天日)、`latest_night`(最深夜的一次对话)、`earliest_morning`(最早的一次对话)、`image_count`(张分享图片)、`doc_count`(篇分享文档)、`top_keywords[0]`(聊天关键词)、`top_emojis[0]`(最爱发的表情 / 全群最爱的表情)。某项确实为空时卡片显示“—”，**不得编造**。

- **群聊第 5 张卡替换（私聊不变）**：私聊第 5 卡是 `image_count`(张分享图片)；**群聊第 5 卡改为“群里说话最多的人”**，取 `top_senders[0][0]`（全年发言条数最多的成员名），长名/英文名随卡片数值字号自适应缩小、不换行不截断；群聊的 `image_count` 仍统计在 stats 里，但不上卡片。其余 7 张卡私聊/群聊一致（第 8 卡标签群聊为“全群最爱的表情”）。

- **表情口径（第 8 项，私聊/群聊完全一致）**：`top_emojis` 把两类表情**合并计数**——① 消息正文里的 `[表情]` 标签；② 大家**长按消息回复的表情表态（Reaction）**。同名归一（如 THUMBSUP 及各肤色点赞 DarkThumbsup 都算“点赞”、JIAYI=加一）。Reaction 统计双方/全员的所有表态、不分是谁点的；**默认直接取拉消息时内嵌的 `reactions.counts`（按人数加权，随分页并发返回、零额外请求，大群也完整）**，归一化后写入每条消息的 `_reaction_emojis` 并随 raw 落盘（原始 reactions 块含 operator id，统计完即丢弃，不进 raw）。只有旧 raw 缺表态且显式 `--backfill-reactions` 时才用 `im reactions batch_query` 兜底（默认上限 2000 条、超出均匀采样）。stats 另给 `top_reaction_emojis`（表态单独榜）、`reaction_total`（表态总数）、`text_emoji_total`（正文表情总数）；只想快速跑可加 `--skip-reactions`。

**时间口径（凌晨 5 点为日界，硬规则）**：
- “最深夜”覆盖当日傍晚 17:00 一直到次日凌晨 04:59，凌晨时段按顺延到 24 点后排序，跨零点的凌晨消息一定最晚；当天没有跨零点也回退取晚间（如 23 点多）最晚一条，**绝不允许为空**。
- “最早”取 05:00–11:59 中最早一条；若无则回退全天最早，也**不为空**。
- 完整时间戳另存 `latest_night_full` / `earliest_morning_full` 供文案取材。

**文档口径**：`doc_count = file 消息 + post 富文本分享卡片 + 文本内云文档链接(docs/docx/wiki/sheets/base/file)`；stats 内有 `file_count/post_count/doc_link_count` 明细，用户对口径敏感时在交付时说明。

**关键词与内容过滤（硬规则）**：分析器用 jieba 词性分词，只保留名词/动词/形容词/成语等真实实词，自动剔除：
- 语气词与口头填充（哈哈、唉、嗯、哦、就是、然后、感觉、可以、不行、不想、事儿 等，见脚本 STOPWORDS）；
- `@人名`、URL、`[表情]` 标签、英文、数字、单字、叠字（哈哈/哦哦）；
- 人名/地名/机构/其他专名（nr/ns/nt/nz 词性），防止无关人名进入关键词；
- 公司内部敏感词（脚本 `INTERNAL_SENSITIVE`）：绩效、工资、奖金、年终奖、薪资/薪酬、调薪/加薪、职级、晋升、述职、考评/考核/评级、期权/股票、离职/裁员/辞退等薪酬绩效与人事词，不进入关键词，也不得写进封号与祝福；
- 关键词必须是被分词确认的真实词汇，不接受正则碎片。

### 第 2 步：基于“全年整体内容”现写封号与祝福（禁止模板）

读取 stats 中的 `text_samples`（按月均匀抽样，覆盖全年而非近期）、`top_keywords`、`top_emojis`、`chat_style_tags`、月/小时分布与极值时间；群聊还要读 `top_senders`，必要时翻 `*_raw.json` 补细节。写入 `content.json`：

```json
{
  "medal_title": "4-10字、有趣有记忆点的年度封号",
  "medal_desc": ["3-5句、每句≤30字；封号卡用来承载数据与亮点"],
  "blessing": ["8-15行、每行≤25字的祝福，空行用 \"\" 分隔"]
}
```

**共同要求（私聊/群聊都适用）**：
- **严禁任何固定模板或随机选句**：必须基于该对象完整 365 天内容现写；换成任何人/任何群都应不同，同一对象重生成也应不同。
- **安全合规**：主动过滤违法违规、色情、暴力、政治敏感、脏话；**屏蔽公司内部敏感词——绩效、工资、奖金、年终奖、薪资/薪酬、调薪/加薪、职级、晋升、述职、考评/考核/评级、期权/股票、离职/裁员/辞退等一律不得出现在封号、祝福或关键词中**；不出现竞品贬损与其他内部敏感信息。渲染器的 SENSITIVE_WORDS 仅作兜底（图面不得出现 `***`），写作环节就要主动避开。
- **通顺校验（渲染前必做）**：逐句通读，确认①无半截句/成分残缺/病句；②无错别字、标点正确且统一（中文全角）；③断句自然、读起来顺口、情感连贯；④每行不超字数上限、空行用 `""`。渲染出图后再对照图片目视复核一遍，无乱码、无截断、无 `***`。

**私聊文案（两个人）**：
- 封号忌“最佳搭档/黄金组合”等通用词，要抓这个人独有的协作梗、高频话题、口头禅、深夜/共创/互怼细节。
- `medal_desc` 引用两人真实数据/关键词/表情/时间。
- `blessing` 要“矫情、有感情”，含三段：① 情谊感慨（共同经历/默契/陪伴）② 未来合作展望 ③ 中秋祝福；结尾不要与固定落款“—— 中秋快乐 ——”字面重复。

**群聊文案（一群人，本次重点）——封号卡与祝福语录分工明确：**

1. **封号卡（medal_title + medal_desc）= 讲数据、讲谁最活跃**
   - `medal_title`（4-10 字）：抓这群人的共同身份、年度状态或群梗，例如一群人总在深夜帮人排查问题，可叫“凌晨在线的字段救火队”；忌“最佳团队/相亲相爱一家人”这类通用词。
   - `medal_desc`（3-5 句、每句≤30 字）：**数据集中放在这里**。可引用消息数、热聊日、最深夜/最早、图片/文档数、关键词等真实统计；也可用轻松、正向、好玩的口吻点出 `top_senders` 里最活跃、最爱接梗、总在深夜答疑、最常发文档的 1–2 位成员，做成趣味“群内担当”（如“这一年，某某是群里最稳的秒回担当”）。
     - 约束：只做善意趣味表彰，**不做完整排名、不与绩效/工作量考核挂钩、不出现敏感词、不泄露 open_id/chat_id**；若成员名字不便公开、群氛围不适合点名，或数据不足，就改用群像泛指（“总有人第一时间接话，也总有人默默守着群”）。

2. **祝福语录（blessing）= 只讲主题与人，不堆数据，要更煽情、更具象**
   - **不要重复卡片和封号里已经出现过的任何数字/数据**（不写消息数、天数、文档数、几点几分）。数据在上面已经说过，这里要走心。
   - **必须落到具体的人和话，严禁泛泛抒情（硬要求）**：动笔前先回 `*_raw.json`（必要时翻每条消息的 Reaction 明细 `_reaction_emojis`、`top_reaction_emojis`）取材——
     ① **找高赞 / 被多人点 Reaction 的原话**：挑那句让群里人会心一笑或心头一暖的真实表达、口头禅、名场面，把它的大意或意象化用进祝福（化用而非逐字搬运，注意脱敏、避开敏感词与 @人名）；
     ② **找高频话题背后的具体场景与瞬间**：不要写“我们积极答疑”，而要写“某个字段怎么都带不出来的下午”“凌晨还在帮人复现的那条消息”“一句让人安心的‘我来看看’‘复现了’‘这么配就对了’”；
     ③ 用 `top_senders` 对应到**具体角色**：谁总在秒回、谁负责收尾、谁最爱甩表情包、谁默默把坑填平。
     宁可写两三处真实、具体、群成员一看就想起“对对对就是这样”的细节，也不要堆“并肩前行 / 共同成长 / 感恩相遇 / 携手并进”这类放之四海皆准的空话。不便点真名时，用“那个总在凌晨回消息的人”“每次先说‘收到’的人”这类**有画面感的指代**，但每个画面对应的人都应能在聊天记录里找到原型。
   - **主线一·这群人这一年主要在聊什么**：从 `top_keywords`、`text_samples` 与上面挖到的具体事件，提炼群的共同主题与一起在做的事（反馈答疑、字段救火、需求共创、项目推进、知识互助、跨团队协作等），写“这一年，我们一起在为什么事较真、为什么事热闹”，要用具体的事，不要只贴主题标签。
   - **主线二·谁喜欢说什么样的话（成员语言风格群像）**：写这群人各自的说话方式、口头禅、群梗与角色，尽量挂上真实细节（某句高频回复、某个高赞梗）；不适合点名就用“有人……有人……”的群像，但每个“有人”背后都应有聊天记录里的原型。
   - **升华成美好愿景**：这是一群人一整年的纪念，要比私聊更有“一群人并肩走过”的集体感与仪式感，由前面的具体细节自然推向感动，而不是空喊口号；写彼此托底、每个提问都有回响、每份较真都被看见、来年继续一起往前走的鼓励与期待。
   - **结尾面向群里所有人送中秋祝愿**（团圆、被看见、月长明、岁岁常相见之类），但**不要与固定落款“—— 中秋快乐 ——”字面重复**：落款已统一祝“中秋快乐”，正文末句换个说法（如“愿群里的每个人，月圆人团圆，岁岁常相见”）。

### 第 3 步：渲染海报

```bash
python3 scripts/poster_generator.py \
  --stats group_stats.json --content content.json \
  --user-name "<本人姓名>" \
  --output poster.png
```

- 渲染器为纯程序化 PIL 合成，确定性输出，不经过生图模型，保证数据/文字/二维码不乱码、不丢失。
- 底部二维码使用固定资产 `assets/qr_code.png`（扫码打开飞书文档 `https://bytedance.larkoffice.com/docx/MGxCdlE7kopkGGxGtj7cSUYAnwg?from=from_copylink`），渲染器自动贴入并统一成米色底深蓝码；**不要再用 `--qr-url` 动态生成**。需要更换二维码时直接替换该文件，渲染后解码确认链接一致。
- 群名头部只显示群名，长群名按字符长度整体缩字号（下限 30px，私聊姓名下限 48px），不换行、不截断、不压到右侧玉兔。

### 第 4 步：交付后追问（必做）

海报渲染、通过检查后，**先把海报图片展示给用户，紧接着调用交互提问工具 `interaction.ask` 追问下一步**。已实测：`interaction.ask` 会在客户端弹出带可点按按钮的弹框——这就是“按钮弹框”的标准、且唯一可靠的实现方式；**不要只用普通文本罗列选项来替代它**（纯文本不会被渲染成按钮）。

**`interaction.ask` 调用参数（一个 question + 三个 option；私聊 / 群聊只差动作①）：**

- `question_id`：`next_action`；`header`：`下一步`
- `display_message`（**始终在文字里写明 1 / 2 / 3 的含义，作为按钮偶发不渲染时的兜底**）：
  - **私聊**：`这张「中秋小笺」做好啦～接下来要我怎么做？可点按下方按钮，或直接回复数字：1）帮你发给 TA　2）重新生成一张　3）先不用了`
  - **群聊**：`这张「中秋小笺」做好啦～接下来要我怎么做？可点按下方按钮，或直接回复数字：1）发到群里　2）重新生成一张　3）先不用了`
- `display_option`（三个，`option_id` 固定为 `send / regenerate / skip`；label ≤40 字、description ≤200 字，把「对方姓名 / 完整群名」替换成 stats 里的真实名称）：
  - **私聊**：`send`→label `帮你发给 TA`、description `以你的身份，把海报发到你和「对方姓名」的飞书单聊`；`regenerate`→label `重新生成一张`、description `数据不变，封号和祝福全部重新现写一版`；`skip`→label `先不用了`、description `结束，不发送、不再生成`。
  - **群聊**：仅动作①不同——`send`→label `发到群里`、description `以你的身份，把海报发到「完整群名」`；`regenerate / skip` 与私聊相同。

**按钮与文字等价（硬规则）：**

- 工具返回 `option_id`（`send / regenerate / skip`）后，直接按下面的“输入解析”映射执行，**不再二次确认**。
- 即使用户不点按钮、直接用文字 / 数字回复（或当前通道没有弹出工具），也按 1 / 2 / 3 与同义语映射执行——**文字回复始终可用**。
- **按钮 + 文字兜底始终并存**：`display_option` 照常传（按钮能渲染就渲染），同时 `display_message` 里始终保留上面那行写明 1 / 2 / 3 含义的文字——这样按钮偶发不渲染时，用户照着文字回复数字即可，不会卡住。这行说明只在弹框 `display_message` 内出现一次，**弹框之外不要再用普通回复额外罗列选项**（避免出现两三行重复）。

- **输入解析（硬规则，点按与文字等价）**：用户点按按钮，或用文字 / 数字回复，都按同一映射执行，**不要对明确的 1 / 2 / 3 再二次确认**：
  - **动作①**：`1`、`发`、`发给TA/发给他/发给她/发给他俩`、`发到群里/发群里`、`发送`、`好，发吧`、`帮我发` 等明确发送意图。
  - **动作②**：`2`、`重新生成`、`重做`、`再来一张`、`换一张/换一个`、`重写一版`。
  - **动作③**：`3`、`先不用`、`不用了`、`算了`、`不发`、`没事了`、`就这样吧`。
  - 仅当用户回复含糊、与上面都对不上、或数字与文字自相矛盾时才追问一次；发送属高风险动作，若无法确定其指向的对象（收件人）就先确认，能确定（按钮/数字/明确姓名）则直接执行。

- **发到群里（点按即确认，不再二次确认）**：群消息虽是全员可见广播，但完整群名已显示在选项 ① 里，用户点选「发到群里」即视为已确认收件人与内容，**直接按下面的“发送动作”发到 `stats["chat_id"]`（oc_ 开头），不要再追加一轮“确认要发到这个群吗”的提问**。群名歧义在第 1 步拉数据前就已通过候选列表 / `--chat-id` 解决，发送时直接用已确认的 chat_id；仅当 stats 里缺少 chat_id、或与当前要发的群明显不符时才停下询问。用户没点发送就绝不主动发群。
- **私聊·发给 TA（点按即确认）**：选项 ① 已带对方姓名，用户点选即确认；内部直接用 `stats["open_id"]`（ou_），并核对它与 stats 里的同事姓名一致以防发错人（这一步是内部校验、不额外弹窗），一致就直接按“发送动作”发送，不一致才停下询问。

**发送动作（私聊 / 群聊完全一致：先发寄语，后发海报，顺序不可颠倒）**：用本人身份（lark-cli 一律加 `--as user`），发送前先读取 `lark-im` 技能。

1. **第一条先发一段富文本寄语（post），只有一行祝福**：以 🌕 开头、🐇 结尾，**不要附技能出处或任何文档链接**。
   - **“（由豆包工作发送）”尾注由飞书 / CLI 在发送时自动追加、无法关闭，正文里不要再手写，以免出现两次**：这一行祝福就是最后内容，尾注会自动补在 🐇 后面。
   - 私聊 `--content`：
     ```json
     {"zh_cn":{"content":[[{"tag":"text","text":"🌕 中秋快乐，赠你一张中秋小笺，记录我与你的碎碎念念，也祝愿我们的情谊岁岁年年。🐇"}]]}}
     ```
   - 群聊 `--content`（主语换成群体，其余一致）：
     ```json
     {"zh_cn":{"content":[[{"tag":"text","text":"🌕 中秋快乐，赠大家一张中秋小笺，记录我们这一年的碎碎念念，也愿群里的每个人岁岁年年常相见。🐇"}]]}}
     ```
   对方实际收到一行祝福（尾注自动出现在句末）：
   > 🌕 中秋快乐，赠你一张中秋小笺，记录我与你的碎碎念念，也祝愿我们的情谊岁岁年年。🐇（由豆包工作发送）
   ```bash
   # 私聊（接收人用 open_id）；群聊把 --user-id ou_xxx 换成 --chat-id oc_xxx
   lark-cli im +messages-send --as user --user-id ou_xxx --msg-type post --content '<上面对应的 JSON>'
   ```
2. **确认第一条返回 `message_id` 成功后，第二条再发海报图片**（两条独立消息，不可合并、不可颠倒）：
   ```bash
   lark-cli im +messages-send --as user --user-id ou_xxx --image ./poster.png
   ```
   `--image` 只接受 cwd 相对路径 / URL / 已上传的 `img_xxx`（绝对路径会被拒绝）：先 `cd` 到海报所在目录用 `./poster.png`，或先 `lark-cli im images create --data '{"image_type":"message"}' --file ./poster.png` 取 `image_key`，再 `--image img_xxx`。
3. 两条都成功后：私聊告知“已连同中秋寄语一起发送给 XXX”，群聊告知“已连同中秋寄语一起发送到「完整群名」”。第一条失败则停止，不要单独把图发出去。
- **重新生成一张（私聊/群聊都有）**：**不重新拉数据**（复用已有 stats/raw，8 类数据不变），回到第 2 步重新现写一套全新封号与祝福——严禁复用上一版、严禁模板或随机选句；重新过敏感词与通顺校验后渲染，交付后再次进入与本会话类型对应的追问（群聊仍是“发到群里 / 重新生成 / 先不用了”三个选项，点“发到群里”直接发送、不再二次确认）。
- **先不用了 / 无回应**：结束，不发送、不再生成。

## 自适应与排版规则（硬规则）

- **宽度固定 1080**；总高度在 2400–4200 间随内容（封号描述行数、祝福行数）自动增减，保证内容完整且**永远保留上下边距**。

## 特殊报错应对

- 假设任意的 tool 调用或脚本调用发现了 error_code=1701 的错误码，说明当前容器可能刚迁移，重试命令即可
- 第 1 步的 `chat_analyzer.py` 本身已做限时分片（单次 ≤115 秒）与按批断点，**原参数重跑总是安全且幂等的**：已落盘的批次不会重拉。所以对它遇到的 1701、超时或 `status="in_progress"`，一律"用同样的参数再跑一遍"，直到 `status="completed"`；只有 `status="failed"` 才需要先改参数。
