# 结构化调试

遇到问题时——先理解本质，再动手修复。禁止在未定位根因前大面积改代码。

## 使用方式

在Codex中输入 `/fix {错误描述或截图}` 或引用此Skill后描述遇到的问题。

可以配合Appshot功能：按两次Command键截取错误页面/终端输出，直接注入调试上下文。

## 执行流程

### 第一步：复现（必须！）

```
在尝试修复之前，先复现问题：
- 用相同的输入/步骤触发同样的错误
- 记录完整的错误信息、堆栈、触发条件
- 确认：这是一个稳定的bug还是偶发性的？
- 偶发性 → 记录触发频率和条件，不要凭一次现象下结论
```

### 第二步：列出假设（3个，按概率排序）

不要只有一种解释。强制列出至少3个可能原因：

```
假设1（最可能，概率约X%）：
  [原因描述]
  验证方法：[如何快速验证这个假设是否正确]
  
假设2（次可能，概率约X%）：
  [原因描述]
  验证方法：[如何快速验证]

假设3（黑天鹅，概率约X%）：
  [原因描述]
  验证方法：[如何快速验证]
```

### 第三步：逐一验证，从最可能的开始

每验证一个假设，记录结论：
- ✅ 确认 → 进入第四步
- ❌ 排除 → 验证下一个假设
- ⚠️ 部分相关 → 纳入修复范围，但继续验证其他假设

**如果三个假设都被排除**：说明对问题的理解有误。回到第一步，重新复现，扩大搜索范围（可能是依赖库的bug、环境差异、并发竞态等）。

### 第四步：最小修复

```
修复原则：
1. 改动越小越好——能改一行不改一个函数，能改一个函数不改一个文件
2. 修复代码本身要有注释解释"为什么这样修"
3. 不要顺手重构——修复和重构是两次独立的提交
4. 如果修复引入了新的复杂度（如额外的状态管理、新的依赖），需要评估是否值得
```

### 第五步：补一个防止回归的测试

```
修复完成后，必须补充一个测试：
- 如果bug在单元层面：补单元测试
- 如果bug在API层面：补集成测试或用.http文件添加回归用例
- 如果bug在Agent行为层面：补一条评估用例到 evals/golden/
- 如果bug是安全问题：补一条到 evals/red-team/

测试要能复现原始bug（确保修复前测试会失败，修复后通过）
```

### 第六步：输出修复报告

```markdown
## 修复报告：{问题简述}

**根因**：[用一句话说清楚问题的本质]
**为什么之前没发现**：[测试盲区？边界条件？依赖变更？并发？]
**修复方案**：[改了什么，为什么这样改]
**影响范围**：[只影响XX功能 | 涉及YY和ZZ模块]
**回归测试**：[新增了哪个测试来防止复发]
**教训**：[如果有时光机，在开发时做什么可以避免这个问题？]
```

## 关键原则（违反任何一条都算调试失败）

1. **先复现，再修复** — 不复现就修 = 闭着眼睛扔飞镖
2. **先假设，再验证** — "我先改改看能不能好"是调试的反模式
3. **最小改动** — 修复的规模应该和问题的复杂度成正比
4. **补回归测试** — 没有回归测试的修复是债，以后还会还
5. **记录根因和教训** — 5分钟后你就会忘记刚才学到了什么
