# Ask Matt

你记不住每个技能，所以开口问。

**流程（flow）**是一条穿过各技能的路径。大多数路径沿一条**主流程**行进，另有两个**入口匝道（on-ramp）**汇入其中。其余的一切要么是独立技能，要么是运行在底层的词汇层。

## 主流程：想法 → 交付

大多数工作所走的路线。你有一个想法，想把它做出来。

1. **`/grill-with-docs`** 通过访谈把想法打磨清晰。只要你**正在一个工作目录中工作**，就从这里开始：它是有状态的，把学到的东西保存在 `CONTEXT.md` 和架构决策记录（ADR）中。（没有工作目录？改用 `/grill-me`，见「独立技能」一节。两者运行的是同一个 `/grilling` 原语；`grill-with-docs` 是会留下书面痕迹的那个，因此只要有仓库可留，它就是两者中更好的选择。）
2. **分支：所有问题都能在对话中解决吗？**如果某个问题需要一个可运行的答案（状态、业务逻辑、一个必须亲眼看看的 UI），就绕道做一个原型，往返都用 **`/handoff`** 作桥梁（原型住在自己的目录里，这正是 `/handoff` 的用途；见「阶段边界」）：
   - **`/handoff`** 出去，然后针对那个文件开一个新会话，
   - **`/prototype`** 用一次性代码回答该问题，
   - **`/handoff`** 把学到的东西带回来，并在最初的想法线索中引用它。
3. **分支：这是一个多会话的构建吗？**
   - **是** → 先 **`/to-spec`**（把线索变成一份规格说明），再 **`/to-tickets`** 把它拆成示踪弹（tracer-bullet）工单，每张工单声明自己的**阻塞边**。在本地跟踪器上，就是 `.scratch/<feature>/issues/` 下每张工单一个文件，按「阻塞方优先」手工推进；在真实跟踪器上，这些边变成原生的阻塞链接，于是任何阻塞项已完成的工单都可以被领取：按工单启动 **`/implement`**，每张之间 **`/clear`** 清掉上下文。每张工单都自包含，所以上一张的上下文可以丢弃。
   - **否** → 就在这里、同一个上下文窗口中 **`/implement`**。

   无论哪种方式，**`/implement`** 都是靠内部驱动 **`/tdd`**（一次一个红-绿切片）来构建每个议题，然后在提交前运行 **`/code-review`** 收尾——对 diff 做双轴评审（Standards 标准 + Spec 规格）。当你只想在没有完整规格的情况下先测试再构建一个具体行为时，单独使用 **`/tdd`**；当你随时想对照一个固定基准评审某个分支或 PR 时，单独使用 **`/code-review`**。

### 上下文卫生

把步骤 1–3 保持在**一个不间断的上下文窗口**里（在 `/to-tickets` 之前不要压缩或清空），这样盘问、规格说明和工单都建立在同一套思考之上。然后每次 `/implement` 都全新开始，从工单出发。

这上面的限制是**[智能区（smart zone）](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能敏锐推理的窗口（在最先进模型上约为 150k token）。如果会话在 `/to-tickets` 之前就逼近它，不要在降级的推理质量上硬撑；在最近的阶段边界 `/compact`，然后继续（见「阶段边界」）。

## 入口匝道

一种产生工作、然后汇入主流程的起始情境。

- **缺陷和请求堆积起来** → **`/triage`**。它让议题走完分类角色流程，产出代理就绪（agent-ready）的议题，供之后的 **`/implement`** 领取。

  分类只针对**不是你创建**的议题：缺陷报告、外部进来的功能请求、任何原始到来的东西。`/to-tickets` 产出的工单已经是代理就绪的，所以**不要对它们分类**。

- **有东西坏了** → **`/diagnosing-bugs`**。用于难啃的那些：第一眼看不出端倪的缺陷、间歇性的偶发故障、在两个已知良好的状态之间悄悄溜进来的回归。在拥有一个**紧凑的反馈回路**（一条在*这个*缺陷上已经能变红的命令）之前，它拒绝凭空猜测，然后用回归测试修复。当真正的结论是「没有合适的接缝来锁定这个缺陷」时，它的复盘会把工作交接给 **`/improve-codebase-architecture`**。

- **一个庞大而模糊的任务：全新项目或巨型功能构建，大到一个会话装不下** → **`/wayfinder`**，这里认知负担最重的流程。当从这里到目的地的路还看不见时，它在议题跟踪器上绘制一张由**决策工单**构成的**共享地图**，一张一张地解决它们，产出**决策，而非交付物**，直到迷雾被推开、路线清晰。**`/grill-with-docs`** 打磨的是你一个会话就能装下的想法，wayfinder 则是给那个你装不下的想法准备的，它更慢、更密，所以只为这种场景保留它，绝不要用在一个范围清晰的功能上。

  地图清晰之后，**它只交接、不构建**：在 **`/to-spec`** 处汇入主流程，把地图上相互链接的决策坍缩成一份可构建的计划，然后照常走 `/to-tickets` 和 `/implement`。把地图直接连到 `/implement` 会跳过这次坍缩，把链接起来的细节都扔掉，所以只有当任务最终证明确实很小的时候，才直接进 `/implement`。

## 代码库健康

不是功能开发，只是日常养护。

- **`/improve-codebase-architecture`** 在你有点空闲的时候就跑一跑，让代码库保持适合代理运作的良好状态。它浮现出**深化机会（deepening opportunities）**；挑一个就*产生了一个想法*，可以带到 `/grill-with-docs` 进入主流程。它是找出候选者的勘察；**`/codebase-design`**（见下文）则是你设计选中的那个候选者的工作台。

## 底层的词汇

两个由模型调用的参考技能，运行在其他技能*之下*，各自是其词汇的唯一事实来源。当问题出在**用词**而不是流程上时，直接使用它们；或者让上面的技能把它们拉进来。

- **`/domain-modeling`**：打磨项目的*领域*语言：质疑一个模糊的术语，解决一个超载的词（「account」一词干了三份活），把一项难以逆转的决策记录为 ADR。它是 `/grill-with-docs` 所驱动的那门积极纪律，让 `CONTEXT.md` 保持为一本干净的术语表。
- **`/codebase-design`** 是深层模块的词汇（module 模块、interface 接口、depth 深度、seam 接缝、adapter 适配器、leverage 杠杆、locality 局部性），用于设计模块的*形态*：在一个干净的接缝后面，用一个小接口装下大量行为。`/tdd` 和 `/improve-codebase-architecture` 都使用这套语言。

## 阶段边界

**阶段（phase）**是会话内的一块工作：盘问、实现、QA。在两者之间的**边界**处，你有五个选项，而从中做选择是整张地图里最模糊的决策：

- **Continue 继续**：原地不动。不花成本，也不损失什么。
- **`/clear`**：清空窗口，当这里的内容对下一步无关紧要时。
- **`/handoff`** 写出一份可移植的 Markdown 文件。用途很窄：只用于**新 harness**、**新目录**、**同事**，或在**阶段中途**分叉一个支线任务。它换来的是可移植性。
- **子代理（Subagent）**：把一个范围紧凑的任务送进它自己的窗口，然后拿回一份报告。
- **`/compact`** 压缩这段上下文，并用它给一个全新会话播种。它是**默认选项**——位于决策树的底部，而不是最先伸手去够的那个。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 了解那棵有序的决策树：五个问题、每个分支背后的理由，以及为什么「一手来源成本」让**继续**成为第一个该被排除的选项。决策要**在**边界处做；阶段中途就继续，或者把剩余部分拆给子代理。

## 独立技能

完全不在主流程上。

- **`/grill-me`**：和 `/grill-with-docs` 一样毫不留情的访谈，但**无状态**：不在本地保存任何东西，也不构建 `CONTEXT.md`。当你**不在工作目录中工作**时使用它（打磨一份计划、一个设计、一篇文字，任何底下没有仓库的东西）。如果你在工作目录中，就改用 `/grill-with-docs`：它跑的是同一场访谈，还留下书面痕迹，所以严格来说它是更好的那个。
- **`/grilling`** 是访谈原语本身：轮次、前沿，事实是代理的活，决策是你的。`/grill-me` 和 `/grill-with-docs` 是两条有名字的入口，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。只有当你想要一场不带任何包装的访谈时，才直接使用它。
- **`/resolving-merge-conflicts`** 逐块（hunk）处理进行中的合并或变基冲突，通过追溯到每一侧一手来源的**意图**来解决，而不是挑行，然后完成整个操作。它从不运行 `--abort`。它独立于所有流程：当你已经身处冲突之中时使用它。
- **`/prototype`** 是一个小型的、一次性的程序，回答一个设计问题：这个状态模型感觉对不对，或者这个 UI 应该长什么样。一次性是对代码**写法**的约束，而不是承诺要销毁它：答案折进真实代码里，原型本身则作为**一手来源**保存在主干之外的 `prototype/<name>` 分支上，并从实现议题指向它。它是主流程第 2 步的绕道，但任何设计问题难以在纸面上敲定的时候，都可以用它。
- **`/research`**：把阅读跑腿的活交给一个**后台代理**：它对照**一手来源**调查一个问题，然后在仓库里留下一份带引用的 Markdown 文件。它读书的时候你继续干活。它产出的文件是要*带进*主流程、在 `/grill-with-docs` 处使用的东西，因为研究是喂养思考，而不是取代思考。
- **`/to-questionnaire`** 登场于卡住你的东西既不在你脑子里、也不在代码库里，而在**别人脑子里**的时候，它给对方写一份问卷去填。它是 `/grill-me` 的反面：不是就主题采访你，而是就**发送**采访你（发给谁、你需要拿回什么），并把问题对准那个缺口。收回来的是 `/grill-with-docs` 或 `/to-spec` 的素材。
- **`/wizard`** 用于只有**人类**才能完成的步骤：开通基础设施、设置凭据或 CI 密钥、点过一个陌生的第三方后台、执行一次性的迁移或切换。它生成一个交互式 bash 脚本，打开每个 URL、捕获每个值，并写入 `.env` 和 GitHub secrets，于是这个流程不再是你每次都要向代理重新解释一遍的东西。它由模型调用，所以代理一撞上只有你才能翻过的墙，就会伸手用它。如果代理自己就能干，它就该自己干；这是给人类真正在回路中的场景用的。
- **`/wait-what`** 是「一条消息没落地」的纠偏手段。在对话中途、任何其他技能内部都能用，代理会用你缺失的上下文、用 `CONTEXT.md` 的词汇、用大白话，把刚才说过的话重新说一遍。它是事后补救；`/grill-with-docs` 是事前预防，因为尽早约定好的共同语言，才能让术语从源头就不出现。
- **`/teach`**：跨多个会话学习一个概念，把当前目录当作有状态的工作区。
- **`/writing-for-agents`** 是撰写供代理阅读的文档时的参考：技能、AGENTS.md、被指向的文档。
