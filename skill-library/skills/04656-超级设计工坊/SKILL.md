# 超级设计工坊 —— Onboarding

首次使用引导。了解你的设计团队实际怎么做事，把配置写好让所有 skill 按你的标准来。

## 触发与状态判断

执行前先读 `~/.qoderwork/plugins/config/super-design-studio/QODERWORK.md`：

- **不存在** → 进入完整 onboarding。
- **顶部含 `<!-- SETUP PAUSED AT: {section} -->`** → 打招呼："欢迎回来，上次停在 {section}，要继续还是从头开始？"
- **含 `[PLACEHOLDER]` 但无 pause 注释** → 模板没填完，问用户从空白处继续还是重头来。
- **完全填好** → 默认不再 onboarding。除非传 `--redo`、`--check-integrations`，否则告知用户已配置好。

## 三档模式

### `--quick` —— 2 分钟极简

只问 3 个核心问题：
1. 你的角色和频道/产品线
2. 业务设定（电商类型）
3. 最在乎的一件事（一票否决项）

其它字段写 `[DEFAULT]` 默认值。最后告诉用户：
> "默认配置已生效，可以直接开始用。当某个 skill 输出感觉不对，就是默认值需要调——它会告诉你调哪一项。
>  随时可以 `/super-design-studio:onboarding --full` 跑完整版，或 `/super-design-studio:onboarding --redo <段名>` 重做某段。"

### `--full` —— 完整版（默认）

按下面的「访谈剧本」走完所有段。10-15 分钟。

### `--redo <段名>`

只重做指定段（例：`--redo 设计评审标准`）。其它段不动。

可选段名：团队、谁在使用、已连接的工具、设计评审标准、命名规范、输出目录偏好、业务规则、升级链、输出风格、共同护栏、偏好设置

### `--check-integrations`

只重测 `## 已连接的工具` 段。逐个调一次 MCP 工具，调通才标 ✓，仅 `.mcp.json` 里有但没测过的标 ⚪。

## 访谈剧本

### 0. 开场（一段话，不超过 4 行）

> "我会做你的电商频道设计助手。在干活之前，我想了解你团队**实际**怎么做设计——不是行业最佳实践，是你的真实流程、评审标准、设计规范。
>  大概十分钟。问几个问题，然后让你给我看几份你最近做过的真实设计稿。"

按需补充三档说明（**写明时间和差别**），让用户挑：
> "**两分钟**版只问角色 + 频道定位，其它用默认值，输出感觉不对再来调。
>  **十五分钟**版问完整评审标准、设计规范、风格偏好、协作流程，再看几份真实设计稿校准。
>  随时升级。"

等用户挑完再继续。

### 1. 共享 profile 检查

读 `~/.qoderwork/plugins/config/team-profile.md`：
- **存在** → 一句话确认："你是 [name]，[公司]，[行业]，[规模]。对吗？错了说 'update'。" 不再问公司类问题。
- **不存在** → 提醒用户："你是这台机器上第一次用这个插件，先存一份共享 profile，下次别的插件就不用再问了。" 然后问：
  - 公司/团队名
  - 行业（电商/互联网/品牌/综合）
  - 规模（初创/中型/大型）
  - 所在地

写到 `team-profile.md`。

### 2. 谁在用 + 工具检测（Part 0）

**角色选择题：**
- UX 设计负责人（管团队、定标准、审方案）
- 体验设计师（独立产出、从策略到交付）
- 视觉设计师（偏视觉执行、高保真产出）
- 混合（身兼多职）

**工具检测：**
逐个检测本插件依赖的 MCP 工具：
1. **浏览器自动化** — 调一次测试页面截取，成功标 ✓，失败标 ✗ 并说明 fallback
2. **钉钉文档** — 调一次文档列表读取，成功标 ✓，失败标 ✗ 并说明 fallback
3. **AI 生图** — 调一次测试图片生成，成功标 ✓，失败标 ✗ 并说明 fallback

向用户报告检测结果，写入 `## 已连接的工具` 段。

### 3. 设计评审标准（Part 1）

> "你们评审设计方案的时候，主要看哪几个维度？比如信息层级、价格突出度、视觉一致性、交互体验……每个大概占多少权重？"

追问：
- "有没有扣分规则？比如什么问题扣几分？"
- "有没有一票否决项——一旦出现不管其他多好都要打回？"

将答案写入 `## 设计评审标准` 段。

### 4. 业务规则和设计流程（Part 2）

**先问有没有现成材料：**
> "有没有团队的设计规范文档、设计系统说明、风格指南？有的话直接发我，我读完只问没覆盖的部分。"

有 → 读完后只问空缺。
没有 → 逐维度问：
- 设计流程（从需求到上线分几步）
- 设计规范引用（Figma/本地 token/文档链接）
- 红线（绝不能做的事）
- 灰色地带（出现时要找谁确认）

将答案写入 `## 业务规则` 段。

### 5. 命名与输出偏好（Part 3）

快速选择题：
- 文件命名：kebab-case / camelCase / 中文+日期
- 项目目录命名：{频道}-{场景}-{日期} / {case-id} / 自定义
- 设计稿版本：v1.0 递增 / 日期版本 / 其他
- 产出存放位置：本地目录路径 + 是否同步钉钉文档

将答案写入 `## 命名规范` 和 `## 输出目录偏好` 段。

### 6. 升级链（Part 4）

> "设计方案定稿谁拍板？什么情况下需要找上级或跨团队确认？"

判断：
- 单兵作战 → 把"升级"重定义为"什么时候找产品/业务方二次确认"
- 有层级 → 问完整审批链 + 触发条件

将答案写入 `## 升级链` 段。

### 7. 真实材料（Part 5）

> "最后一步，最关键的。把你最近做过的 5-10 份真实设计稿发我——页面截图、HTML 原型、评审记录都行。
>  量越多越好，20 份能看出明确模式。少于 5 份也行，但我会在配置里标 [LIMITED DATA]。"

读完后**对比用户说的标准 和 实际设计稿里的做法**——deltas 才是真正的设计规范。

将发现写入 `## 已配置的种子资料` 段。

### 8. 输出风格（Part 6）

> "交付给开发的文档用什么格式？高保真 HTML 还是标注图？内部沟通语气是直白还是正式？"

将答案写入 `## 输出风格` 段。

### 访谈节奏

- **能复用就复用**：每问一个超过一句话能答的问题，先问"有没有现成文档/链接"。
- **2-3 个/轮**：每轮最多 2-3 个可独立回答的问题。
- **明确等待**：需要打字的问题说"这个我等你打字"，不要催。
- **断点保存**：用户说 "pause/暂停/晚点继续" → 立刻把当前已填部分写进 QODERWORK.md，顶部加 `<!-- SETUP PAUSED AT: {section} -->`，未答字段标 `[PENDING]`。
- **写之前回顾**：写 QODERWORK.md 前，列出哪些字段还空着，问用户"现在填还是留空？"

### 写完之后

1. **展示摘要**（不是全文）："这是我听到的，看看哪里我搞错了。"
2. **告诉路径**："你的配置在 `~/.qoderwork/plugins/config/super-design-studio/QODERWORK.md`，纯文本，随时手动改。"
3. **演示一次**：根据用户说的痛点，挑一个最相关的 skill 当场跑一次。推荐优先级：
   - 如果用户痛点是"设计质量不稳定" → 跑 `/super-design-studio:ux-expert review`
   - 如果用户痛点是"出方案慢" → 跑 `/super-design-studio:ux-expert generate`
   - 如果用户痛点是"不了解竞品" → 跑 `/super-design-studio:compete`
4. **结尾说明可演进**：
   > "配置不是一次性的。skill 用着觉得不对就回来调；某个判断你反复改同一种方向，下次我会问要不要把它写进 QODERWORK.md。"

## 失败模式（不要犯）

- **不要写 schema/YAML** — QODERWORK.md 是散文 + 表格，给人改的。
- **不要跳过真实材料** — 访谈说的是"理想标准"，设计稿里看到的才是"真实做法"。两者经常不一样。
- **不要写空泛的回答** — "按行业标准"不算答案，追问："你们评审时具体看哪几个维度？哪个权重最高？"
- **不要在每次会话都跑 onboarding** — 先读 QODERWORK.md，已填完就直接干活。
- **不要把当前会话的上下文偷偷塞进 profile** — 只用用户在 onboarding 里明确打的字 + 明确分享的文档。
- **不要假设设计工具** — 用户可能用 Figma 也可能用 Sketch 或即时设计，不要默认某一种。
