# 编写有效的 README

## 概述

README 回答的是读者会提出的问题。不同的读者需要不同的信息——开源项目的贡献者需要的上下文，和未来的你打开配置文件夹时需要的上下文并不一样。

**始终要问：**谁会读它，他们需要知道什么？

## 流程

### 第 1 步：确认任务类型

**问：**「你正在做哪一类 README 任务？」

| 任务 | 适用时机 |
|------|------|
| **创建** | 新项目，还没有 README |
| **新增** | 需要记录新的内容 |
| **更新** | 能力变了，内容已经过时 |
| **复查** | 检查 README 是否仍然准确 |

### 第 2 步：按任务类型提问

**创建首版 README：**
1. 项目属于哪一类？（见下方「项目类型」）
2. 用一句话说清它解决什么问题？
3. 通往「它能跑起来」的最短路径是什么？
4. 有没有值得单独点出来的亮点？

**新增一节：**
1. 需要记录的是什么？
2. 它应该放在现有结构的哪个位置？
3. 谁最需要这些信息？

**更新已有内容：**
1. 变了什么？
2. 读现有 README，找出已经过时的章节
3. 给出具体的修改建议

**复查与刷新：**
1. 读现有 README
2. 对照项目实际状态核验（package.json、主要文件等）
3. 标出过时的章节
4. 如果 README 里有「最后复查」日期，更新它

### 第 3 步：始终追问一句

起草完成后问一句：**「还有没有你想强调、但我可能漏掉的内容？」**

## 项目类型

| 类型 | 读者 | 关键章节 | 模板 |
|------|----------|--------------|----------|
| **开源** | 世界各地的贡献者与用户 | 安装、用法、贡献指南、许可证 | `templates/oss.md` |
| **个人** | 未来的你、作品集访客 | 它做什么、技术栈、学到的东西 | `templates/personal.md` |
| **内部** | 同事、新入职的人 | 环境搭建、架构、运维手册 | `templates/internal.md` |
| **配置** | 未来的你（一脸困惑时） | 这里有什么、为什么这么放、怎么扩展、有哪些坑 | `templates/xdg-config.md` |

**不确定就问用户**。不要默认所有项目都按开源那一套写。

## 必备章节（所有类型通用）

每个 README 至少需要：

1. **名称** —— 一眼能懂的标题
2. **描述** —— 用 1–2 句话说清做什么、为什么做
3. **用法** —— 怎么用它（配上示例更好）
