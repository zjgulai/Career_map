# 诊断 Bug

针对疑难 bug 的一套纪律。只有在明确说明理由时才能跳过阶段。

探索代码库时，请阅读 `CONTEXT.md`（如果存在），以获得相关模块清晰的心智模型，并检查你所触及区域的 ADR。

## 脱敏

本技能会让你展示命令、输出和捕获的产物。**先对每个秘密脱敏**：在原处写上 `<REDACTED>`。让循环针对环境变量构建，这样凭据留在环境中，而不是出现在你展示的内容里。捕获的产物带有鉴权头：只引用携带信号的那些行。

如果脱敏后的输出不足以诊断 bug，请明确说出来并向用户求助。

## 阶段 1：构建反馈循环

**这就是本技能的精髓。**其余一切都是机械操作。如果你拥有针对该 bug 的**紧凑**通过/失败信号（一个会在这个 bug 上变红的信号），你就能找到原因；二分定位、假设检验和埋点都只是消费这个信号。如果没有这样的信号，盯着代码看多久都救不了你。

在这里投入不成比例的努力。**要激进。要有创造力。拒绝放弃。**

### 构建方法，大致按以下顺序

1. **失败的测试**：在能触达 bug 的任何接缝（seam）上写：单元、集成、e2e。
2. **Curl / HTTP 脚本**：针对运行中的开发服务器。
3. **CLI 调用**：使用固定样本输入，将 stdout 与已知正确的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）：驱动 UI 并对 DOM/console/network 做断言。
5. **回放捕获的追踪记录。**把真实的网络请求 / 载荷 / 事件日志保存到磁盘；在隔离环境中沿代码路径重放它。
6. **一次性测试装置（harness）。**拉起系统的最小子集（一个服务、mock 掉的依赖），用一次函数调用即可驱动 bug 代码路径。
7. **属性 / 模糊测试循环。**如果 bug 是「有时输出错误」，运行 1000 个随机输入并寻找失败模式。
8. **二分定位装置。**如果 bug 出现在两个已知状态之间（提交、数据集、版本），把「在状态 X 启动、检查、重复」自动化，这样就能 `git bisect run`。
9. **差异循环。**让相同输入分别经过旧版本与新版本（或两种配置）运行，然后 diff 输出。
10. **人在环（HITL）bash 脚本。**最后的手段。如果必须由人来点击，用 `scripts/hitl-loop.template.sh` 驱动_他们_，使循环依然有结构。捕获的输出会反馈给你。

构建出正确的反馈循环，bug 就解决了 90%。

### 收紧循环

把循环当作产品对待。一旦你有了_一个_循环，就**收紧**它：

- 能更快吗？（缓存设置、跳过无关初始化、缩小测试范围。）
- 能让信号更锐利吗？（断言具体的症状，而不是「没有崩溃」。）
- 能让它更确定吗？（固定时间、给 RNG 播种、隔离文件系统、冻结网络。）

一个 30 秒的不稳定循环几乎不比没有循环强；一个 2 秒的确定性循环才是紧凑的，是调试的超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。把触发器循环 100 次、并行化、施加压力、收窄时间窗口、注入 sleep。复现率 50% 的 bug 是可以调试的；1% 的不能，所以持续提高复现率，直到可调试为止。

### 当你确实无法构建循环时

停下来并明确说明。列出你尝试过的方法。向用户索要：(a) 能复现它的环境的访问权限，(b) 一份脱敏的捕获产物（HAR 文件、日志转储、核心转储、带时间戳的录屏），或 (c) 添加临时生产环境埋点的许可。**不要**在没有循环的情况下进入假设阶段。

### 完成标准：一个会变红的紧凑循环

当循环达到**紧凑**且**具备变红能力**时，阶段 1 完成：你能说出**一条命令**（一个脚本路径、一次测试调用、一条 curl），并且你**已经至少运行过一次**（展示调用方式及其输出，脱敏后），且它满足：

- [ ] **具备变红能力**：它驱动真实的 bug 代码路径，并断言**用户的确切症状**，因此它能在这个 bug 上变红，修复后变绿。不是「运行不出错」；它必须能_抓住这个具体的 bug_。
- [ ] **确定性**：每次运行结论相同（不稳定的 bug：如上所述，固定且高复现率）。
- [ ] **快速**：以秒计，而不是分钟。
- [ ] **代理可运行（Agent-runnable）**：你可以无人值守地运行它；人只在通过 `scripts/hitl-loop.template.sh` 时才介入循环。

如果你发现自己在读代码构建理论时这条命令还不存在，**立即停止：直接跳到假设正是本技能要防止的失败。**没有具备变红能力的命令，就没有阶段 2。

## 阶段 2：复现 + 最小化

运行循环。看着它在 bug 出现时变红。

确认：

- [ ] 循环产生的是**用户**所描述的失败模式，而不是碰巧在附近出现的另一个失败。错误的 bug = 错误的修复。
- [ ] 失败在多次运行中都可复现（或者，对于非确定性 bug，复现率高到足以据此调试）。
- [ ] 你已捕获确切的症状（错误信息、错误输出、缓慢的耗时），使后续阶段能够验证修复确实解决了它。

### 最小化

一旦变红，就把复现缩小到**仍然变红的最小场景**。**一次一个**地削减输入、调用方、配置、数据和步骤，每次削减后重新运行循环，只保留对失败起支撑作用的部分。

为什么值得这样做：最小复现缩小了阶段 3 的假设空间（剩下可怀疑的活动部件更少），并成为阶段 5 中干净的回归测试。

当**每个剩余元素都起支撑作用**时完成：移除其中任何一个都会让循环变绿。

在完成复现**且**最小化之前，不要继续。

## 阶段 3：提出假设

在测试任何假设之前，生成 **3–5 个排序后的假设**。只生成一个假设会锚定在第一个貌似合理的想法上。

每个假设必须**可证伪**：陈述它作出的预测。

> 格式：「如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更严重。」

如果你无法陈述预测，这个假设只是一种感觉：丢弃它或打磨它。

**在测试之前把排序列表展示给用户。**他们往往拥有能立刻重排的领域知识（「我们刚部署了一个变更到 #3」），或者知道哪些假设已经被排除。廉价的检查点，巨大的时间节省。不要因此阻塞；如果用户不在，就按你的排序继续。

## 阶段 4：埋点

每次探测都必须对应阶段 3 中的某个具体预测。**一次只改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查**，如果环境支持的话。一个断点胜过十条日志。
2. **定向日志**：打在能区分假设的边界上。
3. 绝不「到处打日志然后 grep」。

**给每条调试日志打上唯一前缀标签**，例如 `[DEBUG-a4f2]`。最后的清理就变成一次 grep。没有标签的日志会留下来；带标签的日志会被清除。

**性能分支。**对于性能回归，日志通常是错误的工具。取而代之：建立基线测量（计时装置、`performance.now()`、性能分析器、查询计划），然后二分。先测量，后修复。

## 阶段 5：修复 + 回归测试

在**修复之前**写回归测试，但只有在存在**正确的接缝（seam）**时才这样做。

正确的接缝是指测试能够在调用点复现**真实的 bug 模式**的接缝。如果唯一可用的接缝太浅（bug 需要多个调用方时只有单调用方测试、无法复现触发 bug 的调用链的单元测试），在那里写回归测试只会带来虚假的信心。

**如果不存在正确的接缝，这本身就是发现。**记下它。代码库架构正在阻止这个 bug 被锁定。在下一阶段标记这一点。

如果存在正确的接缝：

1. 把最小化后的复现变成该接缝上的失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 对原始（未最小化）场景重新运行阶段 1 的反馈循环。

## 阶段 6：清理

宣布完成前必须做到：

- [ ] 原始复现不再复现（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或已记录接缝缺失这一事实）
- [ ] 所有 `[DEBUG-...]` 埋点已移除（用 `grep` 搜索前缀）
- [ ] 一次性原型已删除（或移到清晰标记的调试位置）
- [ ] 在 commit / PR 信息中写明最终被证实正确的假设，让下一位调试者得以学习
