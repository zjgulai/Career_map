# 分诊（Triage）

将项目 issue 跟踪器上的 issue 依次通过由分诊角色组成的小型状态机推进。

如果本仓库把外部 pull request 视为一种请求入口（见 issue-tracker 配置），分诊同样覆盖它们：**PR 就是附带了代码的 issue**，使用相同的角色、相同的状态和相同的状态机，只有下文标注「for a PR（针对 PR）」的少数差异。按 tracker 配置把一个光秃秃的 `#42` 解析为 issue 或 PR。

分诊期间发布到 issue 跟踪器的每条评论或 issue **必须**以这段免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何撰写持久的代理简报（agent brief）
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库如何运作

## 角色

两个**分类（category）**角色：

- `bug`：某样东西坏了
- `enhancement`：新功能或改进

五个**状态（state）**角色：

- `needs-triage`：需要维护者评估
- `needs-info`：等待报告者提供更多信息
- `ready-for-agent`：规格完整，随时可交给离线的代理（agent）
- `ready-for-human`：需要人工实现
- `wontfix`：不予处理

对于 PR，同样的状态是针对所附代码而言的：`ready-for-agent` 意味着已附带简报，代理应对该 diff 采取下一步行动；`ready-for-human` 意味着已准备好由人工合并。

每个完成分诊的 issue 都应恰好带有一个分类角色和一个状态角色。如果状态角色互相冲突，标记出来，并在做任何其他事情之前询问维护者。

以上是规范的角色名称。issue 跟踪器中实际使用的标签字符串可能不同。映射关系应该已经提供给你。如果没有，请告诉用户运行 `/setup-matt-pocock-skills`。

状态迁移：无标签的 issue 通常先进入 `needs-triage`；从那里再迁移到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。一旦报告者回复，`needs-info` 返回 `needs-triage`。维护者随时可以覆盖；对看起来不寻常的迁移要标记出来，并在继续之前询问。

## 调用方式

维护者调用 `/triage` 并用自然语言描述他们想要什么。解读请求并执行。示例：

- 「给我看看任何需要我关注的内容」
- 「我们来看看 #42」（issue 或 PR）
- 「把 #42 移到 ready-for-agent」
- 「哪些已经准备好让代理接手了？」

## 展示需要关注的内容

查询 issue 跟踪器并展示三个桶（bucket），按最旧的优先排序：

1. **无标签**：从未分诊过。
2. **`needs-triage`**：评估进行中。
3. **自上次分诊记录以来报告者有活动的 `needs-info`**：需要重新评估。

当 PR 在范围内时，把这些桶里的外部 PR 也包含进来，并给每一行打上 `[PR]` 或 `[issue]` 标签。发现过程只呈现_外部_ PR（tracker 配置定义了哪些人算外部），因此协作者进行中的 PR 不属于分诊工作。此过滤只用于发现；被明确点名的 PR 无论作者是谁，始终会被分诊。

展示计数和每个条目的一句话摘要。让维护者挑选。

## 分诊某个具体的 issue 或 PR

1. **收集上下文。**通读整个 issue 或 PR（正文、评论、标签、作者、日期；对于 PR，还要读 diff）。解析任何先前的分诊记录，避免重新询问已解决的问题。使用项目的领域词汇表探索代码库，尊重该区域的 ADR。对代码库运行两项检查：(a) **冗余**：按领域概念（而不只是按请求的原话）搜索所请求行为的现有实现，并报告你查找过的地方。如果找到，就是「已实现」的 `wontfix`（第 5 步）。(b) **先前被拒绝**：阅读 `.out-of-scope/*.md`，找出任何与本请求相似的记录。

2. **给出建议。**告诉维护者你的分类与状态建议及理由，外加一段与该请求相关的代码库简要总结（包括它是否已实现）。等待指示。

3. **核实声明。**在任何追问之前，检查声明是否站得住脚。对于 bug，按报告者的步骤复现它。对于 PR，确认 diff 确实做到了它所声称的：checkout 出来，运行相关测试或命令。报告结果：已确认（附代码路径）、未能确认，或细节不足（这是 `needs-info` 的强信号）。经过确认的核实会让代理简报有力得多。

4. **追问（如有必要）。**如果请求需要充实，调用 Skill 工具两次，分别传入 "grilling" 和 "domain-modeling"，每次一轮问题地追问成形，在决策落定的同时打磨领域术语并就地更新 `CONTEXT.md`/ADR。

5. **应用结果：**

   - `ready-for-agent`：发布一条代理简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：结构与代理简报相同，但注明为什么不能委派（主观判断、外部访问权限、设计决策、手工测试）。
   - `needs-info`：发布分诊记录（模板见下文）。
   - 对于 `wontfix`，关闭 issue，评论内容取决于_原因_：
     - **已实现**：该变更已经存在于代码库中。指出它所在的位置；**不要**写入 `.out-of-scope/`（那个知识库是给_被拒绝的_请求用的，不是给已构建的请求用的）。
     - **被拒绝（bug）**：给出礼貌的解释，然后关闭。
     - **被拒绝（enhancement）**：写入 `.out-of-scope/`，在评论中链接到它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用该角色。如有部分进展，可选加一条评论。

## 快速状态覆盖

如果维护者说「把 #42 移到 ready-for-agent」，相信他们并直接应用该角色。确认你即将做的事（角色变更、评论、关闭），然后执行。跳过追问。如果在没有追问环节的情况下移到 `ready-for-agent`，询问他们是否要撰写代理简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把追问期间解决的一切都记录到「What we've established so far」一节下，以免工作成果丢失。问题必须具体、可执行，而不是「请提供更多信息」。

## 恢复之前的会话

如果该 issue 或 PR 上存在先前的分诊记录，阅读它们，检查报告者是否已回答任何未决问题，并在继续之前呈现更新的图景。不要重新询问已解决的问题。
