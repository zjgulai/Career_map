# Magpie-Horch 功能交付

只在当前仓库根的 `AGENTS.md` 标识为 LUTE Agentic System，或用户明确点名 Magpie-Horch 时使用。本 Skill 是项目规则的执行层，不能覆盖 `AGENTS.md`、ADR、用户授权和现有门禁。

## 路由边界

- 用户已授权“实现 / 修改 / 新增 / 重构”，且当前任务状态与目标足够明确时，进入本 Skill。
- 用户只要求“审查、验收、是否真的完成、发布判断”，转用 `magpie-horch-evidence-review`；审查本身不授权修复。
- 用户报告 bug、白屏、卡死、加载失败或要求定位根因，先用 `magpie-horch-incident-diagnosis`；在根因和写入范围清楚后再回到本 Skill 实施。
- 用户说“继续 / 恢复 / 从上一步”，而当前写入、验证或工作区归属不清楚，先用 `magpie-horch-context-recovery`。

## 先判定任务级别

先读仓库根 `AGENTS.md`、当前工作区状态、相关包的 `package.json`/README，以及项目要求的 `docs/pitfalls-playbook.md`。把请求分为：

- **机械代码改动**：一处、无接口/运行时/权限影响。写明目标文件与直接验证即可。
- **标准改动**：一个包或一个用户面，需查现有模式、精确写入集和目标测试。
- **复杂交付**：跨包、`file:` 装载链、宿主注入、运行时 UI、升级、持久化、安全、打包或发布。先给出任务契约，再写代码。

不要因任务看起来复杂就把小改强行拆成冗长流程；也不要因用户只说“改一下”而跳过真正的跨包边界。

## 复杂交付的任务契约

在首次写入前，用紧凑的 7 项对齐；事实与推断分开标注：

1. **结果与非目标**：用户最终会看到/得到什么，明确不碰什么。
2. **权威来源**：当前分支、相关 ADR/规格/包契约、真实运行时或上游参照物的来源。
3. **写入集**：预计修改的文件、生成物/装载点是否受影响、明确的禁区（尤其 `vendor/dsh-desktop` 与 pinned 基座）。
4. **消费链**：谁读取这次改动；若有工作树、安装源、装载点、运行中进程等多层字节，逐层列出。
5. **验收命题**：每条命题对应命令、测试、产物或实况读数；先说明“怎样会红”，不要只列会绿的检查。
6. **风险与回滚**：副作用、外部调用、迁移/删除、用户决策点与可逆路径。
7. **完成门**：哪些证据齐全才可称“完成”；不能运行的项预先标成 `UNVERIFIABLE`，不把它伪装成通过。

若选择会改变架构、数据、权限、用户可见 UX 或兼容性，先把可选方案和影响交给用户决定；其余低风险细节按项目既有惯例推进。

## 执行方式

1. 先建立基线：记录 branch、`git status`、相关包归属和现存不属于本任务的脏改动。绝不覆盖、清理或纳入它们。
2. 沿消费链读取现有实现与已有测试，不用记忆替代当前字节。新增规则优先落到已有单一事实源，而不是复制一份清单或提示语。
3. 以最小写入集实现。声明式宿主配置、`files` 清单、`file:` 副本、构建产物和运行态是不同层，不能由其中一层的绿推断另一层成立。
4. 需要多个角色时，分离“设计/实现/复核”视角：设计先定义边界，实施只改获准写入集，复核从 diff 与证据反向寻找反例。若运行环境支持并行代理，审阅者只读且不与实施者并行写同一范围；否则在同一会话中做独立的第二遍审查。
5. 改动后按风险运行最窄且真实的验证。项目默认门禁为 `pnpm run gate`；完整/发布级情形按项目约定使用 `pnpm run gate:full` 或 `pnpm run gate:strict`。读取每项结果与 `skip`/未覆盖说明，不能仅引用退出码。
6. 客户端 bundle、预设、装载点或 UI 改动，必须补消费侧/运行态证据。源码、构建或磁盘字节一致不等于运行中的应用已生效。

在共享或脏工作区运行可能写盘的命令前，先判断该命令的副作用，并用本任务范围的 before/after 状态保护归因。不要用“再跑一次绿了”抹去一次无法解释的红。

## 完成时的交付格式

只报告可核验结论：

- 改了什么，以及为何这是最小写入集；
- 每个完成门的证据：命令/测试/实况读数及结果；
- 未运行或无法证明的项，明确写 `UNVERIFIABLE` 与原因；
- 未触碰的高风险边界、剩余风险和下一步（如有）。

不要把“代码已写入”“测试退出 0”“某一层字节已同步”单独表述为功能已完成。
