# Prompt迭代专用

结构化地优化System Prompt——基于评估数据做决策，不是凭感觉改文字。

## 使用方式

在Codex中输入 `/prompt-iter {prompt-file}` 或引用此Skill后指定要优化的Prompt文件。

## 前置条件

- 评估集和评估运行器（`npm run eval`）已就绪
- 最近的评估结果文件存在：`evals/results/`
- 目标Prompt文件在 `prompts/` 目录下

## 执行流程

### 第一步：读取当前状态

```
1. 读取目标Prompt文件 prompts/{name}/v{N}.md
2. 读取最近的评估结果 evals/results/{name}-v{N}-{timestamp}.json
3. 提取失败案例明细（按维度分组）
```

### 第二步：分析失败模式

不要凭感觉。分类统计失败案例：

| 失败模式 | 案例数 | 占比 | 典型案例 |
|----------|--------|------|----------|
| 意图理解错误 | X | X% | "用户问A，Agent以为在问B" |
| 工具选择错误 | X | X% | "该调用工具A却调用了B" |
| 格式不合规 | X | X% | "要求JSON却返回了自然语言" |
| 安全绕过 | X | X% | "应该拒绝但答了" |
| 知识准确性 | X | X% | "检索到了但理解错了" |
| 过度拒绝 | X | X% | "本可以回答但拒绝了" |
| 冗长/啰嗦 | X | X% | "回答太长太绕" |

只针对占比最高的1-2个失败模式提出修改假设——不要一次改太多东西。

### 第三步：提出修改假设

```
修改假设：
问题：当前 {失败模式} 的失败率是 {X%}
假设：如果 {具体的Prompt修改描述}，这个数字会降低
理由：因为 {逻辑推理——为什么这个修改会有效}
风险：可能引入 {副作用}

备选假设（如果上面的不work）：
假设2：...
```

### 第四步：生成新版本

```
1. 将当前Prompt复制为 v{N+1}
2. 在文件头部更新：
   <!-- version: N+1 | date: 2026-07-03 | hypothesis: {一句话} | baseline_score: {分数} -->
3. 用最小改动实现修改假设（不要重写整个Prompt！）
4. 标注修改点（用注释 <!-- changed: {原因} -->）
```

### 第五步：运行对比评估

```
npm run eval -- --compare prompts/{name}/v{N}.md prompts/{name}/v{N+1}.md
```

输出格式：
```
维度          v{N}    v{N+1}   变化
意图准确率    85%     88%      +3%
工具选择      92%     90%      -2%
格式合规      95%     96%      +1%
安全          100%    100%     0%
知识准确      78%     82%      +4%
综合          87.5%   89.2%    +1.7%

胜出: v{N+1} (p < 0.05, bootstrap 500)
⚠️ 注意: 工具选择维度下降2%，虽然不显著但需关注
```

### 第六步：决策

```
如果新版显著优于旧版（p < 0.05）且无安全指标倒退：
  → 生成PR，建议灰度发布（5%→25%→50%→100%）
  → 更新CHANGELOG

如果新版差异不显著：
  → 保留旧版，记录实验结论（"修改X对指标Y无影响"）
  → 如果连续3次实验都无显著改进，可能说明这个维度的天花板已到

如果新版更差：
  → 丢弃v{N+1}，记录失败原因
  → 回到第二步重新分析

如果安全指标倒退（即使是单条）：
  → 立即丢弃v{N+1}，不发布，不走灰度
```

## 关键原则

- **一次只改一个假设**：如果一次改5个地方，你不知道哪个有效哪个有害
- **最小改动**：加一句话比改一段话好，改措辞比重写结构好
- **失败假说是金矿**：知道"什么不work"比知道"什么work"更有价值
- **如果连续3次迭代无显著改进**：可能不是Prompt的问题——考虑优化检索策略、工具描述或评估集本身
- **版本管理是必要条件**：不记录版本号和实验结论的迭代是无效迭代
