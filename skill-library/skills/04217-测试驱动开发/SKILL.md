# 测试驱动开发

TDD 是红 → 绿的循环。本技能是让这个循环产出值得保留的测试的参考基准：什么是好的测试、测试放在哪里、反模式，以及循环的规则。每一节在每一轮循环中都适用：要在循环之前和循环进行中查阅它们，而不是在循环之后。

探索代码库时，请阅读 `CONTEXT.md`（如果存在），让测试名称和接口词汇与项目的领域语言保持一致，并尊重你所触及区域的 ADR。

## 什么是好的测试

测试通过公共接口验证行为，而不是验证实现细节。代码可以彻底改变；测试不应改变。好的测试读起来像一份规格说明：「user can checkout with valid cart」（用户可以用有效的购物车结账）精确地告诉你存在什么能力，而且它不关心内部结构，因此在重构后依然存活。

示例见 [tests.md](tests.md)，mock 指南见 [mocking.md](mocking.md)。

## 接缝（Seam）：测试放在哪里

**接缝（seam）**是你进行测试的公共边界：即无需深入内部即可观察行为的接口。测试位于接缝处，绝不针对内部实现。

**只在预先商定的接缝处测试。**在编写任何测试之前，写下被测的接缝并与用户确认。不得在未经确认的接缝上编写测试。你不可能测试一切，因此预先商定接缝能让测试精力落在关键路径和复杂逻辑上，而不是每一个边界情况。

提问：「公共接口是什么，我们应该测试哪些接缝？」

当接口本身的形态存疑时（模块有多深、接缝应归属何处、接口应暴露什么），以 "codebase-design" 调用 Skill 工具来获取术语。它是模块、接口、深度、接缝、适配器、杠杆与局部性等术语的共同出处，是一份供查阅的参考，而非一个需要运行的会话。

## 反模式

- **与实现耦合（Implementation-coupled）**：mock 内部协作者、测试私有方法，或通过旁路验证（不通过接口而直接查询数据库）。识别信号：行为没有变化，重构后测试却失败了。
- **同义反复（Tautological）**：断言以与代码相同的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、以同样方式手工推导的快照、断言一个常量等于其自身），因此它天然成立，永远不会与代码产生分歧。期望值必须来自独立的真实来源：一个已知正确的字面量、一个演算过的示例、spec。
- **水平切片（Horizontal slicing）**：先写完全部测试，再写完全部实现。批量测试验证的是_想象出来的_行为：你测试的是事物的_形态_而非面向用户的行为，测试对真实变化变得不敏感，而且你在理解实现之前就锁定了测试结构。改为按**垂直切片（vertical slice）**工作：一个测试 → 一个实现 → 重复，每个测试都是一颗**曳光弹（tracer bullet）**，对上一轮循环教给你的东西作出响应。

## 循环的规则

- **先红后绿。**先写失败的测试，然后只写足以让它通过的代码。不要预判未来的测试，也不要添加投机性的功能。
- **一次一个切片。**每轮循环一个接缝、一个测试、一个最小实现。
- **重构不属于循环。**它属于审查阶段（见 `code-review` 技能），不属于红 → 绿的实现循环。
