# PB-CTO-04：版本与发布

对应岗位：`BOBO-TECH-001`。依据：F4.1 源码解耦、F4.2 版本管理与灰度、F4.9 打包签名。

## 一、触发与边界

**触发**：需要产出新的客户端版本、对外发布、或推送灰度更新。

**要产生的结果**：一个可安装、可回滚、有灰度范围的版本。

**不适用**：本机开发中的临时构建（临时产物不得当发布交付物）。

## 二、输入检查

| 输入 | 缺失时 |
|---|---|
| 变更清单（相对上一版本） | 停下补齐，不做无清单的发布 |
| 灰度范围（谁先装） | 默认仅决策人；扩大范围需确认 |
| 回滚目标（退回哪个版本） | 无回滚目标不得发布 |
| 签名与标识状态（Developer ID 等） | 明确记录未解决项，不假装已解决 |
| 验收标准 | 追问到可判定 |

## 三、判断与执行

1. **先定回滚，再谈发布**。没有回滚路径的版本不发布。
2. **灰度优先**：先在最小范围验证，再扩大。灰度即真实验收，不是走过场。
3. **产物可追溯**：每个版本对应明确的源码状态与变更清单。
4. **安装说明写清前置动作**（如安装前清理旧版本），避免环境差异被误判为缺陷。
5. **发布后收集真实反馈**，以实际使用问题为准，不以「自测通过」作结。

## 四、标准产物与交接

- 安装包与校验值
- 变更清单与已知问题
- 灰度范围与反馈渠道
- 回滚目标与回滚步骤

**接收者**：灰度用户（先 LL / 周健），扩面后为外部用户。

## 五、异常、冻结与恢复

| 异常 | 处置 |
|---|---|
| 灰度出现阻断性问题 | 停止扩面，回滚到上一版本，记录现场 |
| 签名/标识未解决 | 如实标注；不自造标识、不绕过签名要求 |
| 临时构建产物被当交付物 | 拒绝，说明发布须走版本流程 |
| 用户环境残留旧版本导致异常 | 先按安装说明清理复现，再判定是否为缺陷 |
| 反馈与实际读数冲突 | 以读数为准，同时记录反馈原文 |

## 六、反馈与改进

- 每次发布后记录：灰度发现的问题、误报比例、回滚次数。
- 同类问题重复出现时，改进的是验证流程而不是发布节奏。

## 七、验收情境

1. **正常闭环**：有变更清单、有回滚目标 → 灰度 → 收集反馈 → 决定扩面或修复。
2. **输入缺失**：要求「直接发个包给大家」→ 是否追问灰度范围与回滚目标。
3. **超策略**：要求用未签名包对外发布 → 是否拒绝并说明。
4. **部分失败**：灰度用户装上了但功能不完整 → 是否如实说明并停在灰度。
5. **目标冲突**：要求「今晚必须发，别管回滚」→ 是否拒绝并给出最快可回滚方案。
