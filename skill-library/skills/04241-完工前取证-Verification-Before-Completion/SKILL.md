# 完工前取证（Verification Before Completion）

## 概览

**核心原则：** 先有证据，再下结论，永远如此。

**违反这条规则的文字，就是违反它的精神。**

## 铁律

```
没有全新的验证证据，不得作出任何完工声明
```

如果你没有在本条消息里跑过验证命令，就不能声称它通过了。

## 门函数

```
在声称任何状态或表达满意之前：

1. 确认：哪条命令能证明这个说法？
2. 执行：完整跑一遍这条命令（全新、不打折）
3. 读取：读完整个输出，检查退出码，数清失败数
4. 核验：输出是否证实了这个说法？
   - 否：带着证据说明实际状态
   - 是：带着证据作出声明
5. 只有到这一步：才开口下结论

跳过任何一步 = 撒谎，而不是验证
```

## 常见失败

| 声明 | 需要的证据 | 不足为凭 |
|-------|----------|----------------|
| 测试通过 | 测试命令输出：0 失败 | 上一次的运行结果、「应该能过」 |
| linter 干净 | linter 输出：0 错误 | 局部检查、外推 |
| 构建成功 | 构建命令：退出码 0 | linter 通过、日志看着不错 |
| Bug 已修复 | 复现原始症状的测试：通过 | 改了代码、假定已修好 |
| 回归测试有效 | 已验证红-绿循环 | 测试通过了一次 |
| 智能体已完成 | 版本控制 diff 显示有改动 | 智能体自称「成功」 |
| 需求已满足 | 逐条对照的清单 | 测试通过 |

## 危险信号 —— 立刻停下

- 用「应该」「大概」「看起来」
- 在验证之前就表达满意（「太好了！」「完美！」「搞定了！」等）
- 未经验证就要提交／推送／开 PR
- 相信智能体自报的成功
- 依赖局部验证
- 心想「就这一次」
- 累了，想把活赶紧收掉
- **任何暗示成功、却并未跑过验证的措辞**

## 预防自我合理化

| 借口 | 事实 |
|--------|---------|
| 「现在应该能跑了」 | 去跑验证 |
| 「我有把握」 | 把握 ≠ 证据 |
| 「就这一次」 | 没有例外 |
| 「linter 过了」 | linter ≠ 编译器 |
| 「智能体说成功了」 | 独立核验 |
| 「我累了」 | 疲惫 ≠ 理由 |
| 「局部检查够了」 | 局部什么都证明不了 |
| 「换个说法，规则就不适用了」 | 精神高于文字 |

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到：34/34 通过] 「所有测试通过」
❌ 「现在应该能过了」/「看起来是对的」
```

**回归测试（TDD 红-绿）：**
```
✅ 写测试 → 运行（通过）→ 撤销修复 → 运行（必须失败）→ 恢复修复 → 运行（通过）
❌ 「我写了个回归测试」（未经验证红-绿循环）
```

**构建：**
```
✅ [运行构建] [看到：退出码 0] 「构建通过」
❌ 「linter 通过了」（linter 不检查编译）
```

**需求：**
```
✅ 重读计划 → 建立清单 → 逐条核验 → 报告缺口或完成
❌ 「测试过了，这一阶段完成」
```

**委派给智能体：**
```
✅ 智能体报告成功 → 检查版本控制 diff → 核验改动 → 报告真实状态
❌ 直接相信智能体的报告
```

## 何时适用

**以下情形一律先做：**
- 任何形式的成功／完工声明
- 任何表达满意的说法
- 任何关于工作状态的正面陈述
- 提交、创建 PR、任务完成
- 转向下一个任务
- 委派给智能体

**规则覆盖：**
- 字面原话
- 改写与同义词
- 暗示成功
- 任何暗示已完成／正确的沟通
