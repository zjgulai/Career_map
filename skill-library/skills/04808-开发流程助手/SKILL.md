# 开发流程助手

## 概述

本技能提供一套完整的、文档驱动的新项目开发工作流。核心理念：

- **文档先行**：在写第一行代码之前，需求、方案、模块划分必须明确
- **模块分离**：系统拆分为边界清晰、低耦合的功能模块，独立开发和审查
- **需求可追溯**：每个代码文件通过 MODULE_MAPPING.md 可追溯到 PRD 功能点
- **质量内建**：三级审查体系嵌入开发过程，不做事后补救

适用场景：从零构建新项目、根据 PRD 完整实现、快速原型搭建。

---

## 前置判断：项目复杂度

在阶段 2 进行正式判断，但阶段 1 即可初步感知。后续流程据此调整审查强度：

| 特征 | 简单项目 | 复杂项目 |
|------|---------|---------|
| 功能模块 | < 5 个 | >= 5 个 |
| 预估代码量 | < 1000 行 | >= 1000 行 |
| 业务逻辑 | 无复杂算法/状态机 | 有复杂业务逻辑或算法 |
| 性能要求 | 无特殊指标 | 有明确性能指标 |
| 安全要求 | 无合规要求 | 有安全合规要求 |

**差异化策略**：

| 维度 | 简单项目 | 复杂项目 |
|------|---------|---------|
| 阶段2 可行性分析 | 跳过，直接进入阶段3 | 完整执行 |
| 阶段4 任务规划 | 轻量（口头确认即可） | 完整文档 + 里程碑 |
| 审查层级 | 仅即时审查 | 三级审查全开 |
| 测试覆盖率 | > 50% | > 80% |
| 性能/安全审查 | 按需 | 必须 |
| 技术债务记录 | 跳过 | 交付时整理 |

## 核心工作流程（6 个阶段）

按顺序执行，不可跳阶段（简单项目可跳阶段2和阶段4的正式文档产出）。

```
用户需求输入
    ↓
[阶段1] 需求收集与对齐 → AskUserQuestion 多轮确认
    ↓
PRD.md + feature-list.md
    ↓
[阶段2] 技术可行性分析 + 项目复杂度定级（简单项目跳过）
    ↓
feasibility-analysis.md + tech-stack-recommendation.md
    ↓
[阶段3] 技术方案设计 + 模块分解 → 向用户展示模块列表并确认
    ↓
architecture.md + module-breakdown.md + coding-standards.md
    ↓
[阶段4] 开发任务规划 → TaskCreate 任务清单（简单项目轻量处理）
    ↓
milestone-plan.md
    ↓
[阶段5] 模块化开发实施（核心循环）
    │
    ├→ 逐模块开发
    │   ├→ 函数级开发 → 即时审查 → 问题？修复重审
    │   ├→ 模块完成 → 模块审查 → 问题？修复重审
    │   ├→ 更新 MODULE_MAPPING.md（实时同步）
    │   └→ 用户确认 → 进入下一模块
    │
    └→ 所有模块完成
        ↓
[阶段5.5] 集成审查（仅复杂项目）
    ├→ 集成测试
    ├→ 全面代码审查
    ├→ 文档完整性检查
    └→ 用户最终验收
        ↓
[阶段6] 交付与验收
    ├→ 完整交付包（文档 + 代码 + 映射表）
    ├→ 结构化交付报告
    └→ MODULE_MAPPING.md 最终确认
        ↓
项目交付完成
```

---

### 阶段 1：需求收集与对齐

**目标**：通过结构化提问明确用户需求，形成可执行的需求文档。

**执行步骤**：

1. 收集以下信息（使用 `AskUserQuestion` 多轮澄清）：
   - 项目背景和目标
   - 核心功能需求（必须实现 vs 可选实现）
   - 非功能需求（性能、安全、并发等）
   - 技术偏好和约束条件
   - 预期交付时间和优先级

2. 如果用户直接提供了 PRD 或功能清单，通读并充分理解所有功能点。接受以下形式：
   - 直接在消息中发送的功能清单
   - 上传的文档文件（使用 Read 工具读取）
   - 在线文档链接（使用 WebFetch 工具获取）

3. 在完全理解所有需求之前，不要进入阶段 2。

**输出物**：
- `docs/requirements/PRD.md` — 产品需求文档
- `docs/requirements/feature-list.md` — 功能清单（含优先级标注）

**完成标准**：用户明确确认所有功能点和优先级。

---

### 阶段 2：技术可行性分析

> 简单项目可跳过此阶段，直接进入阶段 3。判断标准见「前置判断」章节。

**目标**：评估技术实现方案，识别风险点，正式确定项目复杂度等级。

**执行步骤**：

1. 分析技术难点和实现复杂度
2. 评估第三方依赖和集成风险
3. 正式判定项目复杂度（简单 / 复杂）
4. 提供 2-3 个技术路线选项（含优缺点对比）
5. 使用 `AskUserQuestion` 让用户选择

**输出物**：
- `docs/design/feasibility-analysis.md` — 可行性分析报告（含复杂度定级依据）
- `docs/design/tech-stack-recommendation.md` — 技术栈推荐方案

**完成标准**：用户确认技术路线和项目复杂度等级。

---

### 阶段 3：技术方案设计

**目标**：确定最终技术方案，设计系统架构，完成功能模块分解。

**执行步骤**：

1. 使用 `AskUserQuestion` 与用户确认最终技术栈选择
2. 设计系统架构图和数据流
3. **功能模块分解** — 将需求拆分为独立、可单独开发的功能模块。

   **模块分解原则**：
   - 每个模块具备清晰边界和单一职责
   - 明确输入和输出
   - 与其他模块之间无循环依赖
   - 不需要等另一个模块完成才能开发

   **模块命名规范**：小写字母 + 下划线（如 `user_auth`、`product_management`、`order_processing`）

   **典型模块分类**：
   - 认证 / 用户管理
   - 核心业务实体（商品、订单、发票等）
   - 支撑服务（通知、文件上传、日志）
   - 管理后台 / 仪表盘

   向用户展示分解结果：

   ```
   根据需求分析，系统划分为以下功能模块：

   1. user_auth — 用户认证模块（登录、注册、Token 管理）
   2. product_management — 商品管理模块（CRUD、分类、库存）
   3. order_processing — 订单处理模块（创建、状态流转、支付）
   4. notification — 通知模块（邮件、站内信）
   ...
   ```

   等待用户确认后再继续。如果用户说"直接继续"，则直接进入下一步。

4. 定义模块间接口和数据流
5. 制定编码规范（注释标准、命名约定等）

**项目目录结构规范**：
```
/workspace/
├── src/
│   ├── modules/          # 功能模块（高内聚低耦合）
│   │   ├── user_auth/
│   │   ├── product_management/
│   │   └── ...
│   ├── common/           # 共享工具和类型（被多个模块依赖的代码）
│   └── main.ts           # 入口文件
├── tests/                # 测试文件
├── docs/                 # 文档目录
├── MODULE_MAPPING.md     # 代码→需求追溯映射表（阶段5生成）
└── package.json
```

**输出物**：
- `docs/design/architecture.md` — 系统架构文档
- `docs/design/module-breakdown.md` — 模块分解说明（含每个模块的职责、接口、依赖）
- `docs/design/coding-standards.md` — 编码规范文档

**完成标准**：用户确认技术方案和模块划分。

---

### 阶段 4：开发任务规划

> 简单项目可轻量处理（口头确认任务顺序即可），无需产出 milestone-plan.md。

**目标**：将模块分解为可执行的开发任务。

**执行步骤**：

1. 使用 `TaskCreate` 创建详细任务清单
2. 任务粒度：单个任务不超过 2 小时工作量
3. 明确任务依赖关系和执行顺序
4. 设置关键里程碑检查点
5. 任务安排按模块分组，完成一个模块再进入下一个

**输出物**：
- 任务清单（通过 TaskCreate / TaskUpdate 管理）
- `docs/planning/milestone-plan.md` — 里程碑计划（仅复杂项目）

**完成标准**：任务清单创建完成，用户确认开发计划。

---

### 阶段 5：模块化开发实施（核心循环）

**核心原则**："边开发边审查，发现问题立即修复，确认无误后继续。"

#### 5.1 代码文件规范

**每个模块的标准文件模式**（根据语言调整）：

| 文件 | 职责 | 示例 |
|------|------|------|
| `api.ts` / `routes.ts` | API 端点或路由处理 | REST 接口定义 |
| `service.ts` | 业务逻辑层 | 核心业务实现 |
| `models.ts` / `schema.ts` | 数据模型、Schema、ORM | 数据结构定义 |
| `helpers.ts` / `utils.ts` | 模块专属工具函数 | 格式化、校验 |
| `index.ts` | 桶导出（TypeScript）/ 包初始化（Python） | 统一对外接口 |

**共享代码处理**：如果多个模块需要公共工具，放在 `src/common/` 下，不要重复放在各模块内。在 MODULE_MAPPING.md 中注明这些文件的被依赖关系。

**代码注释要求**：
- 每个文件头部：文件用途说明
- 每个函数/方法：功能描述、参数说明、返回值、示例
- 关键逻辑块：算法思路或业务逻辑说明
- 复杂条件判断：判断条件和预期结果
- 注释语言：与用户语言保持一致

**禁止事项**：
- 禁止使用 `// TODO` 或 `# 待实现` 等占位符代替具体实现
- 禁止将不同模块的代码合并到一个文件
- 禁止模块间循环依赖

#### 5.2 三级审查体系

> 简单项目仅执行层级 1（即时审查）。复杂项目三级全开。

##### 层级 1：即时审查（每个函数完成后）

**审查内容**：
- [ ] 代码能否正常运行（语法检查）
- [ ] 注释是否完整且准确
- [ ] 函数职责是否单一
- [ ] 参数和返回值是否清晰
- [ ] 是否有明显的逻辑错误

**处理方式**：通过 → 继续下一个函数；发现问题 → 立即修复，修复后重新审查。

##### 层级 2：模块审查（每个模块完成后）

**审查内容**：
- [ ] 模块内所有函数是否通过即时审查
- [ ] 模块接口是否清晰定义
- [ ] 模块间依赖是否合理（低耦合）
- [ ] 单元测试覆盖率是否达标
- [ ] 是否存在代码重复
- [ ] 性能关键路径是否优化（仅复杂项目）
- [ ] 安全常见问题检查（仅复杂项目）

**审查流程**：
```
模块开发完成
    ↓
运行所有单元测试 → 失败？→ 修复 → 重新测试
    ↓ 通过
代码审查（结构、注释、规范）→ 问题？→ 修复 → 重新审查
    ↓ 通过
性能/安全检查（仅复杂项目）→ 问题？→ 优化 → 重新检查
    ↓ 通过
使用 AskUserQuestion 向用户展示模块成果 → 用户有异议？→ 调整
    ↓ 确认无误
更新 MODULE_MAPPING.md → 标记模块完成 → 进入下一模块
```

**输出物**：模块测试报告、`docs/development/module-review/{module-name}.md`

##### 层级 3：集成审查（所有模块完成后，仅复杂项目）

**审查内容**：
- [ ] 所有模块是否通过模块审查
- [ ] 模块间接口是否正确集成
- [ ] 端到端测试是否通过
- [ ] 整体性能是否满足需求
- [ ] 文档是否完整且准确
- [ ] 代码风格是否统一
- [ ] 是否满足所有 PRD 功能点

**输出物**：
- `docs/delivery/integration-test-report.md`
- `docs/delivery/final-review.md`

#### 5.3 开发迭代机制

**停止条件**（遇到以下情况必须停止开发，优先解决问题）：
- 单元测试连续失败 3 次以上
- 发现架构设计缺陷需要重构
- 需求理解有偏差需要与用户确认
- 性能严重不达标（仅复杂项目）
- 安全漏洞无法快速修复（仅复杂项目）

**升级机制**：使用 `AskUserQuestion` 向用户说明情况，提供问题分析和解决方案选项，等待用户决策后继续。

**进度记录**：每次审查和修复都要记录到 `docs/development/progress-log.md`（发现的问题、修复方案、修复结果）。

#### 5.4 MODULE_MAPPING.md 实时维护

**每个模块开发完成后，立即更新 MODULE_MAPPING.md**。不要等所有模块完成后再一次性生成。

格式和规范详见下方「MODULE_MAPPING.md 规范」独立章节。

**输出物**：
- 模块化组织的源代码
- 测试用例
- MODULE_MAPPING.md（持续更新）
- `docs/development/progress-log.md`

### 阶段 6：交付与验收

**目标**：完成最终交付，确保满足所有需求。

**交付清单**：
- [ ] 所有功能需求已实现并通过测试
- [ ] 代码注释完整且准确
- [ ] 技术文档齐全（架构、API、部署）
- [ ] MODULE_MAPPING.md 覆盖所有代码文件
- [ ] 用户操作手册
- [ ] 已知问题和技术债务清单（仅复杂项目）

**结构化交付报告**（必须包含）：

```
## 开发完成报告

### 已创建模块
1. user_auth — 用户认证模块
2. product_management — 商品管理模块
...

### 目录结构
src/
├── modules/
│   ├── user_auth/
│   │   ├── api.ts
│   │   ├── service.ts
│   │   └── models.ts
│   ├── product_management/
│   │   ├── api.ts
│   │   ├── service.ts
│   │   └── helpers.ts
│   └── ...
├── common/
│   └── validators.ts
└── ...

### 追溯文件
MODULE_MAPPING.md 已生成，包含 N 个文件的完整映射。

### 统计
- 模块数：M
- 代码文件数：N
- 共享工具文件：P
```

**输出物**：
- `docs/delivery/release-notes.md` — 发布说明
- `docs/delivery/user-manual.md` — 用户手册
- `docs/delivery/known-issues.md` — 已知问题清单（仅复杂项目）
- `docs/delivery/tech-debt.md` — 技术债务记录（仅复杂项目）
- 结构化交付报告（见上方格式）

**完成标准**：用户确认验收，MODULE_MAPPING.md 最终版本确认，所有交付物齐全。

## MODULE_MAPPING.md 规范

> 这是本技能的核心产出之一，将每个代码文件可追溯到 PRD 功能点。

### 格式要求

```markdown
# MODULE_MAPPING.md

## 模块代码映射表

| 代码文件路径 | 所属模块 | 功能描述 |
|---|---|---|
| src/modules/user_auth/api.ts | 用户认证 | 提供登录、注册的 API 端点 |
| src/modules/user_auth/service.ts | 用户认证 | 业务逻辑：密码加密、Token 生成 |
| src/modules/user_auth/models.ts | 用户认证 | 用户数据模型定义 |
| src/modules/product_management/api.ts | 商品管理 | 商品 CRUD 的 API 端点 |
| src/modules/product_management/service.ts | 商品管理 | 商品业务逻辑：库存校验、价格计算 |
| src/common/validators.ts | 公共工具 | 通用输入验证函数 |
| ... | ... | ... |
```

### 规则

1. **按模块分组排列**：先列出某个模块下所有文件，再进入下一个模块
2. **功能描述简洁准确**：可直接追溯到 PRD 功能点
3. **共享/公共文件**：归入"公共工具"分组，注明被哪些模块依赖
4. **覆盖所有文件**：表格必须列出每一个生成的代码文件，不得遗漏
5. **实时更新**：每个模块开发完成即更新，不要拖延到阶段 6
6. **增量同步**：需求变更导致文件增删改时，同步更新映射表（标记新增/修改/删除）

## 需求变更管理

### 变更流程

1. **变更申请**：用户提出变更需求
2. **影响分析**：
   - 识别受影响的模块和文件
   - 评估工作量和对进度的影响
   - 分析潜在风险
3. **变更确认**：使用 `AskUserQuestion` 与用户确认是否执行
4. **任务更新**：更新 TaskCreate 任务清单
5. **文档同步**：更新 PRD、设计文档、任务清单
6. **映射表同步**：更新 MODULE_MAPPING.md
   - 新增文件 → 添加新行
   - 修改的文件 → 更新功能描述列
   - 删除的文件 → 标注为 `~~已移除~~` 或从表中删除
7. **变更报告**：简要说明新增、修改或删除了哪些内容

### 变更记录

`docs/changes/change-log.md` — 记录所有变更：日期、内容、影响范围、处理结果。

## 工具使用规范

| 工具 | 使用场景 | 说明 |
|------|---------|------|
| `AskUserQuestion` | 需求确认、方案选择、变更决策 | 每个关键决策点必须使用 |
| `TaskCreate` / `TaskUpdate` / `TaskList` | 任务管理、进度跟踪 | 任务状态实时更新 |
| `Read` | 读取现有代码和文档 | 修改前必须先读取 |
| `Edit` | 修改现有文件 | 优先编辑而非新建 |
| `Write` | 创建新文件 | 仅在必要时创建 |
| `Glob` / `Grep` | 文件和内容搜索 | 了解现有实现 |
| `Bash` | 运行测试、构建命令 | 验证代码正确性 |
| `Agent` (Explore) | 复杂子任务委托 | 如大规模代码探索 |

## 质量指标

| 审查项 | 复杂项目标准 | 简单项目标准 | 检查方法 |
|--------|-------------|-------------|---------|
| 单元测试覆盖率 | > 80% | > 50% | 测试工具统计 |
| 函数平均长度 | < 30 行 | < 50 行 | 代码分析 |
| 模块耦合度 | 低（依赖注入） | 中等 | 人工审查 |
| 代码重复率 | < 5% | < 10% | 重复检测工具 |
| 注释覆盖率 | 100% 公共接口 | 100% 公共接口 | 人工审查 |
| 循环复杂度 | < 10 | < 15 | 代码分析工具 |

## 约束规则

以下规则不可违反：

1. **禁止跳过阶段**：6 阶段必须按顺序走完，简单项目可跳过阶段 2、4 的正式文档产出，但不能完全跳过
2. **禁止跳过 MODULE_MAPPING.md**：映射表为强制产出，必须列出每个代码文件
3. **禁止合并模块**：每个模块独立目录，不允许跨模块混放代码
4. **禁止占位符代码**：每个函数/方法必须有真实实现，不允许 `// TODO`
5. **禁止跳过审查**：简单项目至少完成即时审查，复杂项目三级全开
6. **禁止在未确认时推进**：每个阶段完成后必须使用 `AskUserQuestion` 确认
7. **变更必须先分析影响**：不允许未评估影响就直接改代码

## 使用示例

### 示例 1：简单项目 — 快速原型

**用户**："帮我做一个待办事项应用，能增删改查就行。"

**执行流程**：
1. 阶段 1：收集需求（确认 CRUD 范围、是否需要分类、是否持久化）
2. 阶段 2：判定为简单项目（< 5 模块，< 1000 行），跳过正式文档
3. 阶段 3：设计（React + LocalStorage，拆分为 tasks / ui / storage 3 个模块）
4. 阶段 4：轻量规划（口头确认顺序：storage → tasks → ui）
5. 阶段 5：逐个模块开发 + 即时审查 + 更新 MODULE_MAPPING.md
6. 阶段 6：交付报告 + 映射表最终确认

### 示例 2：复杂项目 — 正式交付

**用户**："帮我开发一个电商后台管理系统。"

**执行流程**：
1. 阶段 1：收集需求（商品管理、订单、用户、库存、数据统计、权限）
2. 阶段 2：判定为复杂项目（>= 5 模块，有性能和安全要求），完整可行性分析
3. 阶段 3：设计架构（React + Node.js + PostgreSQL + Redis），拆分为 6 个模块
4. 阶段 4：创建详细任务清单（20-30 个任务）+ 里程碑计划
5. 阶段 5：逐模块开发 + 三级审查 + 实时更新 MODULE_MAPPING.md
6. 阶段 6：完整交付包（release-notes + manual + tech-debt + 映射表 + 交付报告）

### 示例 3：基于 PRD 开发

**用户**："这是我们的 PRD 文档 [链接/文件]，请按照 PRD 完整实现。"

**执行流程**：
1. 阶段 1：读取并理解 PRD，提取功能清单，与用户确认理解无误
2. 根据 PRD 规模判定复杂度
3. 阶段 3-6 按对应复杂度策略执行
