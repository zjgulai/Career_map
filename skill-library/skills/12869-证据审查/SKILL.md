# Magpie-Horch 证据审查

只在当前仓库是 LUTE Agentic System，或用户明确点名 Magpie-Horch 时使用。默认**只读审查**：除非用户同时授权修复，不修改代码、配置、预设、发布物或外部状态。

## 路由边界

- 适用于已有 diff、已有测试结果、已有完成声明或待发布产物的独立复核。
- 不把单段代码的审美、命名或“是否优雅”当作验收；这类普通讨论不触发本 Skill，除非用户把它与明确的行为、质量门或合入结论绑定。
- 若用户要求的是“为什么坏 / 如何复现 / 找根因”，转用 `magpie-horch-incident-diagnosis`；本 Skill 可以在诊断或修复后做最终裁决。
- 若用户授权并要求新增或修改功能，转用 `magpie-horch-feature-delivery`；本 Skill 发现的问题先报告，不把审查权限扩展为写入权限。
- 若当前任务的真实状态不明，先由 `magpie-horch-context-recovery` 建立检查点。

## 审查先建立可信范围

1. 读取仓库根 `AGENTS.md`、`docs/pitfalls-playbook.md`、当前 branch 与 `git status`；标出不是本次事项的已有改动与未跟踪产物。
2. 找到用户声称的结果、对应规格/ADR/任务记录，以及真正的消费侧：包入口、安装/装载副本、运行中应用、打包制品或发布面。
3. 把每个结论写成可判定命题。只要命题没有明确对象、时间点和读数来源，它就还是意见，不是验收项。

## 四层证据，不互相替代

按实际风险选择需要的层，而不是机械地全部跑一遍：

| 层 | 回答的问题 | 不足以证明什么 |
| --- | --- | --- |
| 源码/差异 | 是否真的改在正确的权威处、有没有越界 | 不能证明消费者加载了它 |
| 自动化判据 | 目标行为或不变量是否被检查，且坏输入能否判红 | 不能把空射程、skip 或错误仪器读成通过 |
| 交付/装载 | `files`、构建、profile、打包或声明是否闭合 | 不能证明运行中实例已刷新 |
| 运行态/用户面 | 实际应用、接口、DOM、截图或行为是否符合目标 | 不能替代代码与回归防护 |

对声明式配置或 `file:` 依赖，审查“声明 → 产物 → 装载点 → 运行实例”整条链。对 UI 或异步故障，优先读完整负载、真实运行态或可见几何证据，不只读数据源/日志的一侧。

## 审查步骤

1. **从结论反查证据。** 先看 diff、变更范围与测试命令，再检查每条命题被哪一项证据支持。
2. **检查判据是否真在量。** 问：对象集合是什么？`expected / checked / skipped / failed` 是否可见？读不到环境时是否与数据不一致分开？有没有已知坏态或最小变异会判红？
3. **检查消费侧。** 新文件是否进运行时模块图与 `files`？声明有没有被产物实际消费？修改是否已同步、重启并在用户面观察？
4. **检查反例。** 对每个“已修好”，寻找一个最便宜的反例：错误引用、旧字节、空集合、兜底值、路径/版本漂移、超时、并发写者或错误报告路径。
5. **独立裁决。** 不能从实现者的文字直接继承“完成”结论；依据可复现输出给每一项标为：
   - `PASS`：对象、判据和必要消费侧均已证实；
   - `FAIL`：发现真实不符，点名证据与影响；
   - `UNVERIFIABLE`：缺少环境、权限、运行实例、可观察性或可信前提。说明缺什么，绝不降格成 PASS。

若要执行测试或门禁，先确认它是否会写盘、依赖共享实例或受当前脏工作区影响；记录前后状态。审查请求本身不授权“为了让测试绿而顺手修复”。

## 输出

用短表或等价清单交付：`验收命题 | 证据 | 裁决 | 缺口/下一步`。随后给出：

- 是否可以诚实地说“完成”；
- 哪些结论仅为局部验证、历史记录或计划；
- 若有风险，最小的下一步验证是什么。

禁止把 `RC=0`、页面能打开、单个日志、成功写盘或历史绿灯作为全链完成的唯一证据。
