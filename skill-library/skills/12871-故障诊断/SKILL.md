# Magpie-Horch 故障诊断

仅在 LUTE Agentic System / Magpie-Horch 上使用。若用户只要求诊断，止于证据、根因置信度与修复方案；不要擅自写修复。若用户授权修复，仍须先完成足以支持窄改动的证据链。

## 路由边界

- 入口是可观察的异常、回归或“为什么 / 定位根因 / 修复”的请求，而非泛泛的代码质量担忧。
- 诊断确认写入范围后，实施阶段可转交 `magpie-horch-feature-delivery`；若用户只授权诊断，停在方案与证据。
- 修复或历史改动需要独立验收时，转交 `magpie-horch-evidence-review`。
- 若故障是否仍存在、当前版本或任务归属都不清楚，先用 `magpie-horch-context-recovery` 恢复真实检查点。

## 建立事故合同

开始时先读根 `AGENTS.md`、`docs/pitfalls-playbook.md`、相关 ADR/包契约和当前工作区状态。明确：

- 用户可感知的失败、发生条件、复现步骤与“修好”的可观测定义；
- 当前分支、版本、实际运行的宿主/产物/装载点；
- 已有脏改动和不可触碰范围；
- 本轮允许的取证手段与任何外部、凭证、重启或删除边界。

把“猜测”“历史现象”“当前读数”分开写。一次历史成功或一次重试成功，都不是当前故障已消失的证明。

## 诊断循环

1. **重现与基线**：先获取当前失败窗口的日志、生命周期、运行态和相关代码/配置。把时间、对象来源和版本写进读数，避免读到同名但非权威的副本。
2. **分层观察**：分别检查源代码、构建/安装产物、装载点、宿主组合与用户面。一个层面的正常不能替另一层背书。
3. **并列假设**：列出至少两个能解释现象的机制；每项包含支持证据、反证和最便宜的区分实验。不要连续叠 patch 来代替实验。
4. **因果收敛**：只有当变更某机制会按预期改变症状，且排除了主要竞争解释，才把它写为根因。否则是“未归因”或“候选根因”。
5. **窄修复与回归**：修复只动已证实的最小范围；验证必须包括修复前失败形态、修复后成功形态，以及最相邻的回归面。

## 特别规则：卡死、白屏、启动持续加载

当同时出现高 CPU、CDP/inspector 超时、console 无输出、`rAF`/定时器不跑等主线程饿死信号时，遵循仓库 `AGENTS.md` 的旁路取证规则，并在可用时使用既有 `dsh-desktop-diagnostics` Skill。不要先把问题归因于 JIT、CLI、版本或简单延长 watchdog 超时。

对于 MutationObserver/重复挂载类问题，先验证单例与“不再满足移动条件”的不变量；对于启动/插件组合问题，同时核对 lifecycle、同时间段日志、profile/bundle/lockfile、client module 与实际 renderer 载荷，不能只看 UI 或一条日志。

## 输出与裁决

报告按以下顺序给出：

1. 已复现的症状与证据；
2. 根因（或候选根因）及因果链；
3. 排除过的竞争假设；
4. 修复范围、回滚方式与验证结果；
5. `PASS` / `FAIL` / `UNVERIFIABLE` 的最终裁决及尚缺读数。

“症状暂时消失”“日志少了一条”“提高超时后可启动”只能称为缓解，除非完整验收命题已被证实。
