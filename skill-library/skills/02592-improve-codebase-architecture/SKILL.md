# Improve Codebase Architecture

浮现架构摩擦，并提议**深化机会（deepening opportunities）**：把浅层模块变成深层模块的重构。目标是可测试性和 AI 可导航性。

这个命令以项目的领域模型为_依据_，建立在一套共享的设计词汇之上：

- 调用 Skill 工具并传入 "codebase-design"，获取架构词汇（**module 模块**、**interface 接口**、**depth 深度**、**seam 接缝**、**adapter 适配器**、**leverage 杠杆**、**locality 局部性**）及其原则（删除测试、「接口就是测试面」、「一个适配器 = 假设的接缝，两个 = 真实的」）。在每一条建议中精确使用这些术语，不要滑向「component」「service」「API」或「boundary」。
- `CONTEXT.md` 中的领域语言为好的接缝提供命名；`docs/adr/` 中的架构决策记录（ADR）记录了这个命令不应重新争论的决策。

## 流程

### 1. 探索

**先定范围，再扫描：YAGNI。**深化一个模块的回报在于让未来对它的变更更容易，所以要给最近变更过的代码库部分加额外权重。在动手看之前先决定*看哪里*：

- 如果用户指明了一个方向（一个模块、一个子系统、一个痛点），就采用它，并跳过下面的推断。
- 否则，往回追溯一大段提交历史（`git log --oneline`），找出代码库的热点——那些反复出现的文件和区域，让这些路径首先牵引你的注意力。如果变更很分散、没有明显的热点，就扩大搜索面。

先读项目的领域术语表（`CONTEXT.md`）和你所触及区域里的任何 ADR。

然后派一个子代理去走查代码库。不要遵循僵化的启发式规则；有机地探索，并记下你在哪里感到摩擦：

- 哪里要理解一个概念就必须在许多小模块之间来回跳？
- 哪些模块是**浅层**的，接口几乎和实现一样复杂？
- 哪里只是为了可测试性而抽出了纯函数，但真正的缺陷藏在它们的调用方式里（没有**局部性**）？
- 哪里紧耦合的模块在接缝之间泄漏？
- 代码库的哪些部分未经测试，或难以通过其当前接口测试？

对任何你怀疑是浅层的东西应用**删除测试**：删掉它会让复杂度集中起来，还是只是挪个地方？「是的，会集中」正是你要的信号。

### 2. 以 HTML 报告呈现候选者

把一个自包含的 HTML 文件写到操作系统临时目录，这样仓库里不会落下任何东西。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（Windows 上是 `%TEMP%`），写到 `<tmpdir>/architecture-review-<timestamp>.html`，让每次运行都得到一个全新文件。为用户打开它（Linux 用 `xdg-open <path>`，macOS 用 `open <path>`，Windows 用 `start <path>`），并告诉他们绝对路径。

报告用**CDN 引入的 Tailwind**做布局和样式，用**CDN 引入的 Mermaid**画那些图/流程/序列能可靠传达结构的图。把 Mermaid 与手工打造的 CSS/SVG 视觉混用：关系呈图状（调用图、依赖、序列）时用 Mermaid，想要更有编辑感的东西（体量图、剖面图、折叠动画）时用手工搭建的 div/SVG。每个候选者都要有一张**前后对比可视化**。要有视觉表现力。

对每个候选者，渲染一张卡片，包含：

- **文件**：涉及哪些文件/模块
- **问题**：当前架构为什么造成摩擦
- **解决方案**：用大白话描述什么会改变
- **收益**：用局部性和杠杆来解释，以及测试会如何改善
- **前后对比图**：并排、手绘，展示浅层状态与深化之后的状态
- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 之一，渲染成徽章

报告末尾加一个**首推建议**一节：你会先处理哪个候选者，为什么。

**领域用 `CONTEXT.md` 的词汇，架构用 `/codebase-design` 的词汇。**如果 `CONTEXT.md` 定义了「Order」，就说「Order 受理模块」，而不是「FooBarHandler」，也不是「Order 服务」。

**ADR 冲突**：如果一个候选者与现有 ADR 相矛盾，只有当摩擦真实到值得重新审视该 ADR 时才浮现它。在卡片中清楚标注（例如一个警示框：_「与 ADR-0007 相矛盾，但值得重新打开，因为……」_）。不要列出某份 ADR 所禁止的每一种理论上的重构。

完整的 HTML 骨架、图表模式和样式指南见 [HTML-REPORT.md](HTML-REPORT.md)。

先不要提议接口。文件写好后，问用户：「这些里面你想探索哪一个？」

### 3. 盘问循环

用户挑好候选者之后，调用 Skill 工具并传入 "grilling"，与他们一起走决策树：约束、依赖、深化后模块的形态、接缝后面放什么、哪些测试存活下来。

决策成形时，副作用就地发生；随时调用 Skill 工具并传入 "domain-modeling"，让领域模型保持最新：

- **用了一个 `CONTEXT.md` 里没有的概念给深化后的模块命名？**把这个术语加进 `CONTEXT.md`。文件不存在就惰性创建。
- **对话中打磨了一个模糊的术语？**就地更新 `CONTEXT.md`。
- **用户用一个站得住脚的理由否掉了候选者？**提议一份 ADR，措辞是：_「要不要我把这个记成一份 ADR，让未来的架构评审不再重复提议它？」_只有当这个理由确实会被未来的探索者需要、以避免重复提议同一件事时才提议；跳过临时性理由（「现在不值得」）和显而易见的理由。
- **想为深化后的模块探索替代接口？**调用 Skill 工具并传入 "codebase-design"，使用它的「设计两次」并行子代理模式。
