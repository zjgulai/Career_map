# PB-CTO-03：故障诊断与通路验证

对应岗位：`BOBO-TECH-001`。依据：本机 `~/.dsh/AGENTS.md`「遇到问题先读真实读数」、范式 L5。

## 一、触发与边界

**触发**：渠道不通、消息收不到、回复没发出、行为异常、装配不生效。

**要产生的结果**：一个**有原始读数支撑**的原因判定，以及修复或明确的阻塞说明。

**不适用**：功能需求变更（走 PB-CTO-01/02）。

## 二、输入检查

| 输入 | 缺失时 |
|---|---|
| 现象描述（谁、何时、期望什么、实际什么） | 追问到可复现 |
| 原始读数：日志、API 返回、界面状态 | **不得凭空象推断**，先取读数 |
| 最近一次变更（配置、版本、权限） | 主动查，不假设「什么都没改」 |

## 三、判断与执行

**总则是先读读数，再提假设。**

1. **取原始读数**，而不是描述外观：
   - DSH 日志：`~/Library/Application Support/DSH Desktop/logs/`（按 `[dsh-feishu]` 等标签过滤）
   - 平台侧：直接调 API 拿返回码（凭据 → token → 目标接口）
   - 运行时：连接状态、重连循环、装配是否装载
2. **分层定位**，按顺序排除：
   1. 凭据层：token 能否签发
   2. 权限层：用 API 读实际权限列表，比对该渠道所需清单（**不看后台勾选状态**）
   3. 订阅层：事件订阅方式是否配置（**此层无法通过 API 读取**，只能实测）
   4. 连接层：长连接是否建立、是否在重连循环
   5. 装配层：preset 是否装载、persona 是否生效
   6. 会话层：群/私聊与会话映射是否正确
3. **一次只改一个变量**，改完立即复测并记录。
4. **对照已知良好样本**：本机已有可用机器人可作对照，比对配置差异比读文档快。

## 四、标准产物与交接

- 诊断记录：现象、读数原文、分层排查过程、结论、修复动作、复测结果
- 若为范式级缺口，追加一条到范式文件的对应层

## 五、异常、冻结与恢复

| 异常 | 处置 |
|---|---|
| 读数拿不到 | 明确说明拿不到以及为什么，不用推测填充 |
| 需要重启 DSH 才能生效 | **必须先取得同意**——重启会中断进行中的会话 |
| 长连接被第二个消费者抢占 | 立即下线多余消费者（长连接模式下事件会分流，表现为间歇性收不到消息） |
| 修复后无法复测 | 记录为「未验证的修复」，不得标记为已解决 |
| 反复重连 | 停止盲目重启，转为读日志定位首次失败点 |

## 六、反馈与改进

- 每个故障在范式对应层留下一条约束，避免同类问题重犯。
- 反复出现的诊断步骤固化成脚本；`scripts/` 里保留可执行版本。

## 七、验收情境

1. **正常闭环**：消息收不到 → 分层排查 → 定位为首层权限缺失 → 修复 → 复测通过。
2. **输入缺失**：只给「机器人不好用」→ 是否追问到可复现而非直接改配置。
3. **超策略**：需要重启才能生效 → 是否先取得同意。
4. **部分失败**：修好了发送但接收仍不通 → 是否如实拆分陈述而非宣布「修好了」。
5. **冻结恢复**：找不到原因 → 是否如实说明并给出下一步取数计划。
