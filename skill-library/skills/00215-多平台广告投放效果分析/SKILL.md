# 多平台广告投放效果分析

凡向用户输出“设置 - 账号管理”引导，必须先读取 `../discover-store-accounts/references/merchant-account-management.md`，并按其中的 Agent 回复契约完整展示四步图文教程；同一条回复最多展示一次，不得只给链接或输出插件开发机路径。

> **Python 执行统一口径**：本 Skill 的 Python 脚本均使用 `python3` 工具执行，脚本路径与传参路径先展开为绝对路径。

执行阶段统一使用 `multi-platform-intention-router.plan.v3`，且必须满足 `skill=multi-platform-ads-analysis`、`analysisType=广告分析`。计划可以由 Router 生成，也可以在用户直接调用本 Skill 时根据当前对话中的店铺和周期信息规范化生成。当前支持淘宝、天猫、拼多多、京东、抖店（抖音千川）与 1688（数字营销 P4P）：Router 计划中的淘宝和天猫分别使用真实店铺平台 `taobao`、`tmall`；广告 Adapter 再把天猫映射到 `taobao` 阿里妈妈采集通道，同时保留 `platformId=tmall` 的登录范围。拼多多、京东、抖店和 1688 分别使用 `pdd`、`jd`、`doudian`、`1688`。不得把其他平台降级为已支持平台。

- 淘宝/天猫优先选择昨天、过去 7 天、过去 15 天和过去 30 天快捷周期；拼多多优先选择今日/昨日/近 7 日/近 30 日/近 90 日中的匹配项；京东优先选择昨天、近 7 天和近 30 天；抖店优先选择昨天、最近 7 天和最近 30 天。
- 日期统一按“匹配的快捷周期 → 页面已明确支持的 URL 日期参数 → 精确日期组件 → 页面默认周期”降级。不得臆造 URL 参数；找不到某级能力时继续下一级，日期操作失败本身不阻断下载。
- Router 仍必须提供明确观测周期和冻结的绝对 `start/end`。最终使用页面默认或近似周期时保留真实文件并标记周期未验证，不得把它写成用户请求周期，也不得生成投放调整动作。

本文中的 `references/` 和 `scripts/` 均相对本 `SKILL.md` 所在目录。先定位 Skill 目录，再调用脚本。

生成指标、洞察或 HTML 前必须读取 [references/report/analysis-playbook.md](references/report/analysis-playbook.md) 和 [references/report/ai-insight-protocol.md](references/report/ai-insight-protocol.md)。平台字段识别仍以对应 Converter 契约为准；AI 只负责问题识别、洞察和行动建议，不覆盖平台事实或脚本计算指标。

## 强制触发

- 用户通过 `/multi-platform-ads-analysis`、`$multi-platform-ads-analysis`、明确写出 `multi-platform-ads-analysis`，或用“调用/使用这个 Skill”等等价方式指明本 Skill 时，必须进入并执行本 Skill，不得改路由到其他 Skill，也不得仅以“必须先经过 Router”为由拒绝。
- 直接调用未附带 Router plan 时，优先复用当前对话已给出的平台、店铺和时间范围，生成等价 `plan.v3` 后继续工作流。时间范围缺失时按默认近 7 天填充并提示后继续，不追问。店铺范围需消歧时（详见工作流步骤 0，只按**已登录**候选判定），**必须**调用 `ask_user(mode="form")` 列出候选店铺“`platformName / storeName（脱敏 account）`”让用户选择（含「全部店铺」选项）；**禁止**用自由文本框索要店铺名，也禁止用「请回复'确认 + 店铺名'」「请确认目标店铺后开始」这类句式代替表单。目标 `enable` 混合时不启用 `ask_user`，自动跳过未登录目标后继续（详见步骤 0 第 3 步）。
- 强制触发绕过的是 Router 前置要求，不绕过平台能力、只读执行、周期精度、数据完整性、店铺消歧门禁和其他安全边界。

## 边界

- 只读取 Router 计划或直接调用时规范化生成的等价计划，以及 Execution New 交付的店铺级广告 Excel。淘宝/天猫当前尝试五类阿里妈妈报表，营销场景唯一必选；拼多多固定尝试六类报表，商品推广汇总唯一必选；京东当前尝试十类报表，非全站和全站核心汇总两份必选；抖店固定尝试六个千川角色，推商品-商品唯一必选。其他已调度报表是可选趋势或诊断投影，重试耗尽后可跳过，且不得与父级总计重复相加。
- Router plan 的 `platform` 是真实店铺平台，淘宝和天猫必须分别保留为 `taobao/tmall`。Adapter 生成 Execution 请求时，天猫转换为 `platform=taobao` 以选择阿里妈妈 DSL 和 `requestId`，但 `accountDiscovery.platformIdList` 必须写 `tmall`。`commercePlatform` 只用于兼容历史 `taobao + commercePlatform=tmall` 计划；新计划不得使用该结构。不得复制天猫广告 DSL。
- 只使用 `references/dsl-selection.json` 中的原子 DSL ID；每个 DSL 的全部 `goto` 必须与 `references/collection-surface-policy.json` 中的只读页面白名单完全一致。
- 阿里妈妈在线采集当前只调度营销场景、商品、计划、人群和关键词报表。内容、创意、地域、单元和权益报表暂不下载，必须保留在 `dsl-selection.json.temporarilyDisabled` 中，不得写入本轮 Execution 请求；对应 DSL、页面白名单和离线 Converter 识别能力继续保留。
- 京东品牌分析和类目分析的汇总、分天报表暂不下载，四个 DSL 必须保留在 `dsl-selection.json.temporarilyDisabled.jd` 中；京东在线调度只包含核心、产品线、SKU 和 SPU 的汇总/分天任务，离线品牌和类目文件仍可由 Converter 识别。
- 禁止打开、解析或保存用户附带的 URL。
- 禁止生成、修改或直接运行 DSL；全部委托 `multi-platform-rpa-execution-new`。
- 禁止扫描共享下载目录或运行根目录猜测店铺数据。
- 禁止把平台 lane 映射成执行代理：严禁调用 `functions.sessions_spawn`，不得使用 `agent`、`general`、多会话或任何其他子 Agent 机制执行某个平台、店铺或报表 lane；不得以并行执行、任务拆分、浏览器操作、耗时较长或上下文隔离为理由派出子 Agent。所有 lane 必须由当前主 Agent 在本次唯一运行目录内统一调度，并共同遵守本 Skill 的事件契约、全局停止规则、结果记录和目录归属。需要提速时，只能增加当前主 Agent 对 `functions.browser_rpa_run` 的同批工具调用数，不得增加 Agent 或会话数量。
- 打断边界：执行前允许的打断项只有**平台范围与店铺范围**：平台意图不明确时先追问平台，平台确定后店铺无法唯一确定时再追问店铺，两者都必须 `ask_user(mode="form")`。店铺打断条件只按**已登录**（`enable=true`）候选判定：用户指定的店铺在已登录候选中无法唯一匹配（命中多条/同店多账号）、同平台已登录候选 `N_on≥2` 且用户本轮未唯一指定（只给平台名、未点名具体店铺也未说“全部店铺”）。`N_on=1` 或用户已唯一指定（含明确“全部店铺”）时不打断；`<active_store>`、历史店铺、路由注入信息一律不算用户已指定。**登录状态不是打断项**：目标 `enable` 混合、某平台无已登录店铺或无候选时，自动跳过这些目标并在开工播报中列明后继续执行剩余已登录店铺，禁止用 `ask_user` 或文字就登录状态索要确认。观测周期等有默认值的参数一律取默认并由开工播报的对应字段告知后继续；可选报表失败仍按下文广告报表失败门禁自动跳过，不询问用户。禁止用普通文字、Markdown 表格、编号列表、「确认使用【…】」「请回复'确认 + 店铺名'」「请确认目标店铺后开始」句式或任何自由文本框索要确认。
- 开工播报（硬规则）：按 `../multi-platform-intention-router/references/common/kickoff-briefing-contract.md`，在步骤 0 末尾（目标与周期都已写入等价 `plan.v3`）、进入采集之前播报**恰好一次**并在同一轮继续执行；禁止用 `ask_user` 承载，其余禁令见契约 §5。字段口径：动作 = “进入各平台推广后台采集广告报表”；交付 = “广告投放分析 HTML 报告 + 全量 Sheet 汇总 Excel，保存到本次会话工作目录”。
- 在线广告分析每次运行都必须在 Execution 登录态门禁重新调用一次 `discover_store_accounts`。本 Skill 的 `build_collection_requests.py` 必须根据本次计划中的真实店铺平台映射、去重并写入 `accountDiscovery.platformIdList`；Execution 只能校验并原样透传，不得重新推导。账号发现必须带非空 `platformIdList` 调用一次，禁止零参数查询全量账号、禁止 `[]`、不得添加无关平台、不得按店铺拆分多次调用。用户平台意图不明确时必须先 `ask_user(mode="form")` 只问平台（选项仅列广告分析支持的淘宝 / 天猫 / 拼多多 / 京东 / 抖店 / 1688 并附「全部平台」，允许多选），拿到答复后再发起账号发现，禁止默认全平台继续；完整契约见 `../multi-platform-intention-router/references/common/store-scope-contract.md`「账号发现范围统一契约」。计划平台键到账号管理 `platformId` 的映射见下方「平台键映射」唯一权威表；淘宝和天猫虽然共用广告 DSL，也禁止互相代查登录态。

- 页面权限门禁：在线采集页面明确显示当前账号无权访问、暂无权限、未授权或 HTTP 403/Forbidden 时，立即停止整个广告分析任务，不继续其他店铺/平台/报表，不重试、不后处理、不生成 partial/no_data 报告。必须把页面上的权限报错原文直接告诉用户，并要求用户先解决平台权限问题；不得改写成笼统的“采集失败”。普通超时、空数据、登录失效、风控或缺少下载不能冒充权限问题。
- 广告报表失败门禁：`references/collection-requirement-policy.json` 是四个采集平台必选/可选角色的唯一策略源，Adapter 必须把完整分区写入 `batch-request.json.taskRequirement`。所有任务仍先按 Execution 的 `retryPolicy` 自动重试；可选任务耗尽重试后写入 `skippedOptionalTasks` 并继续，不得再次要求用户选择重试、上传或忽略，也不得复用旧文件补齐；必选任务失败才阻塞对应店铺报告。新增 DSL 未在策略中明确分类时请求构建必须失败。权限错误始终服从上一条全局停止规则，不能按可选任务跳过。
- 必选/可选边界必须贯穿 Converter：必选角色归属、内容或结构无法成立时阻塞；可选角色出现未知文件、不同内容的同角色冲突、Sheet/表头漂移或解析失败时只淘汰该角色，并把证据写入 manifest。重复处理必须先识别业务角色，再只对同角色文件比较 SHA-256；字节相同副本可折叠，内容不同不得自动合并或按修改时间猜测。
- 正式交付优先依赖同级 `multi-platform-store-analysis-new/scripts/spec_delivery.py`，旧安装仅兼容回退到 `multi-platform-store-analysis/scripts/spec_delivery.py`。两者都缺失时必须在转换前失败并报告已检查路径，不得把报告写回 Skill 安装目录或临时拼接另一套交付结构。
- 平台前置拦截：收到广告分析请求后，必须先确认本次目标平台。当前支持淘宝、天猫、拼多多、京东、抖店（抖音千川）和 1688（数字营销 P4P）；只要目标范围包含上述六个平台之外的任何平台，必须在账号发现、计划生成、附件处理、RPA、指标计算和报告生成之前整体结束，回复”当前广告分析仅支持淘宝、天猫、拼多多、京东、抖店和 1688，暂不支持该平台的广告分析。”不得把未支持平台改路由为自定义分析、店铺分析或相近平台，不得先处理请求中的已支持平台，也不得生成部分报告。用户没有明确目标平台时，属于平台意图不明确，必须在账号发现之前先 `ask_user(mode="form")` 只问平台（选项仅列广告分析支持的淘宝 / 天猫 / 拼多多 / 京东 / 抖店 / 1688 并附「全部平台」，允许多选），拿到答复后再继续；禁止默认取账号管理中已保存的受支持平台全部店铺直接执行。只有目标范围明确包含上述六个平台之外的平台时才整体结束。
- 1688 回报口径专项：1688 是 B2B 询盘获客场景，广告不产生站内成交额，源报表没有成交金额与 ROI 字段。其回报由线索量、询盘量、优质询盘量承载，效率主指标是线索成本 CPL（消耗 ÷ 线索量，**越低越好**，与 ROI 方向相反，象限含义与红绿配色须整体翻转）。禁止在 1688 报告中把投产比 ROI、总成交金额、成交笔数等电商口径作为数据卡片或图表指标，也禁止把这些结构性不存在的字段列入「待补字段」提醒。曝光量含平台免费扶持流量（各渠道占比实测相差十倍以上），做效率比较必须改用付费曝光（曝光量 − 扶持曝光量）；线索为 0 时 CPL 保持缺失，不得按 0 处理，否则零线索商品会被误判为零成本获客。四条产品线（全站推店 / 全站销货 / 精准获客 / 关键词卡位）**全部可选，没有任何一条是必选产物**——它们在 1688 的文件结构中是**并列关系**而非主从关系：各有独立的投放设置、独立计费、独立一套导出文件，页面上各占一个 `type` 参数，彼此不存在包含或汇总关系，没有哪条是「总表」而其余是「分表」。商家开哪几条由经营需要决定，只开一条也是正常形态。在并列结构里指定某条必选，等于假设「所有商家都开了这条」；该假设不成立时，转换器收到的是一份内容合法但全为空值的概览表（1688 对未开通产品线返回字面 `null` 或 `0`，不是缺文件也不是错误码），门禁无从分辨「没开」与「采集失败」，只能误判为故障中止。唯一门禁是**至少一条产品线有有效投放**，判据为「消耗 > 0 或点击 > 0」——1688 无投放时显示 `0` 或 `null` 而非 `--`，不能沿用京东按空态文案判断的方式。同理全店口径取**实际在投产品线的合计**，不以某条固定产品线作基准；该定义对任意开通组合都成立，只开一条时份额恒为 100%、错配度全为 0，报告应如实呈现并说明「本期仅 X 在投」。四条都无有效投放时才失败，报错须区分「一个概览表都没找到」（采集故障）与「找到了但全为零投放」（确实停投或周期选错）。完整口径见 `references/report/1688-converter-contract.md`。
- 1688 采集周期核对：1688 日期输入框为 `readonly`，只能点选日历；页面右下角「AI 推广专员」是可拖动悬浮组件，位置随用户上次拖动而变，会**间歇性**盖住日期面板的「确定」按钮。被遮挡时即便强制点击，事件也只跳过可操作性检查、不改变浏览器命中测试，最终落到浮层上并触发面板外点击走取消路径——表现为「点击成功、面板关闭、输入框显示值正确，但查询从未提交」，静默下载平台默认周期（近 7 天）的数据。注意输入框 `value` 绑定的是**草稿态**：点快捷档后立即变化且 Escape 不回滚，因此它不能作为「周期已生效」的判据。
  - 采集侧：四个 p4p DSL 用 `when` 条件分支处理——确定按钮可见时走完整选日期流程，被遮挡时整组跳过、改用页面默认周期继续采集。分支内所有日期步骤 `onError=continue`，日期失败不阻断下载。
  - 数据侧（周期的唯一判据）：**源报表自带日期证据**，转换器从「数据概览报表」的分日 Sheet「统计日期」列恢复实际周期。不要用文件名或 Sheet 名判断——概览表文件名只有导出时间戳没有周期，Sheet 名带周期但会被 Excel 截断到 31 字符。
  - 报告周期一律使用**实测周期**而非请求周期；两者不一致时 manifest 的 `periodVerification.status=mismatch`，并在数据质量说明中标注「请求 X~Y，实际覆盖 A~B」，全部结论按实际周期解读。源文件无分日数据时标为 `unverified`。
- 禁止修改推广计划、渠道、预算、出价或店铺设置。用户要求执行广告投放、调整出价、新建/暂停/删除计划、修改预算、操作人群包或任何写入性广告动作时，必须明确拒绝并告知"广告操作功能暂不支持，当前仅支持只读分析"。不得尝试执行、不得部分执行、不得引导用户绕过。
- 写操作前置拦截：目标平台通过平台门禁后，再扫描整条指令是否包含写入性动作（删除关键词/计划/创意、调整出价/日限额、新建/暂停/启动计划、修改匹配方式、操作人群包等）。只要指令中包含任何一项写操作，必须在执行任何步骤前整体拦截，回复"您的请求中包含广告操作（如删除关键词、调整出价、修改日限额），这些功能暂不支持。当前仅支持只读数据分析，如需巡检诊断可以为您生成分析报告，但不会执行任何变更。"不得先做分析再尝试操作，不得把"巡检"拆出来单独执行而默认后续操作留给用户自行完成，不得因用户授权"你来做主"而获得写操作权限。
- 能力前置拦截：关键词报表已可作为只读诊断证据，但真实字段和分析结论必须以本轮导出为准；仍不支持实时竞价/实时调价、自动目标 ROI 优化，也不能从渠道汇总反推计划明细。用户只请求写入或自动调优能力时，在账号发现前直接说明不支持；混合请求中不得伪造对应模块。
- 输入上限：每店最多 20 个原始文件，单文件最多 100 MB、合计最多 300 MB，单计划最多 20 店。`.xls` 必须明确失败并要求导出或转换为 `.xlsx`，不得静默忽略。
- 缺失值不得按 0 使用；无真实同行或时序来源时不得生成同行对标和趋势。
- 每个平台、店铺和账号必须独立转换、聚合和出报告。跨平台只能在存在可验证的同款映射时比较同类问题标签或同口径比例，禁止合并花费、流量、成交和退款事实。
- 严禁使用 write 工具或手动拼接 HTML 产出报告文件。所有报告必须经由 `scripts/finalize_reports.py` 渲染管线生成；只有在调试已有 metrics/insight JSON 时才可单独调用 `scripts/report/render/render_report_v2.py`。

- 不得删减 v2 五大模块结构。01 核心结论始终渲染；02-05 按数据可用性动态渲染。用户可见章节编号必须按实际渲染顺序从 01 连续编号，不得因中间模块隐藏而跳号；AI JSON 内部模块键仍固定使用 01-05。指标口径说明不是独立模块，必须放在 02 店铺总览末尾并默认折叠。
- 禁止主动提议或自行使用 Mock 数据生成报告。只有用户明确要求"使用 mock 数据"时才可构造模拟数据；默认必须基于 Execution 采集到的真实数据。采集为空时走零数据协议，不得以 mock 数据替代。

## 工作流

### 0.0 环境与依赖预检（最先执行，硬门禁）

**所有平台的广告分析都必须先跑这一步**，位置在账号发现之前。本 Skill 全链路依赖 `openpyxl` / `xlrd` / `PIL` / `fontTools` 读写 Excel 与出图，先完成依赖准备可避免采集结束后才暴露环境故障。

执行（路径先展开为绝对路径）：

```
python3 <plugin_root>/skills/multi-platform-intention-router/scripts/check_python_env.py --json -m openpyxl -m xlrd -m PIL -m fontTools
```

**该脚本会自动准备依赖**：`openpyxl==3.1.5`、`et_xmlfile==2.0.0`、`xlrd==2.0.2` 缺失时，只从插件 wheelhouse 离线安装到运行时动态解析的当前 Accio/Phoenix Python `site-packages`；`PIL` / `fontTools` 保留预装环境与镜像补装。调用方只读退出码，禁止另拼 `pip install`、导入隐藏 resolver、硬编码 `external-tools/<version>` 或直接改共享目录。

共享 `site-packages` 已有不同 Excel 版本、包目录与 dist-info 不完整或目标不可写时，脚本会在覆盖前停止并保留冲突原文。不得删除或降级其他插件的依赖来绕过。

按退出码分流，**不得跳过继续**：

| 退出码 | 含义 | 动作 |
|---|---|---|
| `0` | 依赖齐全（可能已从本地 wheel 或镜像自动准备） | 静默继续步骤 0，不向用户播报 |
| `1` | 自动准备后仍无法解析，或共享目标存在版本冲突 | **停止**，按下方话术提示用户，不进入账号发现 |
| 脚本自身无法运行（文件缺失 / 解释器不可用） | 插件安装不完整 | **停止**，提示重新安装插件，不尝试修复 |

退出码 `1` 时向用户播报（面向商家表达，不暴露模块名以外的技术细节）：

> 分析所需的运行组件未能自动准备（缺失：`<JSON 中 modules[] 里 resolved=false 项的 module 字段值，多个用顿号分隔>`），本次广告分析无法开始。请更新 Accio Work 客户端或相关插件后重试；若诊断提示版本冲突，请联系支持并提供冲突原文，不要手工覆盖共享 Python 目录。

字段名以脚本实际输出为准：模块名在 `modules[].module`（不是 `name`）；成功项带 `layer` / `origin` / `version`，失败项带 `layer` / `error`。Excel wheel 与目标目录见 `offlinePythonDeps.wheelhouse` / `offlinePythonDeps.targetDir`；`autoInstall.error` 保留安装或冲突原文。

同时保留 JSON 结果中的 `sitePackages` 与 `baseDirs` 供排查，但不要整段打印给用户。**禁止**改写解释器路径或绕过脚本手动装包；依赖准备逻辑集中在脚本内。

预检通过后不重复执行：同一次运行内即使多店多平台，也只在最开始跑一次。首次准备可能耗时数十秒，属正常现象，不要因等待而重复调用。

### 0. 账号发现与店铺消歧（硬门禁，先于 enable 判定）

平台门禁和写操作门禁通过后、创建运行根目录前，先确定本轮目标店铺集合。已有 Router plan 时直接使用其 `stores[]`；直接调用（无 Router 前置）时执行本步骤。

**第 1 步：账号发现**。按本轮目标平台映射非空 `platformIdList`（映射关系见「边界」段的**平台键映射**唯一权威表，此处不再复述，避免两处清单漂移），调用**一次** `discover_store_accounts` 并复用完整 `accounts[]` 结果；禁止零参数全量扫描、禁止 `[]`、禁止按店铺拆成多次调用。用户平台意图不明确时必须先 `ask_user(mode="form")` 只问平台（选项含「全部平台」，允许多选），拿到答复后再发起账号发现。

调用前必须先完成平台键映射自检：每个目标平台都要能在**平台键映射**权威表中找到对应 `platformId`，实际发出的值只能取自该表。判定必须以该表为准，不得凭本节上下文里的零散举例反推，否则会误拦表中已登记的合法平台。部分平台两侧不同名（如抖店计划键 `doudian`、账号管理键 `dy`），未完成映射就调用会查询到账号管理不接受的键。映射不成立时不得发起查询，直接说明该平台不在广告分析支持范围并停止。发起查询后必须记录本次实际发出的 `platformIdList` 原值，供后续判定与向用户说明时引用，不得凭平台中文名反推。

**第 2 步：逐平台店铺范围消歧（确定性判定，只按已登录候选计数）**。`../multi-platform-intention-router/references/common/store-scope-contract.md` §5 是事实源，下表是其在广告链路的展开；先统计该平台有效候选数 `N_all`，再统计其中 `enable=true` 的已登录候选数 `N_on`，消歧只看 `N_on`：

账号发现响应的字段处理以 `../discover-store-accounts/SKILL.md` “返回结构”为唯一事实源。`discover_store_accounts` 成功返回后必须先读取并执行该规则，后续店铺范围只根据 `accounts[]` 判定。

| 情形 | 动作 |
|---|---|
| `accounts=[]` | 按 `../discover-store-accounts/SKILL.md` “返回结构”的空账号规则处理并停止。 |
| `accounts` 非空且 `N_all=0` | 该平台无候选，在开工播报里说明后自动跳过该平台（可提示到“设置 - 账号管理”（[点击前往账号管理](accio://settings/account-management)｜[账号登录使用教程](https://acciowork.yuque.com/rfmg8t/ieb85b/achx4dk5s999qoa4#WGzMZ)）新增登录），其余平台继续，**不打断** |
| `N_all≥1` 且 `N_on=0` | 该平台候选全部未登录，列出被跳过的“`platformName / storeName（脱敏 account）`”后整平台自动跳过，其余平台继续，**不打断** |
| `N_on=1` | 直接锁定，选中账号由开工播报列出后继续，不打断；同平台未登录候选列为“已跳过（未登录）” |
| `N_on≥2` 且用户已唯一指定（店铺名精确命中一条，或明确说“全部店铺/所有店铺”） | 按用户指定锁定（“全部”→该平台全部已登录候选），不打断 |
| `N_on≥2` 且用户**未**唯一指定（只说“天猫”“淘宝”等平台名） | **必须** `ask_user(mode="form")` 列出该平台**已登录**候选“`platformName / storeName（脱敏 account）`”让用户选择（单选/多选，含「全部店铺」选项，未登录项不作为选项）；用户选择前不创建运行目录、不启动任何 RPA |

多个歧义平台可在同一次 `ask_user(mode="form")` 内以多题一并消歧。`<active_store>`、历史店铺、上一轮选择一律不算用户已指定；平台级全选同样需要确认。用户点名指定的店铺恰好未登录时，只跳过该目标并注明未登录，**禁止**静默换成同平台其它已登录店铺。

当 `accounts` 非空时，账号相关的跳过或停止只区分两种原因：**无账号**（`N_all=0`）和**未登录**（`N_all≥1` 且 `N_on=0`，或目标记录 `enable=false`），不得互相替代或合并原因。`accounts=[]` 时必须按上表空账号分支处理。

**第 3 步：`enable` 登录门禁与图文引导（硬门禁）**。消歧锁定后读取目标记录的 `enable`：全部 `true` 直接继续；**混合状态自动跳过未登录目标、只跑已登录目标，不打断、不追问**，“本次执行”与“已跳过（未登录）”的“`platformName / storeName（脱敏 account）`”作为第 5 步开工播报的字段输出，并在最终报告按同一口径逐条注明登录缺口。**强制触发引导**：若目标平台在发现中无任何账号（`N_all=0`），或选中的账号全部为 `enable=false`，必须停止业务流程并**立即读取 `../discover-store-accounts/references/merchant-account-management.md`**，按其中的指引完整回复用户（包括账号管理地址和图片引导，不可丢失）。**禁止**仅以文字链接或口头提示代替图文教程，也禁止为登录状态调用 `ask_user`。

**第 4 步：写入计划**。每个锁定目标保留同一条发现记录的 `storeId + storeAccountId`（`plan.v3` 两者均必填且必须同源）写入等价 `plan.v3`；完整 `accounts[]` 留在本轮上下文，供步骤 3 登录态门禁按 `storeAccountId` 恢复。

**第 5 步：开工播报**。计划写入后（平台、店铺、周期均已确定）、进入步骤 1 之前，按 `../multi-platform-intention-router/references/common/kickoff-briefing-contract.md` 播报**恰好一次**后同一轮直接继续（字段口径见本文「开工播报」硬规则）；未播报就编译 Execution 请求视为流程未完成。

本步骤与步骤 3 的 Execution 登录态门禁各自调用一次 `discover_store_accounts`：本步骤用于店铺消歧，步骤 3 用于执行前登录态校验；不得合并成一次，也不得在同一阶段重复调用。

### 2. 编译 Execution New 请求

在线采集计划执行本步骤；全部店铺均为 `inputMode=offline` 的拼多多或京东附件计划必须使用 `custom` 起止日期，跳过步骤 2 和 3，按原计划的 batch/store 序号把原始工作簿放入 `<run-dir>/execution/<requestId>/raw_data/` 后直接进入步骤 4。在线与离线店铺不得混在同一计划中，也不得把离线店铺放入 Execution 请求，否则会改变确定性 `requestId` 映射。

编译前先确定每个店铺的观测周期。用户只说“分析广告”而没有给周期时，按默认近 7 天（`end` = Asia/Shanghai 昨天）填充绝对 `start/end`（该周期已在步骤 0 第 5 步的开工播报里告知用户），不得追问、不得阻塞；页面默认周期仍只允许作为 RPA 日期控件不可用后的最后采集降级。

```bash
python3 scripts/build_collection_requests.py \
  --plan /absolute/path/to/plan.json \
  --run-dir /absolute/path/to/data/ads-analysis-<timestamp>
```

读取 stdout 中的 `out`，把该唯一 `batch-request.json` 交给 `multi-platform-rpa-execution-new`。适配器必须保留 Router batch 边界，只输出 `schemaVersion / batches / dsls / accountDiscovery / taskRequirement / run_dir / maxConcurrency`。`taskRequirement` 必须把本轮每个广告 DSL 精确分为 required/optional。请求编译时同时校验 DSL 选择白名单、采集页面白名单和任务必选性策略；投放管理、充值、授权或配置页面不能成为广告 DSL 入口。

#### 各平台并发上限

`maxConcurrency` 由脚本按采集平台自动写入，调用方不要手工指定。取值与逐平台判定依据
来自 `references/collection-concurrency-policy.json`，该配置是唯一真源；下表是它的
摘要，两者不一致时以配置文件为准。

| 采集平台 | 同时执行任务数 | 能否并行 | 判定依据 |
|---|---:|---|---|
| `taobao`（含天猫） | 6 | 并行 | 五张报表各有独立 URL（account / item_promotion / campaign / crowd / bidword），任务间不共享页面状态；下载文件名带本任务专属的 13 位毫秒时间戳，后处理按「报表前缀 + 该时间戳」校验归属，并发下不会认领他人文件 |
| `pdd` | 6 | 并行 | 六个任务分布在商品 / 直播 / 明星店铺三个 overView 页；周期由 URL 的 `beginDate/endDate` 绑定而非页面点选，落盘时按任务角色重命名，同页的汇总与分天互不覆盖 |
| `jd` | 1 | 串行 | 十个任务全部指向同一个 `advert-summary` 页，靠页内点击「非全站/全站营销」「核心指标/数据明细」「SKU 分析/SPU 数据明细」切换口径，并发会互相改写筛选状态；其中六个路由文件名匹配为空，只能按 `--page-id` 归因，同名文件同时落盘无法区分归属 |
| `doudian` | 1 | 串行 | 六个千川任务共用同一入口，与京东同类问题 |
| `1688` | 1 | 串行 | 四个 p4p 渠道共用 `pageId=100391` 单页 SPA，仅靠 `type` 参数切换；页面带 `krumpNotRefresh=true`，切 type 不重新渲染，DSL 须在 goto 后强制 reload，并发会互相打断 reload。下载按钮无稳定标识，只能按容器内相对位置定位，页面被切走后同一定位会点到别的控件；四任务共八个下载事件争抢同一浏览器，归属错位风险高于已放开并行的 taobao / pdd |

天猫不是独立采集平台，映射到 `taobao` 后共用同一取值。

**没有「未登记平台自动串行」的兜底。** 策略文件必须为每个采集平台各登记一条，键集合与
代码里的 `COLLECTION_PLATFORMS` 完全相等，缺一条或多一条都在构建阶段直接失败。新增平台的
正确姿势是：先核实报表页结构，再同时更新 `COLLECTION_PLATFORMS` 与
`references/collection-concurrency-policy.json`，并把判定依据写进 `reason`。
不要指望漏登记只是「慢一点」——它是硬失败。

并发上限不是性能旋钮，而是由报表页结构决定的事实。放开某个平台前，必须先确认它同时满足
两个条件：各报表有独立 URL 或独立周期参数（任务间不共享页面状态），且下载文件可按任务
唯一归因（文件名带任务专属标识，或落盘时按角色重命名）。

### 3. 等待 Execution New 完成

完整执行新版 Execution 的 Assemble、登录、单 DSL 滚动并发、结果记录和后处理。不得在 Execution 完成前生成广告结论。

每个广告原子任务都必须在自己的页面实例中重新尝试日期，且 Adapter 必须把 Router 已确认的绝对 `start/end` 原样传给 Execution。日期动作发生在读取或下载之前，按快捷周期、已有 URL 日期能力、精确日期组件、页面默认周期依次降级；不得继承上一任务状态或臆造 URL 查询参数。周期漂移、日期控件变化和默认周期不会单独阻断下载，但必须在计划、文件名或源报表周期证据中留下偏差，供后续把数据标记为周期未验证。

平台、店铺和报表 lane 只是当前主 Agent 管理的执行队列，不是 Agent 或会话边界。整个 Execution 必须保持在当前主 Agent 和本次 `<run-dir>` 内；禁止为任一 lane 派生子 Agent。即使同批发起多个 `functions.browser_rpa_run` 调用，所有返回事件也必须由当前主 Agent 汇总，并在任一全局停止条件触发后阻止其他 lane 继续启动、后处理或交付。

`build_collection_requests.py` 生成的 `batch-request.json.accountDiscovery.platformIdList` 必须只包含当前广告计划相关店铺的平台 ID。Execution 将其原样复制到 `dsl-run-plan.json`，本次运行验证登录态时再原样调用 `discover_store_accounts({"platformIdList":[...]})`；字段缺失、为空、包含其他平台，或账号发现返回范围外记录时，必须在浏览器启动前停止。

Execution 返回任何 `permission_denied:<页面报错原文>` 时，直接向用户回复该页面报错原文和“请先解决平台访问权限后再重新运行广告分析”，然后结束本次任务。不得进入步骤 4，也不得交付旧文件或空报告。

Execution 写出 `<run-dir>/rpa-post-process-result.json` 后，必须在进入步骤 4 前执行广告分析自己的全平台采集门禁：

```bash
python3 scripts/evaluate_collection_result.py \
  --post-process-result /absolute/path/to/data/ads-analysis-<timestamp>/rpa-post-process-result.json
```

读取 stdout 的 `status/out/canContinueToFinalizer/ignoreExecutionUserDecision`，并读取 `out` 指向的完整审计 JSON：

- `ready`：正常进入步骤 4。
- `ready_with_optional_gaps`：本轮全部最终失败项都属于策略文件中的可选报表；Execution 应已输出 `userDecision.required=false`，直接按 `skippedOptionalFailures` 跳过并进入步骤 4。跳过信息只进入运行日志和最终回复的简短数据范围说明，不写入 HTML 页面，不把缺失值补 0。
- `required_report_failed`：`requiredFailures` 对应店铺不得进入 Converter 或报告生成；`canContinueToFinalizer=true` 时仍继续处理其他成功店铺并按 partial 交付，`false` 时停止报告阶段。不得选择“忽略并继续”绕过营销场景报表门禁。
- `requires_user_decision`：失败项包含未被策略分类的任务，说明 `collection-requirement-policy.json` 存在策略漂移（多为新增 DSL 未分类），不是业务数据问题。按必选缺口处理受影响店铺（写入 `blockedRequestIds`）：`canContinueToFinalizer=true` 时继续处理其余成功店铺并按 partial 交付，`false` 时停止报告阶段；两种情况都必须在最终回复中点名未被分类的 DSL 供后续补策略，**不得**向用户索要重试/上传/忽略选择，也不得用可选策略覆盖必选门禁。
- `permission_denied`：按页面权限门禁立即停止整个任务，并逐字转述 `message`。
- 脚本返回业务阻断码时按同一份审计 JSON 的 `status` 处理；未生成合法审计 JSON、策略漂移或其他契约异常时失败即停，不得凭任务名称手工判断核心/可选属性。多店铺运行中只要仍有 `reportableRequestIds`，核心失败店铺写入 `blockedRequestIds`，成功店铺继续进入步骤 4。

每个店铺的输入必须来自：

```text
<run-dir>/execution/<requestId>/raw_data/
```

不得改用运行级 `raw_data/` 或其他店铺目录。

### 4. 逐店准备 AI 分析上下文

```bash
python3 scripts/finalize_reports.py \
  --plan /absolute/path/to/plan.json \
  --run-dir /absolute/path/to/data/ads-analysis-<timestamp> \
  --plugin-root /absolute/path/to/current-agent-workspace \
  --prepare-ai
```

脚本按 Router batch/store 顺序映射 Execution `requestId`，逐店执行：

1. 按平台识别输入。淘宝/天猫识别唯一必选营销场景及成功的可选下钻报表；拼多多识别必选商品推广汇总及成功的分天、直播、明星店铺报表；京东识别必选非全站/全站核心汇总及成功的分天和维度导出；抖店识别必选推商品商品及成功的账户、计划、素材、直播维度。详细规则见各平台 Converter 契约。
2. 淘宝/天猫使用 `scripts/report/converter/convert_ads_exports.py`，拼多多使用 `convert_pdd_ads_exports.py`，京东使用 `convert_jd_ads_exports.py`，抖店使用 `convert_doudian_ads_exports.py`。转换器输出公共总体/渠道/计划/日期/商品事实，同时把不能安全压平的人群、关键词、京东分域、抖店抖音号以及净额/补贴等保留为平台专项投影；平行投影禁止进入总体重复加总。
3. 从转换后的“场景结案数据”提取总体推广、费用结构和渠道效率指标；多个转化周期不能相加，使用覆盖时间最长的汇总行。
4. 若源文件包含计划名称与投放指标，按广告类型聚合，并保留每个投放计划的花费、总成交金额、展现量、点击量、成交笔数和 ROI；跨行 ROI 必须从计划合计总成交金额与花费重算。只有渠道字段而没有计划身份时，保留渠道聚合并标记为渠道粒度。
5. 若源文件包含真实日期字段，必须同时保留总体日趋势和可用的“日期 × 渠道场景”下钻：按渠道分别聚合花费、总成交金额、展现量、点击量和总成交笔数，并在各渠道各日重算 ROI、CTR、CVR、CPC；不同渠道场景在 02 店铺总览中使用不同折线。缺少渠道日明细时只能明确降级为总体日趋势，不得复制总体值、补 0 或模拟渠道折线。
6. 只有提供商品文件或营销工作簿中存在真实商品 Sheet 时才输出商品模块；提取商品级展现量、点击量、推广花费、总成交金额（退款前/后）、支付转化率、ROI、退款后费比、CPC/CPM、成交买家、加购和收藏明细，不得用汇总数据补造。
7. 区分报告数据状态 `ok / partial / no_data` 和字段级缺失状态。
8. 生成 `ads_metrics.json`、`canonical_ads_model.json` 和 `report_capabilities.json`。统一模型必须保留 Scope、实体、关系质量、事实、平台扩展、来源证据和质量状态；能力清单按真实数据把 02-05 标记为 `ready/partial/not_applicable/blocked`。v2 AI 和渲染器必须复用同一能力清单，旧 metrics 才允许兼容回退。
9. 生成不包含脚本问题标签的 `ai_analysis_context.json`；上下文为每项事实分配稳定 `evidenceCatalog[].id`，并携带同一份 `reportCapabilities`。
10. 对总体汇总与商品合计的花费、交易额、订单、曝光、点击做跨表对账；任一可比指标偏差超过 10% 时标记低置信度并禁止业务加投/减投动作。不可比时标记中置信度，不得假装已核对。
11. 若计划提供 `businessEvents`，按事件日前 3 个可用日期与事件日起后 3 个可用日期生成分段事实；若提供 `profitability.contributionMarginRate` 或 `breakEvenRoas`，生成可审计的盈亏平衡判断。未提供时只能回答广告归因回报，不能宣称经营利润。
12. 当源表只有渠道汇总或没有日期字段时，在上下文和报告数据检查中提前披露，禁止计划级动作或趋势结论。
13. stdout 返回逐店 `analysisRequests[]`，其中包含 `context/contextId/responseTarget` 以及统一模型和能力清单路径。

### 5. Agent 生成问题识别、洞察和行动建议

对每个 `analysisRequests[]`：

1. 完整读取 `context`，只使用其中的事实和证据目录；不得读取旧洞察或调用 `build_insight.py`。
2. 按 `analysis-playbook.md` 和 `ai-insight-protocol.md` 独立判断问题、机会、替代解释和行动优先级。
3. 先按经营影响、证据强度和可行动性从全量事实中筛出 1-3 个核心结论，每个结论只保留 1-3 条不重复的支撑。
4. 对 `requiredModuleInsights` 中每个实际渲染章节，严格在对应 `sectionFactPacks` 范围内生成 `conclusions/evidence/actions`，三组各 1-3 条；行动优先点名真实渠道、计划或商品，并写清验证和回调条件。`actions[].title` 必须是结论性动作，句式为「动作 + 迁出对象 + 迁入对象」（如“暂停 A 商品投放，预算转投 B 商品”），40 字以内不含数据；**禁止用排查/核算/核对/对照/梳理/评估/关注/下钻等动词把判断甩回给用户**——数据推不出方向时也要先给默认动作再附条件；`actions[].content` 只写佐证数字（如“ROI 1.80，全店最低”），25 字以内且必须含数字——无数字的条目会被行动清单当作空话剔除。详见 `references/report/ai-insight-protocol.md`。
5. 每条支撑、章节结论、依据和行动必须引用合法 `evidenceRefs`；商品结论还必须引用同一商品证据。
6. 使用结构化 JSON 写入该请求唯一的 `responseTarget`。不得修改 metrics、context 或原始 Excel。

### 6. 校验 AI 洞察、渲染并交付

```bash
python3 scripts/finalize_reports.py \
  --plan /absolute/path/to/plan.json \
  --run-dir /absolute/path/to/data/ads-analysis-<timestamp> \
  --plugin-root /absolute/path/to/current-agent-workspace \
  --complete-ai
```

完成阶段逐店校验 `contextId`、证据引用、章节事实范围、条目上限、商品身份、周期门禁、跨表 10% 门禁、置信度和零数据门禁，再编译 `insight.v3`、渲染 HTML，并将该店 `raw_data/` 中全部 `.xlsx` 的全部 Sheet 合并为一个业务化命名的汇总 Excel。汇总本增加“数据目录”并保留每个来源 Sheet 的独立投影；它复制已计算的单元格值和数字格式，不跨表聚合，不作为 Converter 输入。原始 Excel 仍由共享交付契约逐字节保留，以追溯公式、图表、批注和平台样式。低置信度响应不得包含业务动作，核心结论必须明确暂不调投。离线检查时可加 `--skip-delivery`；正式任务不得跳过交付。

### 用户交付回复

- `finalize_reports.py` 成功后必须读取 stdout 的 `deliverables`，并逐项确认 `htmlPath` 是现存的绝对 `.html` 文件路径、`excelPath` 是现存的绝对 `.xlsx` 文件路径、`directory` 是现存的绝对目录路径。未完成这一步不得宣称报告已交付。
- 最终回复必须按店铺逐项同时展示 HTML 的可点击链接和未经省略的绝对路径，两者缺一不可。固定格式为：`报告：[打开 HTML 报告](</absolute/path/report.html>)` 和 `HTML 路径：/absolute/path/report.html`。必须直接复用同一项 `htmlMarkdownLink` 和 `htmlPath`，不得手工猜测、缩写路径或只把路径藏在 Markdown 链接目标中。
- 最终回复必须紧接着展示汇总 Excel 的可点击链接和未经省略的绝对路径。固定格式为：`数据汇总：[打开数据汇总 Excel](</absolute/path/summary.xlsx>)` 和 `Excel 路径：/absolute/path/summary.xlsx`。必须直接复用同一项 `excelMarkdownLink` 和 `excelPath`。汇总本是便利查阅副本，原始下载附件继续保留在目录的 `assets/` 中。
- 最终回复还必须提供报告目录链接：`目录：[打开报告文件夹](</absolute/path/directory>)`，直接复用 `directoryMarkdownLink`。不得只给文件名、相对路径、摘要 JSON、终端命令或“报告已生成”等文字描述。
- HTML 链接用于直接在浏览器打开报告；Excel 链接用于打开全部来源 Sheet 的汇总数据；目录链接用于在文件管理器定位报告、汇总本及原始 `assets/`。可以额外提供本地 HTTP 预览地址，但不能替代这三个本地链接。
- 多店铺任务必须逐店交付 HTML 链接、HTML 绝对路径、汇总 Excel 链接、Excel 绝对路径和目录链接，不得只展示第一份。`partial/no_data` 只影响报告内容，不免除上述交付要求。
- 多店铺收口返回 `status=partial` 时，仍须交付全部成功店铺，并逐项说明 `failureDetails` 中的失败店铺；不得因单店失败隐藏成功报告，也不得对确定性的格式/口径错误盲目重试。
- 同一生成分钟内重跑不会覆盖历史目录，共享交付层会追加 `_v2/_v3`。最终回复只使用本次 stdout `deliverables` 返回的路径，不得扫描目录猜测“最新”报告。
- 写最终回复之前必须先调用一次 `present_files` 展示本次报告产物。文字里的链接和绝对路径只解决“能不能点开”，附件卡片是另一条独立通道：不调用 `present_files`，用户侧就只有一段带链接的文字、没有可直接打开的产物卡片。实测存在 HTML 已落盘、回复也带了链接，但因为没调用该工具而始终没有附件卡片的情况，此时不算完成交付。
- `present_files` 的 `files` 直接取自 `finalize_reports.py` stdout 的 `presentFiles` 数组，逐项复用其中的 `path` 与 `label`（形如 `{"path": "/abs/report.html", "label": "分析报告 · report.html"}`），不得自行拼接路径、改写标签或只挑其中一项。多店铺任务必须把每家店铺的产物合并进同一次调用，不得逐店多次调用或只展示第一家。
- 调用顺序固定为：先 `present_files`，拿到返回后再输出最终回复文字。`present_files` 只负责展示产物，不替代上面的 HTML 链接、HTML 绝对路径、Excel 链接、Excel 绝对路径和目录链接，两者必须同时具备。

### 零数据协议

平台核心采集门禁已通过，但核心源文件只有有效表头、明确无数据或有效指标全部缺失时：

1. 仍必须执行 `--prepare-ai`、生成一个明确说明“本期没有足够数据形成广告判断”的合法核心结论，再调用 `--complete-ai`。成功生成空状态报告时任务级 `status=ok`、`dataStatus=no_data`，单店 `quality=no_data`；`no_data` 不是执行失败状态。核心报表下载失败、文件缺失或文件归属校验失败不属于 `no_data`，必须按平台核心门禁阻断受影响店铺。
2. 不得绕过脚本手动生成 HTML 或文本形式的"空报告"，也不得用 Mock 数据替代。
3. `no_data` 报告只保留 01 核心结论，用 1 个结论卡明确“本期没有足够数据形成广告判断”并说明关键缺口；02-05 按数据不可用规则不渲染，也不单独渲染指标口径模块。
4. 不得在 `no_data` 状态下生成预算、渠道或投放调整建议。

## 经营判断纪律

- `no_data` 只表示源报表无数据，不表示店铺零投放；不得生成预算或渠道动作。
- 只有源报表明确给出无数据标记时才使用 `no_data`；只有表头但没有数据行时使用 `partial`。
- 报告展示 Execution `dsl-run-plan.json` 推导的请求周期，并与 Router 日期对照；日趋势首末日只表示有活动的数据范围，只要全部日期落在请求周期内就不因首尾无投放而降级。存在请求范围外日期时标记不一致；源报表没有独立日期字段时必须标记“源报表未验证”，不得写成实际应用周期。
- 日期选择与页面生效校验必须先于读取/下载并按统一优先级降级；日期操作全部失败时允许保留本次页面默认周期文件。源报表周期未验证或与请求周期不一致时，只输出文件中的汇总事实和数据核对项，不生成投放调整动作，也不得展示为请求周期。
- 花费字段真实为 0 时，只建议核对计划状态、报表时间和转化周期，不直接建议增加预算。
- 不使用跨类目的固定 ROI、费比、预算或转化率阈值判断投放好坏。
- 汇总数据只能支持总体事实；预算、渠道、计划或商品调整必须要求对应明细数据。
- 商品状态只使用“有成交记录 / 有消耗无成交 / 有展现无点击 / 未产生展现 / 数据不足”等事实标签，不使用跨类目固定阈值输出“严重”或“优秀”。
- 商品明细未提供时，HTML 不输出商品导航和商品章节，洞察不得生成补商品表的提示；已提供但为空时保留商品章节并显示空状态。
- 商品明细未提供日期字段时不得拼接或模拟日趋势；只展示商品摘要、事实观察和明细表，不输出商品消耗或展现排行。
- 同时存在退款前、退款后成交金额字段时必须分别保留；源字段可名为“支付金额”，但用户可见标签统一为“总成交金额”。ROAS 派生优先使用退款后总成交金额，并显示具体来源字段或公式。
- 商品合计只汇总所有商品均有有效值的可加指标；CTR、CPC、CPM、支付转化率、ROI 和费比必须从合计依赖重新计算，任一依赖缺失时显示缺失。
- 环比只使用等长上一周期的源值或平台直接提供的环比字段；统一按 `(本期值 - 上期值) / |上期值|` 计算，上期为 0 时显示不可计算。CTR、CPC、CPM、CVR、成交成本和 ROI 的上期值必须先由上期基础事实重算，禁止平均行级环比。
- 02/03 的折叠投放明细表共用同一粒度选择：存在有效计划身份时按“渠道 + 投放计划”展示，否则按渠道聚合展示；同一计划存在多日或多行时，花费、总成交金额、展现量、点击量和成交笔数求和，ROI 从合计总成交金额除以合计花费重算。每个可用指标同时展示当前值和环比，悬停可查看上期绝对值。
- 数据总览固定按“花费、总成交金额、展现量、点击量、总成交笔数、投产比 ROI”的顺序展示六项核心指标；每项提供口径提示。
- 02 店铺总览按指标页签展示渠道效率趋势。每个渠道场景使用独立细折线和稳定图例颜色；图例必须支持点击反选，点击后隐藏或恢复该渠道的折线、数据点和极端值标注，并通过 `aria-pressed` 暴露当前状态，悬停或聚焦图例时只强调对应序列。某渠道某日缺失时折线断开，不补 0。日期数或序列数增加时必须保留完整折线路径，只降低非关键圆点的常驻可见度、减少轴标签和辅助网格，不得通过抽样或平滑改写走势。只有总体日趋势时标题必须改为“总体效率趋势”并披露缺少日期 × 渠道场景明细，禁止把总体单线标成“分渠道”。
- 总览与 02 的口径问号浮层必须按视口剩余空间自动选择向左、居中或向右展开，任何屏幕宽度下不得横向溢出；鼠标进入浮层后使用文本光标并允许选择文字，不继续显示问号帮助光标。键盘聚焦、点击打开、Esc 关闭能力必须保留。
- 03 预算错配图的数据源必须是商品维度报表，不得使用渠道汇总或计划汇总替代。只纳入同时具备商品级花费、交易额和 ROI 的商品，并在该可比集合内重新计算花费份额和交易额份额；拼多多全店托管等没有商品 ROI 的记录必须排除并显示排除说明，不得把场景数据分摊到商品。只要存在至少 1 个可核算商品就渲染，不要求全店所有商品都有 ROI；单商品时必须说明份额均为 100%、错配度为 0 仅表示可核算范围，不支持商品间错配判断。错配度只是事实，是否构成问题由 AI 判断。
- 04 商品四象限散点图固定使用横轴=投入金额（花费）、纵轴=投产比 ROI；每个散点代表一个商品。横轴最左侧和纵轴最下侧均从 0 开始，负坐标点不展示；象限分割线使用商品集合中位数并固定在画布正中，不使用跨类目固定阈值或背景辅助网格。40 个以内的可比商品必须直接随卡片宽度完整展示，不设置强制最小宽度或横向滚动；超过 40 个商品后才允许按点数有限扩宽并在图表内部滚动。全部商品气泡使用即时出现的自定义 tooltip 展示完整商品名和核心值，tooltip 跟随鼠标、自动避让边界、支持键盘聚焦，不得依赖 SVG 原生 `<title>`。常驻标签只保留店内相对高 GMV 商品，以及 ROI 位于店内高/低尾部且花费达到店内中位数的商品，最多展示少量重点标签；其他商品默认不展示名称。常驻标签不得使用引导线。
- 04 使用与四象限重点标签一致的候选规则，筛选 ROI 上/下 15% 尾部且花费不低于可比商品中位数的商品。优先从本轮人群、关键词及其他下钻源报表提取可直接关联商品的投放人群、投放关键词、匹配方式、定向方式、资源位、创意、地域和投放单元等特征；只有明确商品 ID 或唯一商品名时才允许关联，禁止用计划名、泛化“主体ID/主体名称”或文本相似度猜商品。
- 04 仅当高/低 ROI 候选都存在、候选集合至少覆盖 2 类真实投放特征、至少 60% 候选商品各具备不少于 2 类特征，且两组各至少有 1 个丰富样本时，展示“高ROI品特征”和“低ROI品特征”两张逐商品表。任一门槛不满足时不得展示稀疏特征表，也不得回退生成典型商品漏斗；特征缺失不得按无投放或空字符串推断。
- 核心趋势只使用日期维度原始行；优先选择明确标注”日趋势/每日”的数据表，多个候选表不得重复相加。渠道折线必须来自同一日期表中的真实渠道/场景字段，计划名称不能冒充渠道。
- HTML 只展示业务指标、对比、观察和行动，不展示输入文件名、Sheet、表头行、转换路径、字段映射、周期核验状态、质量状态或数据缺口提示。缺失指标和无法成立的图表直接省略；内部 JSON、manifest 和日志继续完整保留来源及缺失状态。
- “访客数”只使用源表明确的去重访客字段；广告点击次数不得改名为访客数。只有点击字段时，漏斗使用“曝光 → 推广点击 → 成交”，并明确点击不是去重用户。
- “动销率”只在分母确为全店在售商品数时成立。广告商品报表只能计算“推广商品成交覆盖率 = 有成交推广商品数 / 报表内推广商品数”，不得包装成全店动销率。
- 模块 01 只展示 AI 排序后的 1-3 个核心结论及其支撑；详细行动分别留在 02-05 的章末收口。不得增加、删除或重排 v2 五模块主结构。
