# 专利文档生成

## 读取配置（自动生成，请勿删除）

执行任何动作前，读 `~/.qoderwork/plugins/config/pm-output-engine/QODERWORK.md`。
- 文件不存在或仍含 `[PLACEHOLDER]` → 停下来，回复用户运行 `/pm-output-engine:onboarding`，不要继续。
- 本 skill 会用到配置里的：## 输出风格（专利文档格式偏好、字体要求、存放位置）。
- 配置没覆盖到的字段：使用默认值 → 把默认值写回 QODERWORK.md → 继续。

## 触发条件

当用户说以下类似的话时触发：
- "帮我写专利文档"
- "这个需求可以申请专利吗"
- "帮我从 PRD 提炼创新点"
- "生成实用新型专利申请"
- "这个功能写个专利交底书"
- "帮我把这个方案整理成专利"

## 完整执行流程

### Step 1：理解需求来源

**信息来源分两条路径，必须先判断走哪条：**

**路径 A — 用户提供了 PRD 文件（PDF / Markdown / Word / 链接）：**
1. 读取 PRD 全文
2. 提取以下关键信息：
   - 产品功能描述（做了什么）
   - 用户场景和痛点（解决什么问题）
   - 技术方案或架构描述（怎么做的）
   - 与现有方案的差异点（比之前好在哪）
3. 标注 PRD 中信息不足的部分，用 AskUserQuestion 追问

**路径 B — 用户口头描述创新点：**

用 AskUserQuestion 收集以下信息：

```
问题1: 你的创新方案解决了什么问题？（现有方案有什么不好？）
选项: [根据上下文推断 2-3 个方向] + Other

问题2: 你的方案核心技术手段是什么？（用一两句话描述怎么实现的）
选项: [根据上下文推断 2-3 个方向] + Other

问题3: 市面上有类似的产品或方案吗？（竞品是谁？）
选项: [根据领域推断 2-3 个竞品] + Other
```

### Step 2：提炼核心技术创新点

从 Step 1 的信息中，识别 **1-3 个核心技术创新点**：

**提炼原则：**
- 创新点必须用**技术化语言**描述，不能写成产品需求语言
  - 错误示范：用户可以通过语音快速搜索商品
  - 正确示范：一种基于语音特征提取与语义向量匹配的多模态商品检索方法
- 每个创新点要回答三个问题：
  1. **做了什么**（技术手段）— 用了什么方法/算法/架构
  2. **怎么做的**（实现路径）— 关键步骤是什么
  3. **效果是什么**（技术效果）— 比现有方案在哪些技术指标上有提升
- 创新点之间要有层次区分：
  - 主创新点：整体方案的核心方法
  - 辅助创新点：关键子模块或优化策略

**创新点质量检查（必须全部通过）：**
1. 是否用了技术化语言（非产品需求语言）
2. 是否可被本领域技术人员理解和复现
3. 是否与现有方案有明确的技术差异
4. 是否有可量化的技术效果

### Step 3：生成专利文档

按以下固定模板结构生成完整专利文档（详见 [专利文档模板](references/patent-template.md)）：

---

#### 申请说明（不超过 300 字）

简要说明本发明要解决的技术问题、采用的核心技术手段、以及主要技术效果。
三段式结构：
1. 本发明针对……问题（问题陈述，1-2 句）
2. 提出了一种……方法/系统/装置（技术手段，2-3 句）
3. 实现了……效果（技术效果，1-2 句）

#### 关键词（3-8 个）

用顿号分隔，覆盖核心技术术语。示例：
`语音识别、语义向量、多模态检索、特征提取、相似度匹配`

#### 0 术语定义

对文档中使用的专业术语进行定义，格式：
```
【术语】：定义说明
```

至少包含 3 个术语，覆盖：
- 核心技术概念（如"语义向量"）
- 领域专有名词（如"多模态"）
- 关键缩写的全称（如"ASR（自动语音识别）"）

#### 1 产品概述

2-3 段话，说明：
- 本发明所属的技术领域
- 产品的整体定位和核心功能
- 本发明在产品中的具体应用场景

#### 2 技术背景

3-4 段话，说明：
- 该技术领域的现状和发展趋势
- 现有技术方案的主流做法
- 现有方案存在的技术缺陷或不足（为本发明做铺垫）

#### 3 竞争对手分析

**必须具体到公司名和产品名**，不能泛泛而谈。

格式：
```markdown
| 公司 | 产品/方案 | 技术路线 | 与本方案差异 |
|------|----------|---------|-------------|
| XX公司 | XX产品 | 采用XX技术实现XX功能 | 缺少XX环节 / 未解决XX问题 |
```

至少列出 2-3 个竞品，每个竞品需说明：
- 公司名称和产品名称
- 其采用的技术路线
- 与本方案的关键技术差异

如果用户无法提供竞品信息，应主动搜索该领域的公开资料来补充。

#### 5 相似方案及缺点

详述现有技术方案（至少 2 种），每种方案需说明：
1. 方案描述：现有技术是怎么做的
2. 技术缺陷：存在什么具体问题（性能、精度、效率、成本等）
3. 缺陷原因：为什么会有这些缺陷（技术根因分析）

**注意：** 这里的描述要为后续 6.1 详述做铺垫——本发明正是为了解决这些缺陷。

#### 6.1 详述（核心章节）

这是专利文档最重要的部分，必须包含：

**a) 整体架构描述：**
```
系统包含以下模块：
- 模块A：负责……
- 模块B：负责……
- 模块C：负责……
各模块之间的数据流向为：A → B → C
```

**b) 关键步骤流程（必须可执行）：**

用编号步骤描述核心方法的执行流程：
```
步骤1：接收用户输入的……
步骤2：对输入数据进行……处理，具体包括：
  步骤2.1：……
  步骤2.2：……
步骤3：根据步骤2的结果，执行……
步骤4：输出……
```

**c) 典型场景执行流程：**

选取 1-2 个典型应用场景，从头到尾走一遍完整流程：
```
场景：用户在XX情况下使用本系统
1. 用户发起……请求
2. 系统接收并……
3. 经过XX模块处理后……
4. 最终向用户展示……
```

**d) 关键算法或公式（如果涉及）：**

描述核心算法的输入、处理逻辑、输出。

#### 6.2 替代方案

至少提供 1 种替代实现方案，说明：
- 替代方案的技术路线
- 与主方案的差异
- 替代方案的优缺点

#### 6.3 克服缺点 + 技术效果

**必须以表格形式呈现：**

```markdown
| 现有方案缺点 | 本发明解决方式 | 技术效果 |
|-------------|--------------|---------|
| XX方案存在XX问题 | 本发明通过XX方法 | 提升了XX指标/降低了XX成本 |
```

每一行对应 5 相似方案中的一个缺点，形成闭环。

#### 7 关键技术创新点

列出 1-3 个创新点，每个创新点用技术化语言描述：

```markdown
创新点1：一种XX方法/装置/系统
- 技术手段：通过XX算法/架构/流程实现了XX功能
- 关键步骤：（1）……（2）……（3）……
- 技术效果：相比现有方案，XX指标提升了XX%/XX量级
```

### Step 4：输出文档

**分两步输出：**

**第一步：Markdown 预览**
- 将完整专利文档以 Markdown 格式输出到聊天窗口
- 让用户确认内容、提出修改意见

**第二步：生成 .docx 文件**
- 用户确认无误后，使用 docx skill 或 docx-js 生成 Word 文档
- 字体规范：
  - 标题（Heading 1/2/3）：SimHei（黑体）
  - 正文（Body）：SimSun（宋体），小四号（12pt）
  - 表格内容：SimSun，五号（10.5pt）
- 页面设置：A4 纸张，页边距上下 2.54cm、左右 3.18cm
- 文件名格式：`专利文档_[创新点关键词]_[日期].docx`

## 分支逻辑

- **用户提供了 PRD 文件** → 走路径 A，从文件提取信息，减少追问
- **用户口头描述创新点** → 走路径 B，用 AskUserQuestion 收集信息
- **用户说"这个能申请专利吗"** → 先做可行性判断（是否有技术创新点、是否与现有方案有差异），再决定是否生成文档
- **用户要求修改已有专利文档** → 读取原文档，按修改意见更新对应章节
- **用户提供多份 PRD** → 每份 PRD 单独生成一份专利文档，同一个 session 内可连续处理
- **用户只要创新点提炼** → 只执行 Step 1-2，输出创新点摘要，不生成完整文档

## 与其他技能的协作

- **需求文档撰写** → 专利文档生成：PRD 是专利文档的主要输入来源
- **竞品行业调研** → 专利文档生成：竞品分析结果可直接用于第 3 节竞争对手分析
- 专利文档生成 → **数据汇报文案**：专利技术效果数据可补充到产品汇报中

## 质量红线（不能犯）

1. **创新点必须用技术化语言** — 不能写成产品需求语言（"用户可以XX"），要写成技术方案（"一种基于XX的XX方法"）
2. **竞品分析必须具体** — 必须到公司名+产品名，不能写"市面上的一些产品"
3. **6.1 详述必须包含可执行步骤** — 不能只写概念描述，必须有编号步骤流程
4. **6.3 必须与第 5 节形成闭环** — 现有方案的每个缺点都要在 6.3 中有对应的解决方式
5. **申请说明不超过 300 字** — 超出需要精简
6. **关键词用顿号分隔** — 不是逗号、不是空格

## 陷阱与注意事项

1. **docx-js 生成含中文引号时的转义问题**：文档中出现中文引号（\u201C\u201D）时，必须使用 Unicode 转义 `\u201C` / `\u201D`，否则 docx-js 在某些环境下会输出乱码或报错。同理中文书名号用 `\u300A` / `\u300B`。
2. **创新点语言风格**：AI 产品经理容易把创新点写成 PRD 语言（"支持用户通过XX完成XX"），这是最常见的错误。专利的创新点必须是技术实现层面的描述（"采用XX算法对XX数据进行处理，通过XX步骤实现XX功能"）。
3. **竞品信息不可编造**：如果用户无法提供竞品信息，应明确告知并建议用户补充，或搜索公开资料。绝对不能编造公司名和产品名。
4. **6.1 详述的深度要求**：详述部分不能停留在概念层面（"系统对数据进行分析"），必须具体到可执行的步骤（"系统首先通过XX算法提取XX特征，然后使用XX模型进行XX分类"）。
5. **一个 session 可处理多份 PRD**：用户上传多份需求文档时，不要混淆不同 PRD 的内容。每份 PRD 独立处理，独立生成专利文档。建议在处理每份前明确告知用户"正在处理第 X 份 PRD"。
6. **替代方案不能是空话**：6.2 替代方案必须是一个真实可行的技术方案，不能写"本领域技术人员可以想到其他实现方式"之类的套话。
7. **术语定义不可省略**：即使术语看起来很常见，也要给出定义。专利文档面向审查员，术语定义有助于理解。
8. **docx 表格渲染**：生成 .docx 时，表格需要使用 docx-js 的 Table 对象，注意设置列宽比例和单元格内边距，避免表格在 Word 中显示异常。

## docx 生成技术要点

使用 docx skill 生成 .docx 文件时，注意以下技术细节：

```javascript
// 字体设置示例
const headingStyle = {
  font: "SimHei",    // 黑体
  size: 28,          // 小二号 = 18pt = 36 half-points（Heading 1）
  bold: true,
};

const bodyStyle = {
  font: "SimSun",    // 宋体
  size: 24,          // 小四号 = 12pt = 24 half-points
};

const tableStyle = {
  font: "SimSun",
  size: 21,          // 五号 = 10.5pt = 21 half-points
};

// 中文引号处理
const leftQuote = "\u201C";   // "
const rightQuote = "\u201D";  // "
```

**页面设置：**
- 纸张：A4（210mm x 297mm）
- 页边距：上下 2.54cm（1 inch），左右 3.18cm（1.25 inch）
- 行距：1.5 倍行距

**章节标题层级：**
- Heading 1：SimHei，小二号（18pt），加粗 — 用于大章节（1 产品概述、2 技术背景 等）
- Heading 2：SimHei，小三号（15pt），加粗 — 用于子章节（6.1 详述、6.2 替代方案 等）
- Heading 3：SimHei，四号（14pt），加粗 — 用于子子章节
- 正文：SimSun，小四号（12pt），常规
