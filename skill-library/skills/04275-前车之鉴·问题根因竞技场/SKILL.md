# 前车之鉴·问题根因竞技场

三角色认知对抗协议：三个角色**各自用不同方法独立分析同一问题 → 找出结论间的张力 → 交集=高可信结论，冲突=真实盲区**。这不是头脑风暴，是结构化的对抗验证。

## 什么时候启动

- 同一个问题反复出现，修了又坏
- 知道「是什么」但不知道「为什么」
- 团队对根因各执一词，争论不休
- 解决方案实施后效果短暂，问题很快复发
- 问题涉及多个部门或系统，边界不清

用户没明说但符合上述形态时，也应当启动本协议（在回答中直接采用其结构），并告知用户正在使用该思考协议。

## 竞技场协议（完整推理协议，按此结构作答）

你现在运行「问题根因认知竞技场」模式。三个角色从不同层次同时分析同一个问题，通过张力找到真正的根因和杠杆点。

【角色阵容】

角色A — 根因调查员（5 Whys）
立场：每个答案必须基于可观测事实，目标是找到系统/流程结构缺陷，而非某人失误。
推理协议：
1. 精确描述问题（时间/范围/影响），确保基于事实而非判断
2. 追问Why 1→N，每步标注证据来源，标注[待核实]的假设
3. 停止条件：当答案是「系统规则/流程设计本身允许了这件事发生」时停止
4. 反向验证：如果修复了X，同样问题还能再发生吗？
核心质疑：你的根因对应的对策是「叮嘱某人」还是「改变系统结构」？

角色B — 系统结构分析师（系统思维）
立场：反复出现的问题是系统结构造成的，必须找到反馈回路里的杠杆点。
推理协议：
1. 列出核心变量（存量/流量），5-8个
2. 画因果回路，识别正反馈（恶化/强化）和负反馈（自我调节）
3. 找延迟节点（哪个环节有时间差，会导致过度干预？）
4. 定位杠杆点：改变系统规则/信息流 > 改变反馈回路 > 调整参数
核心质疑：你的解决方案是改变了参数（治标）还是打断了回路（治本）？

角色C — 假设审计师（第一性原理）
立场：所有分析都建立在假设上。假设错了，找到的「根因」只是另一个症状。
推理协议：
1. 列出「问题分析」里所有默认正确的判断，逐条追问：这是事实还是假设？
2. 重点审查：问题的边界定义是否正确？这真的是「一个问题」还是「多个问题的叠加」？
3. 删除无根假设（✗），只保留可验证的基础事实（✓）
核心质疑：你对「问题是什么」的定义本身，是基于事实还是基于惯性？

【竞技场规则】

Phase 1 — 独立发言：三个角色各自给出根因分析，格式不同（因果链/回路图/假设清单）。

Phase 2 — 寻找张力：
- 5 Whys 的「流程缺陷」和系统思维的「回路节点」是否指向同一个位置？
- 假设审计师删掉假设后，问题边界是否改变？如果改变，根因定位需要重做。
- 三个角色的根因是否一致？不一致处是真正的盲区。

Phase 3 — 综合：
- 交集（三者都指向的节点）= 真正的杠杆点，优先级最高
- 冲突（只有一角色支持的节点）= 标注为「需补充证据的候选根因」
- 输出：①一句话根因陈述 ②系统杠杆点 ③反向验证（修复X后问题还能发生吗？）

【质量门禁】如果综合结论是「加强管理/提高重视/更努力」——这是参数调整，不是根因。继续找回路结构中的症结。

## 启动话术（对 Codex/DSH 类对话代理直接粘贴用）

> 请三个角色帮我找到这个问题的真正根因：

## 停止条件（防拖堂）

当①②③全部给出，且对策通过反向验证后停止。

综合输出必须落到决策性产物后即停，不再继续比较/分析本身。

## 三角色速览

- **根因调查员**（5 Whys）—— 立场：每个答案都必须基于可观测事实，目标是找到系统/流程结构上的缺陷，而不是某人失误。
- **系统结构分析师**（系统思维）—— 立场：任何反复出现的问题都是系统结构造成的。改变参数不够，必须找到反馈回路里的杠杆点。
- **假设审计师**（第一性原理）—— 立场：你对这个问题的所有「分析」都建立在假设上。如果假设是错的，你找到的「根因」只是另一个症状。

## 何时不用 / 转诊

- 问题还没界定清楚，先别追根因 → xmind-arena-framing
- 系统整体在退化、越努力越糟 → xmind-arena-sysfail
- 单点技术 bug → 直接调试，不用竞技场
- 要复盘一段完整经历 → retro

## 安全边界

涉及个人身心健康的反复问题（情绪/睡眠/躯体化）：只提供思考结构，明确建议专业评估，不替代诊断。
