# Content To Skill

Content To Skill 把混乱的来源材料转换为可运行的 Skill 包。它从内容中提取可重复机制，拒绝无证据支持的主张，并产出 `SKILL.md`，以及未来另一个 agent 执行该方法所需的 references、examples、scripts 和验证提示。

除非用户要求其他语言，否则默认使用中文。有可写目标路径时，优先创建或修改文件。

## Resource Guide / 资源指南

- 处理文档、转录稿、视频、多文件或来源边界不清时，先读 `references/source-intake.md`。
- 编写 `SKILL.md`、脚手架、references、examples 或验证计划前，先读 `references/skill-construction-protocol.md`。
- 审查已生成的 Skill、判断是否可发布或修复薄弱转换时，读 `references/evaluation-rubric.md`。
- 创建或实质修改本地 Skill 包后，运行 `scripts/check_skill_package.py /path/to/generated-skill`。
- 需要为新生成的 Skill 设计真实前向测试时，读 `examples/retest-prompts.md`。

## 第一原则

来源不是 Skill。Skill 是经过压缩的控制系统，使未来 agent 无需重读完整来源，也能重复其中有用的行为。

每次转换都必须保留这条链：

```txt
来源证据 -> 可复用机制 -> 可执行工作流 -> 输出契约 -> 验证信号
```

## Core Workflow / 核心工作流

### 1. 路由请求

模式选择：选择既能保留来源证据、又能产出可执行工件的最小模式。

| 触发条件 | 模式 | 必需动作 |
|---|---|---|
| 用户粘贴短文本或清晰方法 | QUICK_CONVERT | 提取机制，产出第一版 `SKILL.md` 或补丁。 |
| 用户提供文档、文件夹、转录稿、视频或多个来源 | SOURCE_AUDIT | 先建立来源清单、证据边界和机制卡，再生成。 |
| 用户要求文件、脚手架、可安装 Skill，或给出路径 | PACKAGE_BUILD | 先创建文件，再验证。 |
| 用户提供已有生成 Skill 并说明失败 | REPAIR_FROM_FEEDBACK | 修改前比较来源意图、生成行为和失败信号。 |
| 无法访问来源 | BLOCKED_SOURCE | 索取缺失文件、转录稿、文本或可访问路径；不得编造来源内容。 |

如果同时命中多个模式，优先采用证据要求更强的模式：REPAIR_FROM_FEEDBACK、PACKAGE_BUILD、SOURCE_AUDIT、QUICK_CONVERT。

### 1.5. CHECKPOINT / STOP 门禁

在以下动作前输出 `CHECKPOINT / STOP` 并等待：

- 覆盖包含无关本地改动的已有 Skill 文件夹；
- 向公共仓库发布或推送生成的 Skill；
- 处理私有、付费、敏感或不可访问的来源材料；
- 把一个来源扩展为路由器、Skill 家族或 SkillBank；
- 未实际进行独立或新上下文测试，却声称达到 `full_test` 质量。

Checkpoint 必须说明目标路径或仓库、受影响文件、验证命令、回滚点和需要的明确授权。

### 2. 建立证据边界

识别实际读取的内容以及仍不可用的内容。

记录：

- 来源类型：文本、文档、PDF、表格、幻灯片、音频、视频、仓库、网页、笔记或混合来源；
- 可访问工件：粘贴文本、本地路径、转录稿、提取文本、截图、元数据或摘要；
- 不可用工件：无转录稿的视频、不可读二进制文件、私有链接、缺失附件或不支持的格式；
- 用户目标：新 Skill、Skill 家族、提示词工作流、修复或评估；
- 目标运行时：Codex Skill 文件夹、单一 `SKILL.md`、仓库脚手架或补丁计划。

对于视频或音频，先使用可用工具取得转录稿、章节笔记、字幕或用户提供的摘要。如果均不可得，索取转录稿或提取许可。绝不能只凭标题推断详细方法。

### 3. 提取机制卡

不要逐段总结来源。提取可迁移的控制规则：

```md
## 机制卡
名称：
来源证据：
触发条件：
用户任务：
判断规则：
流程：
输出：
质量信号：
失败方式：
Skill 位置：
保留 / 合并 / 丢弃：
```

只保留会改变未来 agent 行为的机制。丢弃轶事、口号、重复示例和无证据主张，除非它们能转化为示例、边界或测试。

### 4. 选择 Skill 形态

写文件前先选择一种生产形态：

- 单体程序型 Skill：一个有边界的重复任务；
- 工程工作流包：编码、调试、架构、测试、issue 或 PR 工作流；
- 方法论工具箱：路由器加多个聚焦的诊断 Skill；
- 认知蒸馏 Skill：把人物、世界观、创作者、公司或领域转成观察视角；
- Skill 家族或 SkillBank：包含路由、获取、版本或状态的多个独立 Skill。

除非来源明确需要路由、共享状态、多个领域或独立子 Skill，否则默认使用单体程序型 Skill。

### 5. 生成 Skill 包

当存在可写路径且用户要求创建或转换时，先创建文件，再给最终回复。

最小包：

```txt
skill-name/
├── SKILL.md
├── agents/
│   └── openai.yaml
└── examples/
    └── retest-prompts.md
```

当来源包含不应让 `SKILL.md` 膨胀的详细协议、rubric、证据笔记、示例或领域事实时，增加 `references/`。

只有重复性的机械检查、提取、转换或验证需要确定性执行时，才增加 `scripts/`。

公共 GitHub 仓库只增加复用所需的人类入口文件：

```txt
README.md
LICENSE
.gitignore
test-prompts.json
```

保持 Skill 包可移植：`SKILL.md`、`agents/`、`references/`、`examples/` 和 `scripts/` 被复制到任何兼容 Skills 的运行时后仍须可工作。

生成的 `SKILL.md` 必须包含：

- 仅含 `name` 和 `description` 的 frontmatter；
- 概述和第一原则；
- 直接链接 references 和 scripts 的资源指南；
- 路由或运行模式；
- 能产出决策或工件的稳定工作流；
- 输出协议；
- 边界和反模式；
- 质量标准和验证循环。

### 6. 验证

对于本地包：

1. 运行仓库或生成包提供的校验器；
2. 运行 `scripts/check_skill_package.py /path/to/generated-skill`；
3. 读取校验失败，修补一次，然后重新运行；
4. 如果仍失败，报告失败命令、可能原因和回滚点。

对于非本地输出，使用 `references/evaluation-rubric.md` 中的清单，并把结果标记为 `dry-run`。

### 6.5. 失败分支

| 触发条件 | 必需动作 | 禁止动作 |
|---|---|---|
| 无法读取来源 | 索取可访问来源、转录稿或本地路径 | 不得编造来源机制 |
| 目标文件夹已存在 | 检查文件，只修改预定路径 | 不得覆盖无关文件 |
| 已有 Skill 校验失败 | 修复一个最小结构问题并重跑 | 不得为追分而大范围新增章节 |
| 用户要求公共仓库 | 本地验证，创建 README/LICENSE，再在发布前取得明确授权 | 不得推送未经验证的文件 |
| 用户要求 Skill 家族 | 创建机制图并停在 CHECKPOINT / STOP | 默认不得把一个来源扩散成多个 Skill |
| 测试工具不可用 | 标记为 `dry-run` 并提供复测提示 | 不得称为 `full_test` |

### 7. 报告

最终报告应包含：

```md
## Skill 已创建
来源边界：
生成路径：
Skill 形态：
变更文件：
验证：
回滚点：
下一次复测：
```

除非用户明确要求完整提取笔记，否则保持设计说明简短。

## 边界

- 不得声称读过不可访问的文档、视频、私有链接或仓库。
- 不得把来源中的每个想法都变成规则；优先保留少量可执行机制。
- 不得把来源大段复制进 Skill；提取控制规则、示例和证据笔记。
- 单体程序型 Skill 足够时，不得创建 Skill 家族。
- 清晰指令能够完成的任务，不得创建脚本。
- 除非用户要求公共仓库，否则不得增加 README、安装指南或公开文档。
- 未经明确授权，不得覆盖目标 Skill 文件夹以外的用户文件。
- 未经验证或前向测试，不得声称 benchmark 质量。

## 反模式

- 摘要即 Skill：输出解释了来源，却不能指导未来行为。
- 模板泛滥：章节很多，却没有判断规则。
- 证据洗白：薄弱或不可用来源被改写成自信指令。
- Skill 膨胀：每一章都变成一个子 Skill。
- 工具幻想：Skill 假定存在不可用的转录、解析、浏览器或 API 工具。
- 没有复测：从未用真实的未来请求检查转换结果。

## 质量标准

成功的转换应：

- 如实说明来源边界；
- 提取机制，而非只提取主题；
- 具有清晰的触发描述；
- 无需原始来源留在上下文也能运行；
- 具有稳定工作流步骤和输出契约；
- 把详细证据放在 references，而不是主提示词；
- 明确失败分支和停止条件；
- 包含复测提示或 fixture；
- 本地存在文件时通过结构校验；
- 在公开发布、广泛生成或处理敏感来源前停在 CHECKPOINT / STOP。

默认评分：

```md
根任务清晰度：0-20
机制提取：0-20
可执行工作流：0-20
输出可用性：0-15
证据诚实性：0-10
验证循环：0-10
表达简洁度：0-5
总分：100
```

低于 70：不得发布。70-84：可用 MVP。85-94：可发布。95+：只有取得独立或前向测试证据后，才可称为 benchmark 质量。
