一个模糊的想法来了——大到一个代理会话装不下，且笼罩在迷雾中：从这里到**目的地（destination）**的路还看不见。寻路（wayfinding）的要义是找到那条路，而不是朝目的地猛冲。本技能把这条路绘制成仓库议题跟踪器上的一张**共享地图（shared map）**，然后一张一张地推进它的**决策工单（decision tickets）**（其解决方式是一份决策，而不是要执行的一块构建切片），直到路线清晰为止。

目的地因任务而异，而命名它是绘制地图的第一个动作：它塑造每一张工单。它可能是要交接并继续迭代的一份规格说明，是规划开始前要敲定的一项决策，或是一处就地完成的变更，比如数据结构迁移。地图与领域无关：工程工作、课程内容，任何符合这个形态的事情都行。

## 规划，而非执行

Wayfinder 默认是**规划**：每张工单解决一项决策，当路线清晰、在别人动手去做之前已无可决策之事时，地图即告完成。那种「不如直接动手干」的冲动，通常正是你已经走到地图边缘、该交接出去的信号。一次任务可以在其 **Notes（备注）**中推翻这个默认，把执行本身纳入地图；但如果没有这么写，就只产出决策，不产出交付物。

## 以名称引用

每张地图和每张工单都是一个议题，所以它有一个**名称**：它的标题。在所有人类会读到的内容里（叙述、地图的「已定决策」），都要用这个名称来引用它，绝不要只写一个光秃秃的 id、编号或 slug。满屏的 `#42, #43, #44` 难以阅读；名称一眼就能看懂。id 和 URL 并没有消失；一个名称包裹着它的链接，但它们嵌在名称*之内*，绝不取代名称。

## 地图

地图是仓库议题跟踪器上的一个单独议题，打上 `wayfinder:map` 标签，是权威性制品。它的工单都是地图的子议题。

地图是**索引**，不是存储。它列出已做出的决策，并指向保存其细节的工单；一项决策只存在于一个地方——它的工单，所以地图从不复述它，只给出要点并附上链接。

**地图、其子工单、阻塞关系与前沿查询实际存放在哪里，取决于具体的跟踪器。**议题跟踪器应当已经提供给你。如果没有，请让用户运行 `/setup-matt-pocock-skills`。查阅跟踪器文档的「Wayfinding operations（寻路操作）」一节，了解*这个*仓库如何表达它们。如果尚未提供任何跟踪器，默认使用本地 Markdown 跟踪器。

### 地图正文

整个地图以低分辨率呈现，每个会话加载一次。未关闭的工单**不**列在这里：它们是未关闭的子议题，通过查询来发现。

```markdown
## Destination

<what reaching the end of this map looks like: the spec, decision, or change this effort is finding its way to. One or two lines; every session orients to it before choosing a ticket.>

## Notes

<domain; skills every session should consult; standing preferences for this effort>

## Decisions so far

<!-- the index: one line per closed ticket, enough to judge relevance, then zoom the link for the detail the ticket holds -->

- [<closed ticket title>](link): <one-line gist of the answer>

## Not yet specified

<!-- see "Fog of war": in-scope fog you can't ticket yet; graduates as the frontier advances -->

## Out of scope

<!-- see "Out of scope": work ruled beyond the destination; closed, never graduates -->
```

### 工单

每张工单都是地图的一个**子议题**；跟踪器上的议题 id 是它的身份。它的正文就是问题本身，规模按一个 100K token 的代理会话来定：

```markdown
## Question

<the decision or investigation this ticket resolves>
```

每张工单带一个 `wayfinder:<type>` 标签，取值为 `research`、`prototype`、`grilling`、`task` 之一（见[工单类型](#ticket-types)）。

一个会话**认领（claim）**一张工单，方式是把它指派给主导这张地图的开发者，**并且要先**指派、再开始任何工作，这样并行的会话就会跳过它。那个被指派人*就是*认领本身：一张未关闭且未指派的工单就是无人认领的。

阻塞关系使用跟踪器**原生**的依赖关系：这至关重要，因为它能在跟踪器自己的界面里*可视化*地呈现前沿，让人不用打开地图就能看到哪些可以领取。只有不支持原生阻塞关系的跟踪器，才退回到在正文里约定。当阻塞一张工单的所有工单都已关闭时，它就是**未被阻塞（unblocked）**的；**前沿（frontier）**就是那些未关闭、未被阻塞、无人认领的子工单——已知世界的边缘。

答案不属于正文的一部分；它在解决时记录（见[沿地图推进](#work-through-the-map)）。解决工单过程中创建的资产从议题里以链接引用，而不是粘贴进来。

## 工单类型

每张工单要么是 **HITL**（human in the loop，人在回路——与一位能自主发言的人类*一起*推进），要么是 **AFK**，由代理独自驱动。HITL 工单只能通过这种实时交流来解决；代理绝不能替人类扮演他那一边的角色（一个自己回答自己问题的 grilling 代理就破坏了这一点）。

- **Research（研究）**（AFK）：阅读文档、第三方 API，或知识库之类的本地资源，找出某项决策正在等待的事实。由调用 Skill 工具并传入 "research" 的子代理解决。当需要当前工作目录之外的知识时使用。
- **Prototype（原型）**（HITL）：通过调用 Skill 工具并传入 "prototype"，制作一个廉价、粗糙、具体的制品供人回应（一份大纲、一个粗略的初稿、一个桩，或 UI/逻辑代码），从而提升讨论的保真度。把原型作为资产链接进来。当关键问题是「它应该长什么样」或「它应该如何表现」时使用。
- **Grilling（盘问）**（HITL）：对话。这是默认情况。始终调用 Skill 工具两次，分别传入 "grilling" 和 "domain-modeling"。
- **Task（任务）**（HITL 或 AFK）：在做出*决策*之前必须完成的动手工作：没什么可决策、可原型化或可研究的，但讨论在它完成之前被卡住。注册一个服务以便评判其 API、开通访问权限、搬动数据以便看清其形态。这是唯一一个*动手做*而非做决策的类型，它凭「为一项决策解除阻塞」赢得一席之地，而不是靠交付目的地本身。代理能独自完成的地方就独自驱动（AFK）；否则就交给人类一份精确的清单（HITL）。工作完成时解决；答案记录做了什么，以及后续工单所依赖的任何结果事实（凭据存放位置、新 URL、行数）。

## 战争迷雾

地图*故意*保持不完整：不要绘制你还看不见的东西。在现存工单之外是**战争迷雾（fog of war）**：你能预感到即将到来、却还无法锁定的决策和调查所构成的模糊视野，因为它们悬在仍未解决的问题之上。解决一张工单就会驱散它前方的迷雾，把如今已可具体化的内容一步步「毕业」为新的工单，直到通往目的地的路清晰无阻、不再剩任何工单。

地图的**Not yet specified（尚未具体化）**一节，正是写下那片模糊视野的地方：疑似的问题、稍后要回访的区域。它是*朝向*目的地的未探明前沿：这里的一切都在范围内，只是还不够清晰到能写成工单。视野允许写多松就写多松、写多全就写多全；它同时充当路标，让协作者看出这次任务正走向哪里。

**放迷雾还是开工单？**判断标准是：你现在能否精确地陈述这个问题，而*不是*你现在能否回答它。

- **写成工单**：当问题已经足够清晰，即使它被阻塞、你还不能行动。
- **留在「尚未具体化」**：当你还无法把它表述得那么清晰时。不要提前把迷雾切成工单大小的小块：它比工单更粗糙，前沿抵达时，一片迷雾可能毕业成多张工单，也可能一张都没有。

**尚未具体化**排除掉已经定案的内容（已定决策）、已经是现存工单的内容，以及超出范围的内容（见下一节）。

## 范围之外

迷雾只会*朝向*目的地聚集。目的地固定了范围，所以超出它的工作就是**范围之外（out of scope）**：它不是迷雾，也不属于**尚未具体化**。它在地图上拥有自己的**Out of scope（范围之外）**一节：你已自觉排除在*这次*任务之外的工作。让它落到这里的是范围，而不是清晰度。

范围之外的工作永远不会毕业（前沿止步于目的地），所以只有当目的地被重新划定、并且作为一次全新的任务时，它才会回来，而不是作为延续。

把某件事划出范围是一个划定范围的动作，而不是路线上的一个步骤。当一张已存在的工单结果位于目的地之外（绘制时划错范围，或被某个结论暴露出来），就**关闭它**（已关闭的工单毫无疑问地离开前沿），并在**范围之外**一节留一行：要点加上它为何超出范围，并链接那张已关闭的工单。它不得进入**已定决策**——那里记录的是实际走过的路线；范围边界不是这条路线上的一个步骤。

## 调用方式

两种模式。无论哪种，**每个会话最多解决一张工单**，research 工单除外。

### 绘制地图

用户带着一个模糊的想法调用。

1. **命名目的地。**调用 Skill 工具两次，分别传入 "grilling" 和 "domain-modeling"，敲定这张地图要找的是什么：规格说明、决策，还是变更。目的地固定范围，所以最先敲定它。
2. **绘制前沿。**再次盘问，这次采用**广度优先**：在整个空间上铺开，而不是在任何一条线索上深挖，浮现出悬而未决的决策和现在就能迈出的第一步。**如果这一步没有浮现出任何迷雾**（通往目的地的路已经清晰，整个旅程小到一个会话就能装下），你就不需要地图。停下来询问用户想如何继续。
3. **创建地图**（标签 `wayfinder:map`）：填好 Destination 和 Notes，Decisions-so-far 留空，把迷雾草拟进**尚未具体化**。
4. **把现在能具体化的工单创建出来**，作为地图的子议题，然后在**第二轮**里接好阻塞边（议题需要先有 id 才能互相引用）。接线会把它们分成前沿的和被阻塞的；一切你还无法具体化的内容留在迷雾中：即**尚未具体化**一节。
5. **派出 research 子代理。**为你刚创建的每张 `research` 工单各启动一个子代理，让它调用 Skill 工具并传入 "research"，并行解决这些工单，把发现记录在一次性的 `research/<name>` 分支上，并从工单给出上下文指针。
6. 停下：绘制地图是一个会话的工作量；它不亲手解决任何东西。

### 沿地图推进

用户带着一张地图（URL 或编号）调用。工单是**可选的**：不指定时，由你来挑选下一项决策，而不是用户。

1. 加载**地图**：低分辨率视图，而不是每张工单的正文。
2. 挑选工单。用户指定了就用那张。否则按顺序取第一张前沿工单。**认领它**：在做任何工作之前先把它指派给你自己。
3. 解决它。**按需放大**：随时按需获取任何相关或已关闭工单的完整正文；对 `## Notes` 块中列出的每个技能调用 Skill 工具。拿不准时，调用 Skill 工具两次，分别传入 "grilling" 和 "domain-modeling"。
4. 记录结论：把答案作为**结论评论（resolution comment）**发布，**关闭**该议题，并在**已定决策**处追加一条上下文指针。
5. 添加新浮现的工单（先创建后接线）；把答案使其变得可具体化的任何迷雾毕业，将每一片毕业的迷雾从**尚未具体化**中清除，让它只以新工单的形式存在。如果答案揭示某张工单（这张或其他）位于目的地之外，就**把它划出范围**，而不是在路线上解决它。如果这项决策使地图的其他部分失效，就更新或删除那些工单。

用户可能并行推进未被阻塞的工单，所以要做好其他会话同时在编辑跟踪器的准备。
