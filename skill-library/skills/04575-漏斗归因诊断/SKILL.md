# 漏斗归因诊断

> 指标掉了，不是"感觉掉了"——是要量化掉多少、掉在哪里、为什么掉。
> 本技能通过 MECE 分层拆解 + CASE WHEN 多事件漏斗 + 贡献度计算，帮你从大盘数字定位到具体可行动的根因。

## 1. 触发条件

满足以下任一条件时，启动本技能：

- 用户说"XX指标掉了"、"XX数据下降了"、"XX不如之前了"

- 用户说"帮我归因"、"帮我定位原因"、"根因分析"
- 其他技能（如数据决策分析）发现异动后调用本技能做深入诊断

## 2. 完整执行流程

### Step 1：量化异动 —— 先搞清楚"掉了多少"

**目标：** 用绝对值（pp）和相对值（%）精确描述异动幅度，并锁定最大变化区间。

**操作：**

1. 确认目标指标的完整口径（从 QODERWORK.md 的「指标口径定义」段获取）。
2. 确认对比时间段：
   - 默认：环比（本周期 vs 上周期，周期粒度由数据频率决定）
   - 如果用户指定了对比区间，以用户为准
3. 拉取数据，计算：
   - **绝对变化**：`Δpp = 当前值 - 对比值`（单位：百分点/pp）
   - **相对变化**：`Δ% = (当前值 - 对比值) / 对比值 × 100%`
4. 如果数据有日粒度时间序列，画出趋势线，**找到拐点日期**——
   即变化最剧烈的相邻两天或相邻一周。

**产出示例：**
> "渗透率从 12.3% 降至 10.8%（-1.5pp / -12.2%），拐点出现在 6月3日-6月5日。"

**分支判断：**
- 如果用户已经提供了具体的下降数字（如"从12%掉到10%"），跳过量化步骤，直接进入 Step 2。
- 如果用户只说"感觉掉了"但没数字，必须先拉数据完成量化。

---

### Step 2：MECE 分层拆解 —— 把大盘数字拆到可行动粒度

**目标：** 通过多层级互斥穷举（MECE）拆解，找到异动的具体归属段。

**三层拆解框架：**

#### Level 1：nu / ou 拆分（新用户 vs 老用户）

这是最关键的拆分，因为 nu 和 ou 的异动往往有完全不同的根因。

- **nu（New User）**：首次使用/访问该功能的用户
- **ou（Old User）**：之前已使用过、本次为回访的用户

**拆分逻辑：**
```sql
-- nu/ou 拆分基础模板
SELECT
  CASE
    WHEN is_new_user = 1 THEN 'nu（新用户）'
    ELSE 'ou（老用户）'
  END AS user_type,
  COUNT(DISTINCT visitor_id) AS uv,
  -- 指标计算（根据 QODERWORK.md 口径定义替换）
  <指标分子> AS metric_numerator,
  <指标分母> AS metric_denominator
FROM <表名>          -- 从 QODERWORK.md「常用 ODPS 表映射」获取
WHERE day = '<日期>'  -- 分区条件
GROUP BY
  CASE
    WHEN is_new_user = 1 THEN 'nu（新用户）'
    ELSE 'ou（老用户）'
  END;
```

**验证规则：** nu UV + ou UV 必须等于总 UV（允许 ±0.5% 误差，因为跨段去重）。
如果误差超过 0.5%，说明拆分逻辑有问题，**停下来排查再继续**。

#### Level 2：入口 / 场景 / 渠道拆分

在 nu 和 ou 内部，进一步按流量入口或业务场景拆分：

- 按入口页面（如：首页推荐、搜索结果、push 唤醒）
- 按业务场景（如：拍照翻译、文档翻译、对话翻译）
- 按渠道来源（如：自然流量、付费投放、社交分享）

**拆分维度取决于业务实际**——从 QODERWORK.md 的「业务规则」段获取团队常用的拆分维度。

#### Level 3：用户行为分层

在最细粒度上，按用户行为模式拆分：

- 高频用户（日均 ≥ N 次）vs 低频用户
- 完整走完漏斗 vs 中途流失
- 不同设备/平台（iOS / Android / Web）

**注意：** 不是每次分析都要拆到 Level 3。根据 Step 1 的异动幅度和 Level 1/2 的结果，
判断是否需要继续深入。如果 Level 1 已经定位到明确根因，可以提前结束。

---

### Step 3：CASE WHEN 多事件漏斗构建

**目标：** 在每个关注点（每个 Level 的关键段）内，构建完整的事件漏斗，
观察从曝光到最终转化的每一步转化率。

**核心 SQL 模式（CASE WHEN 多事件漏斗）：**

```sql
SELECT
  day,
  CASE
    WHEN arg1 = 'page_exposure'  AND event_id = '2201' THEN '01_曝光'
    WHEN arg1 = 'entry_click'    AND event_id = '2101' THEN '02_入口点击'
    WHEN arg1 = 'feature_enter'  AND event_id = '2001' THEN '03_功能进入'
    WHEN arg1 = 'action_trigger' AND event_id = '2101' THEN '04_核心动作触发'
    WHEN arg1 = 'result_show'    AND event_id = '2201' THEN '05_结果展示'
    WHEN arg1 = 'result_click'   AND event_id = '2101' THEN '06_结果点击'
    ELSE NULL
  END AS funnel_stage,
  COUNT(1)              AS pv,
  COUNT(DISTINCT visitor_id) AS uv
FROM <表名>
WHERE day BETWEEN '<start_date>' AND '<end_date>'
  AND arg1 RLIKE 'page_exposure|entry_click|feature_enter|action_trigger|result_show|result_click'
GROUP BY day,
  CASE
    WHEN arg1 = 'page_exposure'  AND event_id = '2201' THEN '01_曝光'
    WHEN arg1 = 'entry_click'    AND event_id = '2101' THEN '02_入口点击'
    WHEN arg1 = 'feature_enter'  AND event_id = '2001' THEN '03_功能进入'
    WHEN arg1 = 'action_trigger' AND event_id = '2101' THEN '04_核心动作触发'
    WHEN arg1 = 'result_show'    AND event_id = '2201' THEN '05_结果展示'
    WHEN arg1 = 'result_click'   AND event_id = '2101' THEN '06_结果点击'
    ELSE NULL
  END
HAVING funnel_stage IS NOT NULL
ORDER BY day, funnel_stage;
```

**关键要点：**

- **PV 和 UV 必须对称输出**：每一行同时包含 `COUNT(1)` 和 `COUNT(DISTINCT visitor_id)`。
  只看 PV 或只看 UV 都会导致分析偏差。
- **漏斗阶段编号前缀**（01_、02_...）：确保排序正确，避免字母序导致阶段乱序。
- **arg1 过滤用 RLIKE 优于 IN**：避免隐式类型转换和编码问题，尤其在 ODPS 环境下。
- **CASE WHEN 条件顺序**：先写具体条件，再写通用条件。如果某事件有多个 event_id，
  把最具体的 event_id 条件写在前面。
- **NULL 兜底 + HAVING 过滤**：ELSE NULL 配合 HAVING funnel_stage IS NOT NULL，
  确保非漏斗事件不计入结果。

**漏斗对比方式：**

对每个关注段，分别拉取异动前后的漏斗数据，计算：
- 每一步的绝对 PV/UV 变化
- 每一步到下一步的转化率变化
- 找出转化率下降最大的那一步（漏斗瓶颈）

### Step 4：贡献度计算 —— 每段贡献了多少变化

**目标：** 量化每个拆分段对总指标变化的贡献度。

**计算公式：**

```
段贡献度 = (该段本期指标值 × 该段本期权重) - (该段对比期指标值 × 该段对比期权重)
总变化 = Σ(各段贡献度)
段贡献占比 = 段贡献度 / |总变化| × 100%
```

其中"权重"是该段在总分母中的占比（例如该段 UV 占总 UV 的比例）。

**也可以简化为直接拆解：**

如果指标 = Σ(各段分子) / Σ(各段分母)，则：

```
段贡献(pp) = 该段本期分子/总分母_本期 - 该段对比期分子/总分母_对比期
```

**产出格式（表格）：**

| 拆分段 | 对比期值 | 本期值 | 变化(pp) | 贡献占比 |
|--------|---------|--------|----------|----------|
| nu-场景A | 3.2% | 2.1% | -1.1pp | 73.3% |
| nu-场景B | 1.5% | 1.4% | -0.1pp | 6.7% |
| ou-场景A | 5.8% | 5.4% | -0.4pp | 26.7% |
| ou-场景B | 1.8% | 1.9% | +0.1pp | -6.7% |
| **合计** | **12.3%** | **10.8%** | **-1.5pp** | **100%** |

---

### Step 5：最大贡献区间定位

**目标：** 找到贡献了 80% 变化的最小区段集合——这就是你需要集中火力解决的问题。

**操作：**

1. 将所有拆分段按贡献占比从大到小排序（取绝对值）
2. 累加贡献占比，直到累计 ≥ 80%
3. 被纳入的段就是"最大贡献区间"

**产出示例：**
> "nu-场景A 单独贡献了 73.3% 的下降，加上 ou-场景A 达到 100%。
>  最大贡献区间为 [nu-场景A]，建议优先排查该段漏斗。"

**特殊情况处理：**

- 如果所有段的贡献都很均匀（最大单段 < 20%），说明是**平台级问题**而非功能级问题，
  应转向排查大盘流量变化、版本发布、系统稳定性等宏观因素。
- 如果某段贡献为负（即在指标下降时反而上升），不要忽略它——
  它可能在缓冲更大的下降，需要单独分析它为什么逆势增长。

---

### Step 6：根因归纳与策略建议

**目标：** 把数据发现翻译成可行动的策略建议。

**根据定位结果选择对应策略方向：**

| 根因定位 | 典型原因 | 策略方向 |
|---------|---------|---------|
| nu 集中下降 | 获客渠道变化、新用户引导缺失、首次体验门槛高 | 优化 onboarding、调整投放策略、降低首次使用门槛 |
| ou 集中下降 | 功能体验退化、竞品分流、使用场景萎缩 | 排查版本变更、用户调研、增强核心功能粘性 |
| 特定入口下降 | 入口位置变化、UI 改版、曝光减少 | 确认是否有 UI 改动、检查曝光量变化、A/B 测试验证 |
| 特定场景下降 | 场景需求变化、技术故障、体验劣化 | 排查技术问题、分析场景使用趋势、用户访谈 |
| 全段均匀下降 | 大盘流量下降、季节性因素、平台策略变化 | 检查大盘 DAU、对比行业趋势、确认是否有全局变更 |
| 漏斗某步转化骤降 | 页面加载慢、交互异常、流程中断 | 检查对应页面的技术指标（加载时间、错误率、crash率） |

**策略建议格式：**

> **根因：** [一句话概括]
> **证据：** [关键数据点]
> **建议：** [具体可执行的下一步动作]
> **优先级：** P0 / P1 / P2
> **预期影响：** 如果修复，预计可恢复 X pp / Y%

### Step 7：生成报告

**目标：** 产出结构化的分层分析报告。

**默认格式：HTML 报告**（除非 QODERWORK.md 的「输出风格」段指定了其他格式）。

报告必须包含以下模块：

#### 7.1 摘要卡片（Stat Cards）

在报告顶部用卡片展示核心数字：
- 指标当前值 & 对比值
- 绝对变化（pp）
- 相对变化（%）
- 最大贡献段名称 & 贡献占比

#### 7.2 瀑布图（Waterfall Chart）

用 Chart.js 绘制贡献度瀑布图：
- X 轴：各拆分段
- Y 轴：贡献值（pp）
- 正贡献为绿色柱、负贡献为红色柱
- 最右侧为合计柱

#### 7.3 分层漏斗可视化

对最大贡献区间内的段，绘制漏斗对比图：
- 异动前漏斗（浅色）vs 异动后漏斗（深色）
- 每一步标注 PV、UV、转化率
- 转化率下降最大的步骤高亮标记

#### 7.4 三段叙事结构

按 QODERWORK.md「输出风格」中定义的汇报叙事风格输出。默认三段结构：

1. **结论先行：** "XX指标从A降至B（-Xpp / -Y%），最大贡献来自[segment]。"
2. **数据支撑：** 关键拆分数据 + 漏斗瓶颈定位。
3. **行动建议：** 具体策略 + 优先级 + 预期影响。

#### 7.5 Boss 汇报摘要

生成一段可直接复制给老板的摘要文字（3 段以内，先结论后数据），遵循：
> **三段叙事：** 绝对pp提升 + 相对% + 稳定平台
> 例："渗透率下降1.5pp（-12.2%），主要由新用户-场景A贡献（73.3%），老用户基本稳定。
> 建议优先排查新用户引导流程，预计修复后可恢复1.0-1.2pp。"

## 3. 分支逻辑速查

```
用户说"XX指标掉了"
├─ 不知道掉多少 → Step 1 量化异动
├─ 已知掉多少 → 跳到 Step 2 分层拆解
│
├─ Level 1 拆分后：
│  ├─ nu 集中下降 → onboarding/获客问题，深入 nu 漏斗
│  ├─ ou 集中下降 → 体验/留存问题，深入 ou 漏斗
│  └─ nu + ou 同步下降 → 平台级问题，检查大盘
│
├─ Level 2 拆分后：
│  ├─ 特定入口下降 → 检查 UI 改动、曝光变化
│  ├─ 特定场景下降 → 检查技术问题、需求变化
│  └─ 所有入口/场景均匀下降 → 宏观因素，排查大盘流量
│
├─ 漏斗分析后：
│  ├─ 某一步转化率骤降 → 定位到具体页面/交互问题
│  └─ 每步都略有下降 → 整体体验问题，可能需要用户调研
│
└─ 贡献度分析后：
   ├─ 最大单段贡献 > 50% → 聚焦该段，深挖根因
   ├─ 最大单段贡献 < 20% → 平台级问题，不要纠结单点
   └─ 某段贡献为负（逆势增长）→ 单独分析，可能是缓冲因素
```

## 5. 陷阱与红线（必须遵守）

### 技术陷阱

1. **漏斗分析必须保持 PV 和 UV 对称输出。**
   每一步同时输出 PV（`COUNT(1)`）和 UV（`COUNT(DISTINCT visitor_id)`）。
   只看 PV 会被刷量用户带偏，只看 UV 会丢失频次信息。两者缺一不可。

2. **arg1 过滤用 RLIKE 优于 IN。**
   在 ODPS 环境下，`IN` 操作符在遇到隐式类型转换或特殊字符编码时可能静默失败。
   用 `RLIKE 'value1|value2|value3'` 更安全，且支持模糊匹配。

3. **nu/ou 拆分后必须验证两边 UV 之和等于总 UV。**
   如果 nu UV + ou UV ≠ 总 UV（误差 > 0.5%），说明用户分类逻辑有问题，
   可能存在跨天用户身份切换或 visitor_id 去重异常。停下来排查再继续。

4. **CASE WHEN 中先写具体条件再写通用条件。**
   CASE WHEN 按顺序匹配，一旦命中就停止。如果把通用条件写在前面，
   具体条件永远不会被执行。例：先写 `event_id = '2101' AND arg1 = 'specific'`，
   再写 `event_id = '2101'`。

5. **贡献度为负不代表该段没问题。**
   当总指标下降时，某个段的贡献为负（即该段逆势增长），并不意味着它表现好——
   它可能在缓冲更大的下降。需要单独拉出来分析它为什么逆势增长，
   以及这种增长是否可持续。

### 业务红线

6. **不准在没确认口径的情况下直接给数据。**
   拉数据前必须从 QODERWORK.md 确认指标口径。如果口径定义是 PLACEHOLDER，
   先问用户确认口径再拉数。

7. **任何对外数据必须标注口径和日期。**
   报告中的每个数字旁边必须标注：口径来源 + 数据日期。
   这是一票否决项（来自 QODERWORK.md 配置）。

8. **不准用 SELECT * 不带 LIMIT 查生产表。**
   所有查询必须指定具体列，且带 LIMIT（建议 LIMIT 10000）。
   如果需要全量聚合，用 GROUP BY 而非 SELECT *。

9. **不要用"大概"、"差不多"描述数据变化。**
   所有变化必须用精确数字描述：精确到小数点后一位的 pp 值和 % 值。

10. **不要跳过验证步骤。**
    每层拆分后都要做 sanity check：拆分后的各段之和必须等于总数。
    如果不等，说明拆分有交叉或遗漏，需要修正后再继续。
