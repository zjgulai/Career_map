# 图像生成综合技能

本 Skill 统一调度图像生成相关能力，根据用户需求自动路由到对应的子能力模块。

## 能力边界声明（首轮强制）

本技能**覆盖以下 10 种图像生成/处理能力**（详见下文「能力概览」表）：背景消除、水印移除、SKU 换色、Logo 贴图、场景展示、细节生成、清晰度增强、模特图生成、图片翻译、指令绘图。

**越界信号 — 在调用任何图像工具前先做范围自检：**

| 用户表达 | 正确处理 |
|---------|---------|
| 视频处理 / 视频剪辑 / 替换视频音频 / 给视频加字幕 / 视频翻译 | 不属于本技能；建议改用「商品视频生成」（alibaba-product-video-generation），或在视频后期工具人工处理 |
| 文档/PDF 内图片 OCR / 提取/识别 PDF 中的图 | 不属于本技能；建议先用 office-suite 解析文档拿到独立图片 URL，再让本技能处理 |
| 直接修改商品发布信息中的图片 / 替我替换主图并发布 | 本技能只生成图片素材；上架/替换图片请由「智能发品」或「商品信息优化」执行 |
| 创建系统级定时图片任务 / 自动每天生成 N 张 | 本技能仅支持单次会话内执行；定时素材任务请在卖家中心 → 智能营销中配置 |
| 多智能体编排（"@A 分析 → @B 生图 → @C 上架"） | 不假装编排；列出本插件实际能直接调用的 SubAgent 清单，请用户确认要执行哪一步 |
| 调用未在本技能工具列表内的图像/海报底层能力 | 列出可用能力（`image_edit`、`image_generate`、产品海报 HTML 生成）及对应工具，引导用户选择 |

**复合请求处理：** 用户一次请求中包含可做项 + 越界项时（例：去背景 + 改成视频），必须先完成可做项并 emit 凭证（图片 URL），再在末尾标注"本轮未处理项 + 建议路由"。

**对工具失败的负反馈处理：** 用户连续反馈"还是没生成 / 还是看不到图"时，禁止重复同一话术；下一步必须立即降级输出（i豆余额提示 / 手动入口链接 / 已成功部分的清单）。

**意图误识别防护（高频问题）：**
- 用户附带图片并要求"分析/点评/看看这张图怎么样" → 这是图片审阅意图，不是生图请求。本技能**只在用户明确要求生成/处理/修改图片时才执行**，纯分析/点评/建议类请求应路由到其他技能或直接文本回答。
- 用户说"帮我写文案/写卖点/写标题" → 这是文案生成意图，不属于本技能。即使用户同时附带了图片，只要核心动作是"写文字"而非"处理图片"，应告知本技能仅处理图像并建议路由。
- 用户要求"批量生成 N 张不同商品的图" → 确认 i 豆余额充足后逐一执行，每张独立 emit 链接。若中途 i 豆耗尽，已生成部分正常交付，未完成部分标注原因。
- 用户在指令中附带图片作为"模板参考" → 必须确认是否要基于该图生成（如去背景/换色/场景图），还是仅作为风格参考。模糊时追问确认再执行。

**交付证据强化：**
- 每张已生成图片必须以可点击链接形式交付（Markdown 图片或 URL），禁止仅文字描述"已为您生成"。
- 用户要求"无Logo"时，生成后必须自行校验图片描述中是否含 Logo/文字标志相关信息；若无法自行校验，在交付时主动提醒"请确认图中无 Logo，如不满意可重新生成"。
- 批量任务逐项列出结果表格：序号 + 原图描述 + 生成结果（URL/失败原因）。

- "帮我把这张图片的背景去掉"

## 通用执行规范

### 工具调用约定

本技能统一使用以下图像/海报生成工具：

| 工具 | 用途 | 支持的 task_type |
|------|------|-----------------|
| `image_edit` | 基于已有图片进行编辑或生成 | `white_background`、`watermark_removal`、`hd_upscale`、`simple_generation`、`complex_generation` |
| `image_generate` | 无参考图片时从零生成 | `simple`、`complex` |

**调用原则：**
- 所有需要输入原图的处理能力，统一使用 `image_edit`。
- 用户未提供任何图片、仅通过文字描述生成时，使用 `image_generate`。
- **产品海报 HTML 生成**使用 AI coding 直接生成 HTML 海报文件。
- 每个任务独立调用工具；多张图片/多任务互不依赖时，可并行执行。

### task_type 选择标准

| 工具 | task_type | 适用范围 |
|------|-----------|---------|
| `image_edit` | `white_background` | 白底图（单一功能，仅支持 1:1） |
| `image_edit` | `watermark_removal` | 去水印（单一功能，仅支持 1:1） |
| `image_edit` | `hd_upscale` | 清晰度增强（单一功能，仅支持 1:1） |
| `image_edit` | `simple_generation` | 单区域、局部、元素 ≤2、标准质量要求的编辑 |
| `image_edit` | `complex_generation` | 多区域、全图变换、高保真、≥2 张参考图的编辑 |
| `image_generate` | `simple` | 单主体、简单场景、低成本生成 |
| `image_generate` | `complex` | 多元素、海报、模特、3D 风格、高细节生成 |

### 单一功能 task_type 降级规则

`white_background`、`watermark_removal`、`hd_upscale` 为单一功能 task_type，仅在满足以下条件时使用：

1. 用户请求为单一意图（无其他编辑需求）。
2. 用户未指定非 1:1 的 `aspect_ratio`。
3. 非后续追加的复杂编辑请求。

触发降级时，切换到 `simple_generation` 执行：prompt 仍按对应场景的 reference 文档构建，并传入用户指定的 `aspect_ratio`。

### aspect_ratio 参数

生成或编辑图像时需确定输出图像的宽高比。

**支持的比例：**

```
1:1 | 2:3 | 3:2 | 3:4 | 4:3 | 4:5 | 5:4 | 9:16 | 16:9 | 21:9
```

**适用范围：**

| 场景 | 是否需要 aspect_ratio |
|------|----------------------|
| `white_background` | 仅支持 1:1；非 1:1 时降级为 `simple_generation` |
| `watermark_removal` | 仅支持 1:1；非 1:1 时降级为 `simple_generation` |
| `hd_upscale` | 仅支持 1:1；非 1:1 时降级为 `simple_generation` |
| 其他所有场景 | 需要判断 |

**判断规则：**

1. **用户明确指定了比例**（如"生成 16:9 的图"、"竖版 9:16"）→ 使用用户指定的比例。
2. **用户指定的比例不在支持列表中**（如"5:3"、"2:1"）→ 告知当前支持的比例列表，请用户选择。
3. **用户在白底图/高清/去水印场景中要求非 1:1 比例** → 自动切换为 `simple_generation`，并传入 `aspect_ratio`。
4. **用户未指定比例** → 按以下分支处理：
   - 白底图 / 高清 / 去水印 → 默认 1:1。
   - 其他场景：
     - 若用户上传了原图 → 读取原图宽高，从支持列表中选择最接近的比例作为默认值。
     - 若用户未上传原图 → 默认 1:1。

### 参数校验（前置拦截）

**在调用任何图像工具之前，必须先进行参数校验。如果必传参数为空或缺失，不得发起工具请求，直接向用户返回明确的提示信息。**

#### 通用必传参数

| 必传参数 | 校验规则 | 缺失时提示 |
|---------|---------|-----------|
| `imageUrl` | 不能为空，必须是有效的图片 URL | "请提供需要处理的图片" |

### 输入处理

1. **图片输入**：接受图片 URL 或本地路径。
2. **图片链接有效性校验**：
   - 在处理用户上传的图片前，需要校验图片链接是否可正常访问。
   - 如果图片链接**无法打开、已失效、返回 404 或其他非正常状态**，**不发起任何工具请求**，直接向用户返回以下固定文案：
     - **"您提供的图片链接无法访问或已失效，请重新上传图片或提供有效的图片链接"**
   - **批量场景**：如果用户上传多张图片，仅对链接失效的图片返回上述提示，链接有效的图片正常处理；需明确告知用户哪些图片链接失效。
3. **参数提取**：从用户请求中提取必要的参数。
4. **默认值**：对于可选参数使用合理的默认值。
5. **批量处理时的图片去重与命名处理**：
   - **检测命名冲突**：按照"从左到右"顺序遍历所有输入图片，识别文件名相同（不含后缀）的图片组。
   - **判断内容一致性**：对于命名相同的图片，比对图片内容（如文件大小、图像哈希等）。
   - **去重处理**：
     - 如果图片内容完全一致，则视为重复图片，**只保留从左到右顺序中最靠前的那一张**。
     - **必须告知用户**：明确列出哪些图片被识别为重复并已去重。
   - **区分命名处理**：
     - 如果图片内容不一致，则对后续同名图片按序号区分命名。
     - **命名规则**：基于"从左到右"顺序，**第一个出现的保留原名**，后续同名不同内容的按顺序添加 `_1`、`_2`、`_3`... 后缀。
     - **必须告知用户**：明确告知用户哪些图片进行了重命名。
   - **映射关系维护**：在调用图像工具**之前**完成去重/重命名，并更新映射关系。使用最终命名作为图片标识，确保后续结果返回不错位。

### 输出规范

1. **原样输出**：严格按照对应 references 文档中的输出格式输出，不要做任何额外处理。
2. **错误处理与降级交付**：
   - 网络错误：自动重试一次。仍失败时，告知具体错误信息并提示用户检查网络后重试。
   - 参数错误：提示检查输入参数，明确列出缺失或格式错误的字段。
   - 服务错误：提示服务状态，建议稍后重试。
   - 工具调用失败：自动重试一次；仍失败时，告知用户"图片处理服务暂时不可用"并建议稍后重试，同时返回已成功的其他图片结果（如有）。
   - 批量部分失败：以表格形式展示每张图的处理结果，成功的展示图片 URL，失败/超时的展示原因。末尾汇总"共 N 张，M 张成功，K 张失败/超时"。
3. **余额不足错误处理**：
   - 当工具返回 i豆不足类错误时，必须提醒用户：**"您当前生意助手的i豆不足，无法进行生图，请充值i豆后再进行使用"**。
   - 同时返回已经执行完成的步骤获取到的结果（如有）。
4. **交付证据规则**：
   - 只有工具返回非空图片 URL 时，才可以说"已生成/已处理完成"。
   - 用户明确要求数量、类别或版本时，必须先列出交付清单；最终返回前逐项核对，少一项就说"部分完成"并列出缺哪一张。
   - 批量图片必须按输入从左到右顺序返回，并标明每个结果对应的原图/类别；不能只给总链接或只说"全部完成"。
   - 用户反馈图片链接打不开或主体不对时，下一步必须先核验原链接/原图映射，再重试，不得直接口头确认成功。

## 组合使用

多个图片处理能力可以组合使用，支持串行、并行以及混合执行模式。

### 场景1：多张图片并行执行同一能力

**场景描述**：用户有多张图片需要执行相同的处理能力。

**示例**：批量去背景。

**执行流程**（以 N 张图为例）：
1. **建立图片与任务的映射关系**（严格按照从左到右的顺序）：
   - 图片1 → 调用 `image_edit`，`task_type: white_background`。
   - 图片2 → 调用 `image_edit`，`task_type: white_background`。
   - ...（每张图独立调用工具）
   - 记录映射：`{原图名称/标识: 结果URL, 顺序: 1, 处理要求: xxx}`。
2. **并行执行并获取结果**。
3. **严格一对一匹配结果**：图片1 的结果对应图片1，以此类推。
4. **等待所有任务都完成后，按输入顺序返回结果**。

**重要**：
- 图片顺序：严格按照用户上传的从左到右顺序处理，第1张图是最左边的图片。
- 必须维护输入图片与工具结果的严格映射关系，确保结果不会错位。
- 失败重试时，必须更新该图片与结果的映射关系。

### 场景2：多张图片分别执行不同能力

**场景描述**：用户有多张图片，每张图片需要执行不同的处理能力。

**示例**：图片1 去背景，图片2 清晰度增强，图片3 生成模特图。

**执行流程**（以 N 张图为例）：
1. **建立图片、能力、任务的映射关系**（严格按照从左到右的顺序）：
   - 图片1（去背景）→ `image_edit`，`task_type: white_background`。
   - 图片2（清晰度增强）→ `image_edit`，`task_type: hd_upscale`。
   - 图片3（模特图）→ `image_edit`，`task_type: simple_generation`。
   - 记录映射：`{原图名称/标识: 结果URL, 顺序: 1, 能力: 去背景, 处理要求: xxx}`。
2. **并行执行并获取结果**。
3. **严格一对一匹配结果**。
4. **等待所有任务都完成后，按输入顺序返回结果**。

### 场景3：一张图片执行多个能力（串行）

**场景描述**：一张图片需要按顺序执行多个处理能力，下一步依赖上一步的结果。

**示例流程**：去背景 → 场景展示
1. 调用 `image_edit`，`task_type: white_background`，生成白底图。
2. **等待第1步完全完成后**，使用生成的白底图 URL。
3. 调用 `image_edit`，`task_type: simple_generation`，将白底图合成到场景中。
4. **等待第2步完全完成后**，返回最终结果。

**示例流程**：换色 → 加Logo
1. 调用 `image_edit`，`task_type: simple_generation`，改变商品颜色。
2. **等待第1步完全完成后**，使用生成的换色图 URL。
3. 调用 `image_edit`，`task_type: simple_generation`，添加品牌 Logo。
4. **等待第2步完全完成后**，返回最终结果。

**重要**：
- 串行执行必须**严格等待上一步完成**后再执行下一步。
- 上一步的输出 URL 作为下一步的输入。
- **必须等最后一步完成后，再返回最终结果**。

### 场景4：一张图片执行多个能力（串并行混合）

**场景描述**：一张图片需要执行多个能力，部分可以并行，部分需要串行。

**示例**：去背景后，同时进行【场景展示】和【清晰度增强】。

**执行流程**：
1. 调用 `image_edit`，`task_type: white_background`，去除背景。
2. **等待去背景完全完成**，获取白底图 URL。
3. **并行执行**以下两个任务：
   - 调用 `image_edit`，`task_type: simple_generation`，将白底图合成到场景。
   - 调用 `image_edit`，`task_type: hd_upscale`，增强白底图清晰度。
4. **等待两个并行任务都完成后，一起返回两个结果**。

### 通用执行原则

1. **任务映射管理（关键）**：
   - 必须建立并维护输入图片与工具结果的严格映射关系。
   - 图片顺序定义：用户上传的多张图片按照**从左到右**的顺序排序，第1张图是最左边的图片。
   - 使用字典或 Map 结构记录：`{原图名称/标识: 结果URL, 顺序: 1, 处理要求: xxx}`。
   - 返回结果时必须严格按映射关系对应，**绝对不能错位**。

2. **工具调用**：
   - 每个任务都是独立的工具调用。
   - 记录每次调用的输入参数（原图名称/标识、处理要求）和返回结果。

3. **结果返回**：
   - **无论串行还是并行，必须等所有任务都完成后，再统一返回结果给用户**。
   - **必须按照输入图片的顺序返回结果**：第1张图（最左边）的结果在第1位，第2张图的结果在第2位，以此类推。
   - 返回结果时必须明确标识每张输入图片对应的输出结果。
   - 如果返回结果包含标题（如"绿色大衣"），必须确保标题与图片实际内容严格对应。

4. **失败重试处理**：
   - 如果某个任务失败需要重新发起请求，**必须更新映射关系**。
   - 返回结果时仍然按照原图顺序返回，但使用的是最新调用对应的结果。

5. **余额不足处理**：
   - 当某个任务返回 i豆不足错误时，**不进行重试**。
   - 必须提醒用户充值。
   - 同时返回已经执行完成的步骤获取到的结果，并明确标识哪些图片因 i豆不足未处理。
