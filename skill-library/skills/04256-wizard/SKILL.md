# Wizard

**向导（wizard）**是一个 bash 脚本，一步步带领人类走完一套手动流程——这套流程亲手做很繁琐，每次向 AI 重新解释也很繁琐。它打开每个 URL，说清楚该点什么、该复制什么，捕获各项值，把它们写到该去的地方（`.env`、GitHub secrets），在每个阶段确认，并显示还剩多少个阶段。它可能配置第三方服务、执行一次性迁移，或把项目从一种状态挪到另一种状态。

令人愉悦的 UX 已经由 [template.sh](template.sh) 解决了：逐阶段进度、确认关卡、跨平台打开 URL（含 WSL）、隐藏式密钥输入、幂等的 `.env` 更新插入（upsert）、`gh secret`/`gh variable` 写入，以及结尾摘要。**你的工作只是划定流程范围并撰写它的各个阶段。** `STAGES` 标记之上的库在每个向导中完全相同；这种一致性正是关键所在：永远不要手工编辑它。

向导默认是短命的：为一次运行而建，存到临时目录或 `scripts/` 路径，活干完就删。只有当用户想要一条应长期留在仓库里的可重复安装路径时，才提交它。

## 流程

### 1. 划定流程范围

理清人类必须执行的每一个手动步骤，以及沿途要捕获的每一个值。先读仓库，不要凭空发问：

- 对于安装类：`.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架配置，以及 `.github/workflows/*`（每处 `secrets.*` / `vars.*` 引用都是向导必须产出的一个值）。
- 对于迁移或状态转换类：当前状态、目标状态，以及两者之间不可逆的动作。

然后把按顺序排列的阶段列表以及每个阶段产出的值展示给用户并确认：用户可以增、删或重排。

**完成标准：**每个阶段都按顺序命名，且对每个要捕获的值，你知道 (a) 人类从哪里拿到它，(b) 它写到哪（`.env`、GitHub secret、两者都要，或哪儿都不写；有些阶段是纯动作），以及 (c) 它是否机密（隐藏输入）或公开。

### 2. 映射每个阶段的路径

为每个阶段写下人类要走的精确路径：打开哪个 URL、在那里做什么、值显示在哪里、填入哪个变量，例如「Dashboard → Developers → API keys → Reveal test key → copy」。对于你并不真正了解当前界面或确切命令的地方，直说，并询问用户或查文档：绝不要编造可能并不存在的步骤。

**完成标准：**每个阶段都能落到一个陌生人也能照做的具体指引上。

### 3. 撰写向导

把 `template.sh` 复制到目标路径。按依赖顺序，把示例阶段替换为每步一个 `stage`。使用库提供的辅助函数：`stage`、`say`/`step`、`open_url`、`ask`/`ask_secret`、`write_env`、`set_secret`/`set_var`、`pause`/`confirm`。把 `TOTAL_STAGES` 设为你写的阶段数。

守住模板立下的标准：先打开 URL 再索取它的值，任何机密内容用 `ask_secret`，每个要持久化的值都 `write_env`，只有 CI 真正需要的值才 `set_secret`，任何不可逆动作之前先 `confirm`。每个 `stage` 会清屏，只显示当前步骤：让一个阶段专注于一项任务，这样人类需要的信息就不会滚出屏幕。不要碰标记之上的库代码。

### 4. 验证并交接

- `bash -n <script>`；如果可用就运行 `shellcheck`。
- `chmod +x <script>`。
- 不要自己端到端运行它：它会打开浏览器并阻塞在人类输入上。改为静态追踪：步骤 1 里的每个值都被捕获，并落到步骤 1 所说的地方；每个 `set_secret` 名称都与 CI 中的某个 `secrets.*` 引用精确匹配。
- 告诉用户如何运行它。如果这是一条可重复的安装路径，就提交它并从 README 链接它，让下一个人直接运行脚本，而不是去问 AI。
