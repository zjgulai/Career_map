对 `HEAD` 与用户给定的固定点之间的 diff 进行双轴审查：

- **Standards（规范）**：代码是否符合本仓库成文的编码规范？
- **Spec（规格）**：代码是否忠实实现了来源 issue / spec？

两个轴都以**并行子代理（sub-agent）**运行，互不污染对方上下文，然后由本技能汇总它们的发现。

你应该已经被提供了 issue 跟踪器配置。如果 `docs/agents/issue-tracker.md` 缺失，请告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 确定固定点

用户所说的任何内容就是固定点（提交 SHA、分支名、tag、`main`、`HEAD~5` 等）。如果用户没有指定，就询问用户。

一次性记录 diff 命令：`git diff <fixed-point>...HEAD`（三个点，即与 merge-base 比较）。同时通过 `git log <fixed-point>..HEAD --oneline` 记下提交列表。

继续之前，确认固定点可以解析（`git rev-parse <fixed-point>`）且 diff 非空。无效的引用或空 diff 应在此处失败，而不是在两个并行子代理内部失败。

### 2. 确定 spec 来源

按以下顺序查找来源 spec：

1. 提交信息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等），通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的 spec 文件。
4. 如果什么都没找到，询问用户 spec 在哪里。如果用户说没有，**Spec** 子代理将跳过并报告「no spec available（无可用 spec）」。

### 3. 确定规范来源

仓库中任何记录代码应该如何编写的文档，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

在仓库自有文档的基础上，Standards 轴始终附带下面的**坏味道基线（smell baseline）**：一组固定的 Fowler 代码坏味道（_《重构》_第 3 章），即使仓库没有任何文档也适用。它受两条规则约束：

- **仓库优先。**仓库成文的标准永远胜出；当仓库标准认可了基线会标记的某种做法时，抑制该坏味道。
- **永远是主观判断。**每个坏味道都是一种带标签的启发式判断（如「可能是 Feature Envy」），绝不是硬性违规。与这里的任何标准一样，跳过工具链已经在强制执行的内容。

每个坏味道都按*它是什么* → *如何修复*的格式阅读；对照 diff 进行匹配：

- **神秘命名（Mysterious Name）**：函数、变量或类型的名称没有揭示它的作用或所持有的内容。→ 重命名它；如果找不到一个诚实的名字，说明设计本身是模糊的。
- **重复代码（Duplicated Code）**：相同的逻辑形态在该变更的多个 hunk 或文件中出现。→ 提取共享的形态，两处都调用它。
- **依恋情结（Feature Envy）**：一个方法访问另一个对象数据的次数超过访问自己数据的次数。→ 把方法移到它所依恋的数据上。
- **数据泥团（Data Clumps）**：相同的几个字段或参数总是结伴出现（一个想要诞生的类型）。→ 把它们捆绑成一个类型，传递该类型。
- **基本类型偏执（Primitive Obsession）**：用基本类型或字符串代替一个值得拥有自己类型的领域概念。→ 给这个概念一个属于自己的小型类型。
- **重复的 Switch（Repeated Switches）**：同一类型上相同的 `switch`/`if` 级联在该变更中反复出现。→ 用多态替换，或让两处共享同一个 map。
- **霰弹式修改（Shotgun Surgery）**：一个逻辑变更迫使在 diff 中跨多个文件进行零散修改。→ 把一起变化的东西收拢到一个模块里。
- **发散式变化（Divergent Change）**：一个文件或模块因为多个互不相关的原因被修改。→ 拆分，使每个模块只为一种原因而变化。
- **投机性通用化（Speculative Generality）**：为 spec 并不存在的需求添加的抽象、参数或钩子。→ 删除它；内联回去，直到出现真实需求为止。
- **消息链（Message Chains）**：调用方本不应依赖的长链式导航 `a.b().c().d()`。→ 把这段导航隐藏到第一个对象的某个方法之后。
- **中间人（Middle Man）**：一个类或函数的大部分工作只是继续转发委托。→ 砍掉它，直接调用真正的目标。
- **被拒绝的遗赠（Refused Bequest）**：子类或实现者忽略或覆盖了所继承的大部分内容。→ 放弃继承，改用组合。

### 4. 并行派发两个子代理

**Standards 子代理的提示词**应包含：

- 完整的 diff 命令和提交列表。
- 你在第 3 步找到的规范来源文件列表，**加上第 3 步的坏味道基线**，完整粘贴（子代理没有其他途径获得它）。
- 任务说明（brief）：「按相关文件/hunk 报告：(a) diff 中每一处违反成文标准的地方：引用该标准（文件 + 规则）；以及 (b) 你发现的任何基线坏味道：说出名称并引用 hunk。区分硬性违规与主观判断：违反成文标准可能是硬性的，但基线坏味道永远是主观判断，而且仓库成文的标准优先于基线。跳过工具链已强制执行的内容。不超过 400 词。」

**Spec 子代理的提示词**应包含：

- diff 命令和提交列表。
- spec 的路径或抓取到的内容。
- 任务说明（brief）：「报告：(a) spec 要求但缺失或只完成了一部分的需求；(b) diff 中未被要求的行为（范围蔓延）；(c) 看起来已实现但实现方式有问题的需求。每条发现都要引用 spec 的原文行。不超过 400 词。」

如果 spec 缺失，跳过 Spec 子代理，并在最终报告中注明这一点。

### 5. 汇总

将两份报告分别放在 `## Standards` 和 `## Spec` 标题下呈现，可原文照搬或稍作整理。**不要**合并或重排发现，因为两个轴是有意分离的（见_为什么是双轴_）。

最后用一句话总结：每个轴的发现总数，以及_每个轴内部_最严重的问题（如有）。不要在两个轴之间选出唯一的最差问题：那正是这种分离所要防止的重排。

## 为什么是双轴

一个变更可能通过一个轴，却在另一个轴上失败：

- 代码符合所有规范但实现了错误的东西 → **Standards 通过，Spec 失败。**
- 代码完全按照 issue 的要求实现，却破坏了项目的约定 → **Spec 通过，Standards 失败。**

分开报告可以防止一个轴掩盖另一个轴。
