## 完整执行流程

### Step 1：理解需求本质

**必须搞清楚五个核心问题：**

1. **问题是什么** — 这个需求解决什么痛点？用户遇到什么困难？
2. **目标用户是谁** — 影响哪些用户群体？规模多大？
3. **成功指标是什么** — 用什么数据衡量成功？目标值是多少？
4. **约束条件有哪些** — 时间、资源、技术、合规等限制
5. **上下游依赖** — 涉及哪些团队？需要谁配合？

**信息来源优先级：**
- 用户提供了背景材料 → 从中提取关键信息
- 用户只说了需求名称 → 用 AskUserQuestion 收集：

```
问题1: 这个需求解决什么问题？
选项: [根据需求名称推断 3-4 个可能场景] + Other

问题2: 目标用户群体是？
选项: [根据需求推断 3-4 个用户群] + Other

问题3: 核心成功指标是什么？
选项: [根据需求推断 3-4 个指标] + Other
```

**不要一次问超过 3 个问题**，如果用户描述已经足够清晰，跳过追问直接执行。

---

### Step 2：MoSCoW 优先级划分

用 MoSCoW 框架对需求拆解，确保聚焦核心价值：

```
Must have（必须有）:
- 没有这些功能，需求无法上线
- 直接影响核心成功指标
- 示例：用户登录、核心流程、数据安全

Should have（应该有）:
- 重要但非阻塞，可以延后一个迭代
- 显著提升用户体验或运营效率
- 示例：批量操作、快捷键、导出功能

Could have（可以有）:
- 锦上添花，资源充足时才做
- 不影响核心功能完整性
- 示例：个性化皮肤、高级筛选、动画效果

Won't have（这次不做）:
- 明确排除，避免范围蔓延
- 记录原因，便于后续规划
- 示例：跨平台支持、第三方集成、历史数据迁移
```

**输出格式：**

| 优先级 | 功能点 | 说明 | 预估工作量 |
|--------|--------|------|-----------|
| Must | 功能A | 核心流程 | 5人天 |
| Must | 功能B | 数据安全 | 3人天 |
| Should | 功能C | 体验优化 | 2人天 |
| Could | 功能D | 高级功能 | 4人天 |
| Won't | 功能E | 本期不做 | - |

---

### Step 3：策略矩阵构建

**策略矩阵 = 用户分群 × 策略手段 × 预期效果**

用于明确针对不同用户群体的差异化策略：

```
构建步骤：
1. 识别用户分群（按行为、属性、场景等维度）
2. 为每个分群设计针对性策略
3. 预估每个策略的预期效果（量化）
4. 标注策略实施难度和优先级
```

**输出格式：**

| 用户分群 | 分群特征 | 策略手段 | 预期效果 | 实施难度 | 优先级 |
|---------|---------|---------|---------|---------|--------|
| 新用户 | 首次使用，不熟悉功能 | 新手引导 + 简化流程 | 次日留存 +15% | 低 | P0 |
| 活跃用户 | 高频使用，熟悉功能 | 高级功能 + 个性化推荐 | 使用时长 +20% | 中 | P1 |
| 流失用户 | 30天未活跃 | 召回邮件 + 优惠激励 | 回流率 +8% | 低 | P1 |
| 付费用户 | 已购买增值服务 | 专属客服 + 优先体验 | 续费率 +12% | 高 | P2 |

**策略矩阵红线：**
- 每个分群必须有明确的量化特征（不能只写"新用户"，要写"注册7天内"）
- 预期效果必须量化（不能只写"提升体验"，要写"转化率 +10%"）
- 策略手段必须具体可执行（不能只写"优化"，要写"简化注册流程至3步"）

---

### Step 4：功能清单与优先级

将需求拆解为具体功能点，用 P0/P1/P2 标注优先级：

```
P0（必须上线）:
- 核心功能，阻塞上线
- 不实现则需求失败
- 示例：用户认证、核心算法、数据同步

P1（重要功能）:
- 重要但可延后一个迭代
- 影响用户体验完整性
- 示例：错误处理、日志记录、基础统计

P2（次要功能）:
- 锦上添花，资源充足时实现
- 不影响核心功能
- 示例：高级配置、自定义皮肤、导出功能
```

**功能清单格式：**

| # | 功能名称 | 优先级 | 功能描述 | 验收标准 | 预估工时 | 负责人 |
|---|---------|--------|---------|---------|---------|--------|
| 1 | 用户登录 | P0 | 支持手机号+验证码登录 | 1. 验证码60秒内到达 2. 登录成功率>99% | 3人天 | 张三 |
| 2 | 数据同步 | P0 | 实时同步用户操作到云端 | 1. 同步延迟<2秒 2. 支持断点续传 | 5人天 | 李四 |
| 3 | 操作日志 | P1 | 记录用户关键操作 | 1. 日志保留30天 2. 支持按时间筛选 | 2人天 | 王五 |
| 4 | 数据导出 | P2 | 支持导出为Excel格式 | 1. 单次最多导出1万条 2. 导出时间<30秒 | 3人天 | 待定 |

**功能拆解原则：**
- 每个功能必须有明确的验收标准（可测试、可量化）
- 预估工时必须包含开发+自测时间，不含联调和测试
- P0 功能数量控制在总功能的 30% 以内，避免全部标 P0
- 负责人未确定时写"待定"，不要留空

### Step 5：排期规划

根据功能清单和资源情况，制定迭代排期：

```
排期要素：
1. 迭代周期：通常 2 周一个迭代
2. 资源盘点：可用开发人数 × 可用天数
3. 功能优先级：P0 优先排入当前迭代，P1 排入下一迭代
4. 风险缓冲：预留 20% 时间应对突发问题
```

**排期表格式：**

| 迭代 | 周期 | 功能点 | 优先级 | 负责人 | 预估工时 | 交付日期 |
|------|------|--------|--------|--------|---------|---------|
| Sprint 1 | 2024-04-01 ~ 2024-04-14 | 用户登录 | P0 | 张三 | 3人天 | 2024-04-05 |
| Sprint 1 | 2024-04-01 ~ 2024-04-14 | 数据同步 | P0 | 李四 | 5人天 | 2024-04-10 |
| Sprint 1 | 2024-04-01 ~ 2024-04-14 | 联调测试 | - | 全员 | 2人天 | 2024-04-12 |
| Sprint 2 | 2024-04-15 ~ 2024-04-28 | 操作日志 | P1 | 王五 | 2人天 | 2024-04-18 |
| Sprint 2 | 2024-04-15 ~ 2024-04-28 | 数据导出 | P2 | 待定 | 3人天 | 2024-04-22 |

**排期红线：**
- 单个迭代总工时不能超过可用资源的 80%（预留 20% 缓冲）
- P0 功能必须在迭代前半段完成，留出联调时间
- 联调和测试时间必须单独列出，不能省略
- 交付日期必须标注，不能只写迭代周期

### Step 6：协作流程设计

**协作流程是 PRD 的核心章节，必须详细设计！**

#### 6.1 需求评审流程

```
评审前：
1. PRD 文档提前 2 天发给评审人
2. 评审人提前阅读并准备问题
3. 评审会议邀请：产品、研发、测试、设计、运营

评审中：
1. 产品讲解需求背景和目标（10分钟）
2. 演示用户流程和交互设计（20分钟）
3. 研发评估技术可行性和工时（20分钟）
4. 测试提出测试场景和风险点（10分钟）
5. 确认排期和交付物（10分钟）

评审后：
1. 整理评审纪要，24小时内发出
2. 更新 PRD 文档，标注变更点
3. 同步排期给所有相关人
```

#### 6.2 需求变更管理

```
变更触发条件：
- 业务方提出新需求
- 研发发现技术方案受限
- 测试发现重大缺陷
- 上线后数据不达预期

变更审批流程：
1. 变更发起人填写变更申请（说明原因和影响）
2. 产品评估变更必要性和优先级
3. 研发评估变更工时和风险
4. 产品负责人审批（P0/P1 变更需总监审批）
5. 更新 PRD 文档，标注版本号和变更点
6. 通知所有相关人
```

#### 6.3 上下游通知机制（极其重要！）

**核心规则：细节讨论变动至少在群里周知到 +1（直属上级）**

```
通知场景和规则：

场景1：需求细节调整（不影响排期）
- 通知对象：研发负责人、测试负责人
- 通知方式：项目群 @相关人
- 通知时限：变更确认后 4 小时内

场景2：排期调整（影响交付日期）
- 通知对象：研发负责人、测试负责人、运营负责人、直属上级（+1）
- 通知方式：项目群 @all + 邮件通知
- 通知时限：变更确认后 2 小时内
- 必须说明：调整原因、新排期、影响范围

场景3：功能范围变更（新增/删减功能）
- 通知对象：所有评审人、直属上级（+1）、业务方
- 通知方式：项目群 @all + 邮件通知 + 更新 PRD 文档
- 通知时限：变更确认后 1 小时内
- 必须说明：变更原因、影响评估、新排期

场景4：紧急问题（线上故障、重大缺陷）
- 通知对象：研发负责人、测试负责人、直属上级（+1）、总监
- 通知方式：电话 + 项目群 @all
- 通知时限：发现后 15 分钟内
```

**通知红线（不能犯）：**
- 任何排期调整必须通知到 +1（直属上级），不能只通知执行层
- 功能范围变更必须同步更新 PRD 文档，不能只口头通知
- 紧急问题必须电话通知，不能只发群消息
- 通知必须说明影响和原因，不能只说"变更了"

#### 6.4 上线前检查清单

```
上线前 3 天：
- [ ] 研发完成自测，提交测试
- [ ] 测试完成回归测试，输出测试报告
- [ ] 产品完成验收测试，确认功能符合预期
- [ ] 运营准备上线公告和用户引导材料

上线前 1 天：
- [ ] 确认上线时间和灰度策略
- [ ] 确认回滚方案和应急预案
- [ ] 确认数据监控指标和报警阈值
- [ ] 通知所有相关人上线时间

上线当天：
- [ ] 按灰度策略逐步放量
- [ ] 实时监控核心指标（UV、转化率、错误率）
- [ ] 收集用户反馈和客诉
- [ ] 确认全量上线或回滚
```

### Step 7：输出 HTML 产品文档

**输出格式：HTML 单文件，包含所有样式和交互**

HTML 文档必须包含以下章节（缺一不可）：

1. **文档头部**：需求名称、版本、作者、日期、状态
2. **目录导航**：可折叠的侧边栏目录，快速跳转各章节
3. **需求背景**：问题描述、目标用户、成功指标
4. **策略矩阵**：用户分群 × 策略手段 × 预期效果（交互式表格）
5. **功能清单**：P0/P1/P2 功能列表，支持按优先级筛选
6. **排期规划**：甘特图或时间轴，展示迭代计划
7. **协作流程**：评审流程、变更管理、通知机制
8. **风险与应对**：识别的风险点和应对策略
9. **附录**：术语表、参考文档、变更记录

**HTML 模板结构见 [PRD 模板](references/prd-template.md)**

## 分支逻辑

根据需求类型，选择不同的文档模板和重点：

### 情况 A：新功能需求

```
特征：从 0 到 1 的全新功能
文档重点：
- 详细的需求背景和用户调研
- 完整的用户流程和交互设计
- 策略矩阵（多用户分群）
- 完整的功能清单（P0/P1/P2）
- 详细的排期规划（多迭代）
```

### 情况 B：功能优化需求

```
特征：对现有功能的改进
文档重点：
- 现有功能的数据表现和问题分析
- 优化目标和预期提升幅度
- 优化方案对比（多方案 PK）
- 精简的功能清单（聚焦变更点）
- 短周期排期（通常 1-2 个迭代）
```

### 情况 C：Bug 修复需求

```
特征：线上问题修复
文档重点：
- 问题描述和复现步骤
- 影响范围评估（影响多少用户）
- 根因分析和技术方案
- 修复方案和验证标准
- 紧急排期（通常当天或次日上线）
```

### 情况 D：用户描述模糊

```
处理方式：
- 最多追问 2-3 个结构化问题（见 Step 1）
- 不要开放式追问，给选项让用户选
- 如果用户说"你看着办" → 用默认配置：
  * 需求类型：新功能
  * 用户分群：新用户 + 活跃用户
  * 迭代周期：2 周
  * 输出格式：完整 PRD
```

## 输出格式规范

每份 PRD 必须包含以下九个章节，缺一不可：

| 章节 | 内容 | 格式要求 |
|------|------|---------|
| 文档头部 | 需求名称、版本、作者、日期 | 固定顶部栏，显示文档元信息 |
| 目录导航 | 各章节快速跳转 | 侧边栏，可折叠，当前章节高亮 |
| 需求背景 | 问题、用户、目标、约束 | 文字描述 + 关键数字高亮 |
| 策略矩阵 | 用户分群 × 策略 × 效果 | 交互式表格，支持排序和筛选 |
| 功能清单 | P0/P1/P2 功能列表 | 可筛选表格，支持按优先级过滤 |
| 排期规划 | 迭代计划和时间轴 | 甘特图或时间轴可视化 |
| 协作流程 | 评审、变更、通知机制 | 流程图 + 文字说明 |
| 风险应对 | 风险点和应对策略 | 表格形式，标注风险等级 |
| 附录 | 术语、参考、变更记录 | 可折叠区块，不占主屏空间 |

## 质量红线（违反任何一条即为不合格）

1. **不准没有成功指标就写 PRD**
   - 每个需求必须有 1-3 个可量化的成功指标
   - 指标必须有目标值（不能只写"提升转化率"，要写"转化率从 5% 提升至 8%"）

2. **不准功能清单没有验收标准**
   - 每个功能点必须有明确的验收标准（可测试、可量化）
   - 验收标准不能用模糊词（如"体验好"、"速度快"），必须量化（如"加载时间<2秒"）

3. **不准排期没有缓冲时间**
   - 单个迭代总工时不能超过可用资源的 80%
   - 联调和测试时间必须单独列出
   - P0 功能必须在迭代前半段完成

4. **不准协作流程缺失通知机制**
   - 必须明确需求变更时的通知对象和通知方式
   - 排期调整必须通知到 +1（直属上级）
   - 功能范围变更必须同步更新 PRD 文档

5. **不准策略矩阵没有量化预期效果**
   - 每个策略的预期效果必须量化（不能只写"提升体验"）
   - 预期效果必须有数据支撑（历史数据、A/B 测试、行业基准）

6. **不准 P0 功能占比超过 30%**
   - P0 功能数量控制在总功能的 30% 以内
   - 如果全部标 P0，说明优先级没有真正区分
   - 用 MoSCoW 框架重新评估

7. **不准 HTML 文档缺少目录导航**
   - 文档必须有侧边栏目录，支持快速跳转
   - 当前章节必须高亮显示
   - 目录可折叠，不占主屏空间

8. **不准没有风险识别和应对策略**
   - 每个需求必须识别 3-5 个主要风险
   - 风险必须标注等级（高/中/低）和应对策略
   - 高风险必须有应急预案

## 常见陷阱（不能犯）

### 陷阱 1：需求范围蔓延

**问题**：写着写着功能越来越多，PRD 变成"许愿清单"
**正确做法**：
- 用 MoSCoW 框架严格控制范围
- Won't have 章节明确列出"这次不做"的功能
- 新增功能必须走变更流程，评估影响

### 陷阱 2：排期过于乐观

**问题**：工时估算偏低，没有预留缓冲时间
**正确做法**：
- 研发评估工时后，产品加 20% 缓冲
- 联调和测试时间单独列出，不能省略
- P0 功能排在前半段，留出应急时间

### 陷阱 3：协作流程缺失通知机制

**问题**：需求变更后只通知执行层，上级不知情
**正确做法**：
- **细节讨论变动至少在群里周知到 +1（直属上级）**
- 排期调整必须通知到 +1
- 功能范围变更必须通知到 +1 和业务方
- 通知必须说明影响和原因，不能只说"变更了"

### 陷阱 4：成功指标不可量化

**问题**：目标写成"提升用户体验"、"优化产品性能"，无法衡量
**正确做法**：
- 每个目标必须量化（如"次日留存从 30% 提升至 40%"）
- 指标必须有数据来源（如"基于埋点数据"、"基于用户调研"）
- 目标必须有时间期限（如"上线后 30 天内达成"）

### 陷阱 5：策略矩阵流于形式

**问题**：用户分群模糊，策略泛泛而谈，预期效果拍脑袋
**正确做法**：
- 用户分群必须有明确的量化特征（如"注册 7 天内的新用户"）
- 策略必须具体可执行（如"简化注册流程至 3 步"）
- 预期效果必须有数据支撑（如"基于 A/B 测试，预计提升 15%"）

### 陷阱 6：验收标准不可测试

**问题**：验收标准写成"体验流畅"、"界面美观"，测试无法验证
**正确做法**：
- 验收标准必须可测试（如"页面加载时间<2秒"）
- 验收标准必须可量化（如"成功率>99%"）
- 验收标准必须有明确的测试方法（如"使用 Chrome DevTools 测量"）

### 陷阱 7：风险识别不充分

**问题**：只写技术风险，忽略业务风险、运营风险、合规风险
**正确做法**：
- 风险识别要全面（技术、业务、运营、合规）
- 风险必须标注等级（高/中/低）
- 高风险必须有应急预案和负责人

## 与其他技能的协作

- **数据决策分析** → 需求文档撰写：数据分析结论直接用于需求背景和成功指标
- **竞品行业调研** → 需求文档撰写：竞品分析结论用于策略矩阵设计
- **埋点方案设计** → 需求文档撰写：功能清单确定后，触发埋点方案设计
- **上线效果监控** → 需求文档撰写：上线数据用于验证成功指标，指导下一轮迭代
