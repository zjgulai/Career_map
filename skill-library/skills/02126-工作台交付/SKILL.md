# PB-CTO-01：工作台交付

对应岗位：`BOBO-TECH-001`（技术一号位）。节奏依据：F2.7「一天一个工作台」、F5 四步工作流。

## 一、触发与边界

**触发**：需要为一个新的业务场景交付一个工作台。

**要产生的经营结果**：该场景下的人能在工作台里完成原本要跨系统、跨人工的一揽子操作。

**不适用**：

- 只是改文案、改样式（走迭代，不走交付流程）
- 场景未定义清楚（先走 `PB-CTO-02` 的需求澄清，或退回提出者）
- 需要新增未授权数据源（先走授权，不在本 Playbook 内解决）

## 二、输入检查

| 输入 | 来源 | 缺失时 |
|---|---|---|
| 场景定义：谁、在什么情况下、要解决什么问题 | 提出者（LL / 周健） | **停下追问**，不自行假设场景 |
| 当前人工流程与痛点 | 提出者 | 可先用现有事实基线里的场景描述，并标注来源 |
| 数据来源与授权 | 事实基线 F4；数据源本身 | 未授权即不做，记录为阻塞项 |
| 验收标准 | 提出者 | 与提出者当场对齐，写成可判定的句子 |
| 交付时间 | 提出者 | 按「一天一个」的默认节奏，超出即说明 |

## 三、判断与执行

1. **先问场景，再问实现**。场景不清楚时，任何实现都是返工。
2. **选最小可验证形态**：先做能被真实使用一次的最小闭环，不做预留扩展点的架构。
3. **确认数据通路**：数据从哪来、是否已授权、查询方式（MCP / API / 文件），逐条落实并记录。
4. **装配而非重写**：优先复用已有 preset、技能与工作台骨架。
5. **自测一遍**：以真实数据跑通一次完整操作，不留「应该能行」的环节。
6. **交付时说明取舍**：这个形态放弃了什么（响应速度 / 覆盖面 / 精度），对应 P1。

## 四、标准产物与交接

**产物**：

- 可运行的工作台（本机构建产物）
- 一页说明：场景、输入输出、数据来源与授权状态、已知限制、**放弃了什么**
- 验收记录：以真实数据跑通的证据

**接收者**：提出该场景的人（通常 LL 或周健）。

**验收要求**：接收者用真实数据完成一次完整操作；记录结果与问题。

## 五、异常、冻结与恢复

| 异常 | 处置 |
|---|---|
| 场景定义反复变更 | 冻结，回到步骤 1 重新对齐；不做「边改边做」 |
| 数据源未授权 | 冻结该数据相关范围，其余部分照常交付，授权状态写入交付说明 |
| 依赖的平台能力未验证 | 不承诺该能力，标注为未验证，改走替代方案或缩小范围 |
| 部分成功 | 明确区分「已跑通」与「未跑通」的部分，不合并陈述 |
| 提出者要求跳过自测直接交付 | 拒绝，说明跳过的风险，给出最短自测路径（对应 P4） |

## 六、反馈与改进

- 记录实际使用中的卡点、误操作、与原人工流程的差异。
- 若同一类场景出现三次以上，考虑抽象为可复用的工作台骨架。
- 规则更新（如改变默认节奏）需由决策人确认，不由本岗位自行调整。

## 七、验收情境（必须回放）

1. **正常闭环**：场景清楚、数据已授权 → 一天内交付并跑通。
2. **输入缺失**：只给了「做个能看数据的页面」→ 是否正确追问而没有假设。
3. **超出边界**：要求接入未授权的内部数据 → 是否拒绝并记录阻塞。
4. **部分失败**：数据源只通了一半 → 是否明确区分已通/未通。
5. **目标冲突**：要求「今天上线、不用测」→ 是否拒绝并给出最短验证路径。
