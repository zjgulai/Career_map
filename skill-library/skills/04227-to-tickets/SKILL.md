# To Tickets

把一个计划、规格说明或对话拆分成一组**工单（ticket）**：示踪弹（tracer-bullet）式垂直切片，每张工单都声明**阻塞（block）**它的那些工单。

议题跟踪器和分类标签词汇表应当已经提供给你。如果没有，请让用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

基于对话上下文中已有的内容工作。如果用户以参数形式传入一个引用（规格说明路径、议题编号或 URL），就获取它并通读其完整正文和评论。

### 2. 探索代码库（可选）

如果你还没有探索过代码库，先探索以了解代码当前状态。工单标题和描述应使用项目的领域术语表词汇，并尊重你所触及区域的架构决策记录（ADR）。

寻找对代码做预重构（prefactor）的机会，让实现更容易。「先让变更变得容易，再做那个容易的变更。」

### 3. 起草垂直切片

把工作拆成**示踪弹（tracer bullet）**工单。

<vertical-slice-rules>

- 每个切片都贯穿每一层（模式、API、UI、测试）切出一条窄但**完整**的路径：是垂直的，**不是**某一层的水平切片
- 一个完成的切片自身即可演示或验证
- 每个切片的规模要能装进一个全新的上下文窗口
- 任何预重构都应最先完成

</vertical-slice-rules>

给每张工单标出它的**阻塞边（blocking edges）**：必须先完成的其他工单。没有阻塞项的工单可以立即开工。

**宽幅重构（wide refactor）是垂直切片的例外。**宽幅重构是指单个机械性变更（重命名一个列、修改一个共享符号的类型），其**波及面（blast radius）**扩散到整个代码库，一次编辑就会同时破坏成千上万个调用点，任何垂直切片都无法独立保持绿灯通过。不要把它硬塞进示踪弹；按**扩展—收缩（expand–contract）**来排序。先扩展：在旧形式旁边加上新形式，让一切照常工作。然后按波及面分批迁移调用点（按包、按目录），每批各是一张工单，都被「扩展」这一步的工单阻塞，因为旧形式仍然存在，所以批与批之间持续集成（CI）保持绿灯。最后收缩：一旦不再有调用方，就删除旧形式，这张工单被所有迁移批次阻塞。当连各批次都无法单独保持绿灯时，保持这个顺序，但让它们共用一个集成分支，全部阻塞一张最终的「集成并验证」工单；只有在那里才承诺绿灯。

### 4. 向用户提问确认

把提议的拆分以编号列表呈现。对每张工单，展示：

- **标题**：简短的描述性名称
- **被谁阻塞**：哪些其他工单（如果有）必须先完成
- **交付什么**：这张工单实现并跑通的端到端行为

询问用户：

- 粒度是否合适？（太粗 / 太细）
- 阻塞边是否正确：每张工单是否只依赖真正卡住它的工单？
- 是否有工单需要合并或进一步拆分？

反复迭代，直到用户批准该拆分方案。

### 5. 将工单发布到已配置的跟踪器

发布已批准的工单。**发布方式**取决于 `/setup-matt-pocock-skills` 配置的跟踪器；无论哪种方式工单本身都一样，只有阻塞边的形态不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下为每张工单写一个文件，按依赖顺序从 `01` 开始编号（阻塞方在前）。每个文件的「被谁阻塞」列出它所依赖的编号/标题。使用下面每张工单一个文件的模板：一张工单一个文件，绝不写成单个合并文件。
- **真实的议题跟踪器（GitHub、Linear 等）** → 按依赖顺序（阻塞方在前）为每张工单发布一个议题，让每张工单的阻塞边能引用真实的标识符。平台本身有阻塞/子议题关系的就用它；否则把每张工单的「被谁阻塞」设为那些阻塞它的议题。除非另有指示，否则打上 `ready-for-agent` 分类标签；这些工单天然就是可被代理（agent）直接领取的。

从**前沿（frontier）**开始推进：即所有阻塞项都已完成、可开工的工单。对于纯线性链条，就是自上而下。

不要关闭或修改任何父议题。
