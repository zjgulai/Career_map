# 三宝无限画布 Playbook

版本：2026-10-09
用途：给人、Native Agent 设计者和后续接手的 Codex 一套共同的读图、讨论、更新和交接规则。

## 1. 先把它当成什么

这张画布不是一张“已经上线的系统截图”，也不是把旧产品原样搬进门户的目录。它是三宝经营网络与 AgenticOS 产品设计的共同工作台，用来回答：

- 当前要解决的经营问题是什么；
- 哪个角色或能力位置负责交付什么；
- 依据、输入、输出和边界在哪里；
- 下一张卡应该补哪一个证据或决定；
- 哪些内容仍只是候选，不能假装已经运行。

画布的空间位置用于分层和找路，不自动表示时间顺序、审批顺序、数据流、权限或真实执行。

## 2. 推荐的读图顺序

每次打开画布，按下面顺序读，不要一上来钻进最细的 Skill：

1. **经营网络总览**：先看三类关系——价值创造、经营治理、能力供给。
2. **三条经营主链（C-011）**：新品经营、持续经营、新市场经营。它们属于同一个网络，共享能力和事项，不是三个独立产品。
3. **共享经营事项（C-014）**：确认这次讨论围绕哪个问题、范围和端到端主责。
4. **Lead–Worker 协作**：Lead 负责把目标、依赖、取舍和遗留收回同一事项；Worker 负责自己的专业判断和交付。Lead 不吞并 Worker 的专业边界。
5. **专业责任卡**：看问题、责任角色、输入、交付、验收和未知。
6. **能力候选**：最后才看来源资产、候选 Skill、小范围工作流、Bundle 或 Preset。候选位置是“竞聘位”，不是已经任命的员工。

新市场经营必须和新品、持续经营一样从 C-011 的统一全景卡开始，再进入“新市场进入问题与范围说明”，不能从某个国家、平台或单个技能直接跳进去。

## 3. 当前右侧抽屉怎么用

右侧抽屉现在有三个固定提示：

- **第 N 层**：告诉你当前是总览、主链、事项、责任卡还是更深的证据卡。
- **阅读入口／卡片下钻**：入口是同层索引；下钻是对当前卡的补充说明。
- **只做阅读，不代表业务流程**：返回和点击只是导航，不会创建任务、授权动作或改变经营状态。

打开一张卡时，按这句话读：

> 这张卡解决什么？交付什么？下一位凭什么接？缺什么证据？哪些事仍然不能由它决定？

卡片较多时，一次只打开一张。先看卡片摘要，再进入子卡；看完用“返回上一级”，不要同时打开多个抽屉层。若只想查方向，回到“经营网络总览”；若要查来源，使用“来源库”；若要查决策沿革，使用“决策记录”。

## 4. 一张合格卡片应该包含什么

卡片不需要塞满长文，但必须能定位六件事：

| 面 | 用人话说明 |
| --- | --- |
| 要解决的问题 | 这张卡到底在处理哪一个业务难题？ |
| 责任位置 | 谁对这段判断或交付负责？是否只是候选位置？ |
| 输入 | 需要哪些事实、版本、范围、条件或前置交付？ |
| 输出 | 交给下一位的具体交付物是什么？ |
| 验收 | 下一位怎样知道“这份交付够不够用”？ |
| 边界与未知 | 哪些事情它不能替代，哪些证据还没有？ |

正式关系线尽量写出“从谁 → 向谁、传什么、依据是什么”。卡片嵌套只说明阅读层级，不能单凭嵌套关系推断数据流。

## 5. 三条主链的读法

### 01 新品经营

先看消费者需求洞察，再看商业论证、产品定义、实现、验证、上市与接续。商业验证采用客户价值、兑现能力、经营可行性三维框架（C-012）；有限放量不自动等于持续经营已经接收。

首个常用镜头是 VOC：需求证据与问题地图 → 商业论证。VOC 是验证设计的业务镜头，不是第四条主链。

### 02 持续经营

首个展开场景是“需求变化后的供给、渠道／触达与现金联合调整”（C-043）。先看需求变化判断和未来情景，再对照供给兑现、市场侧条件、经济与现金影响，最后看依赖、实际偏差和未结责任。

预测不是供给承诺，销量也不自动等于真实需求。完成一个局部动作，不自动结束整个事项。

### 03 新市场经营

从 C-011 全景入口开始，先说清“为什么进入、进入哪个范围、需要验证什么”，再进入商业论证、准入、上市、供给、渠道和首单等专业卡。国家、区域、平台和宣称都属于范围条件，不能把某一个市场样本直接写成普遍结论。

Shopify AI+BI 是持续经营的智能运营验证镜头；它和 VOC 一样用于检验产品设计，不会凭案例自动增加岗位、Skill 或经营决定。

## 6. 共享经营事项与 Lead–Worker

一个事项至少要能回查四类关联（C-014）：

1. 目标与责任；
2. 验证与证据；
3. 决定与资源；
4. 行动与结果。

Lead 负责范围、目标、依赖、选项比较、待决问题和遗留责任的整体可读性；Worker 负责自己的专业事实、判断、条件和交付。五个共同对照面是阅读骨架，不是强制统一字段、Schema、权限或工作流。

一次授权只能覆盖一组明确动作（C-016），写清责任角色、对象、动作、资源、时间和前提。前提失效、越界或出现新反证时，先停在边界上重新核对；不把“应暂停”写成现场已经暂停，也不把 Skill 存在写成有权限。

## 7. 能力状态要分开看

画布中可能同时出现以下状态，不能混用：

1. **来源资产**：原仓库、文档、方法或代码可定位；
2. **候选能力**：已经提出要解决某个子问题；
3. **来源片段／预览**：能看到局部内容或实现线索；
4. **候选提交包**：按 C-376 收件合同交齐版本、具名地址、输入输出和边界证据；
5. **Skill／Bundle／Preset**：经过明确的制作、验证和范围化生效；
6. **数字员工工作台**：有职责、知识、工具和授权的组装；
7. **运行事实**：有真实输入、输出、日志、结果和独立验收；
8. **真实业务动作**：另需明确授权，不能由画布或静态样本代替。

C-376 的最小收件闸包含：自有版本、至少两个具名 C 地址样本、输入输出锚点、交接／RETURN、失败隔离、停止反例等证据。缺一项就标 `RETURN／待补证`，不向下冒充 Preset 或 Runtime。

## 8. 什么时候可以更新画布

每轮只推进一个依赖最靠前的问题。用户确认一个决定后，更新时必须同时说清：

- **新增了什么**：具体卡、关系或状态文案；
- **放在哪里**：总览、哪条主链、哪张父卡下面；
- **改变了哪条阅读路径**：从哪张卡可以进入、返回到哪里；
- **保留了什么**：旧节点、旧关系、未定项和 Skill 竞聘空位；
- **没有做什么**：没有把候选变成运行，没有新增未决定的岗位或动作。

不要通过不断缩小字号、堆叠长文或横向追加单行来“容纳更多内容”。新内容优先进入卡片下钻，主总图保持正方形、留白和可读连线。

## 9. 证据和来源的最小记录

任何候选或决定至少记录：来源名称、路径或 URL、定位信息、版本或时间、适用范围、原文事实、专业判断、未知和下一次核对条件。把原始事实和解释分开；把设计态与运行态分开。

不能用以下内容替代运行证据：

- GitHub 目录或索引存在；
- 历史“绿色”状态；
- 静态页面、截图或合成样本；
- 浏览器原型点击成功；
- 37 个 Skill 的聚类数量；
- 一次成功的模型预览。

## 10. 每轮验收清单

提交下一轮前，逐项回答：

- 三条主链是否仍从同一经营网络进入？
- 新市场是否从 C-011 全景卡开始？
- 卡片是否显示问题、角色、输入、输出、验收和边界？
- 连线是否写明方向、对象和依据？
- Lead 是否只做协调和取舍，Worker 是否保留专业判断？
- 3+50 是否保持“姓名 + 岗位名称”，且没有被误写成任命或运行？
- Skill 候选是否仍留有竞聘位置？
- 候选、已验证、运行和真实动作是否分开？
- 是否保留未知、RETURN 和停止条件？
- 页面在当前视口中是否可读，抽屉是否没有重叠遮挡？

## 11. 交接格式

交给另一台电脑或另一个 Codex 时，固定写六行：

1. 当前断点和最近决策号；
2. 已确认的主线、接口和不变量；
3. 当前候选及证据状态；
4. 下一张要展开的卡和完成标准；
5. 明确禁止越界的动作；
6. 文件路径、commit、远端 push 和未验证事项。

这份 Playbook 是画布的使用规则，不是把设计态直接变成生产系统的授权书。
